## 二、把项目压缩成三层叙事（先背这个，其余都是补充）

### 30 秒版（自我介绍里那一段）
> "我做的是一个**给电商运营团队用的 AI 助手**，叫掌柜。它不是一个聊天机器人：用户用自然语言提问，系统先做**意图路由**，分析类问题会拆成多个子任务**并行执行**（每个子任务是一个独立的 ReAct 循环），最后**综合成经营报告**；整个执行过程通过 SSE 实时推到前端，用户能看见它在干什么。"

### 3 分钟版（骨架 + 三个亮点 + 一个边界）
- **骨架**：intent →（planner → executor×N → synthesizer）/ content / service / document，四角色编排；自研 48 行 AgentGraph 状态图（条件边 + 异步节点）；LLM 层有 BaseLLM 抽象 + BudgetedLLM 预算装饰器。
- **亮点 1（可观测）**：SSE 事件流（intent / plan / subtask / token / report / usage / document）→ 前端活动流，把 Agent 从黑盒变成"看得见在干活"。
- **亮点 2（可靠性）**：工具有统一契约层（工具名 / 必填 / 类型校验 + 本体异常兜成结构化错误回喂 LLM）；并行子任务异常隔离 + 降级；LLM 预算超限**降级出报告**而不是抛 500。
- **亮点 3（评测）**：三层尺子 —— 检索层 51 条金标（Recall@5 / Hit@1 / MRR，四策略对比）、回答层（幻觉数字筛查 + 扰动测试）、**编排层 15 条金标 6 项指标**（意图准确率 / 工具召回与精确率 / 必要维度覆盖率 / hint 合规率 / 报告数字有据率 / 成本）。
  **编排层真机实测（2026-09-15，qwen3.7-flash，15 条全过）**：意图路由 **15/15**、必要维度覆盖 **18/18**、hint 合规 **13/13**、工具召回 **100%**（精确率 76%）、报告数字有据 **166/177（94%）**；平均每轮 **5.3 次 LLM 调用 / 51s**（15 条共 79 次调用、113k tokens、766s）。
- **边界**：没做反思（Reflection）回路、没做多角色同时分派、工具没有行级权限 —— 并说清下一步。

### 10 分钟版（按数据流讲，每层一句"为什么"）
1. **为什么路由**：查数、写文案、答售后、处理文档四类任务的上下文需求 / 输出契约 / 失败模式都不同，塞进一个 prompt 会互相污染 → 一次廉价 LLM 分类 + 条件边。
2. **为什么分析要拆**：LLM 一次算多步易错且贵；拆成 2~5 个**互相独立**的子任务可并行（asyncio.gather），每步可观测可复核。
3. **为什么子任务又是 ReAct**：子任务内部要多次查数才能下结论（先查销量 → 发现跌 → 再查库存），单次调用做不到。
4. **为什么工具有契约层**：LLM 会传错参数（比如中文日期"本周"），异常不能让整条链路崩 → 统一校验 + 结构化错误回喂，让它自己改。
5. **为什么要有预算**：ReAct 的调用次数由 LLM 自己决定，不加预算成本不封顶 → 预算卡在 **LLM 层**（装饰器），因为 Graph 节点看不见循环内部的调用。
6. **为什么要评测**：没有尺子就不知道改 prompt 是变好还是变坏 → 三层评测 + 改前后对比同一份金标集。

## 四、5 个缺口 + 最小补齐方案

> 原则：**缺口不要装作没有**。"我知道但没做 + 为什么 + 下一步怎么做" 是高级信号。

1. **反思 / Reflection（题 6、15）** —— 最小方案：synthesize 节点判"结果不足以回答目标"时发 replan 信号，图上加一条回 planner 的边，最多补一轮。讲法："反思我倾向做成**编排层的 replan 回路**，而不是让模型自评 —— 自评容易自我肯定。"
2. **记忆压缩（题 12）** —— 概念要补：滑动窗口 / 摘要压缩 / 分层摘要 / 关键信息抽取。现状是"整条丢 + 截断"，讲清取舍（简单可预测，但会丢细节）。
3. **中断恢复（题 18）** —— 讲法：状态在 SQLite 可恢复会话，但**执行中的图不可断点续跑**；AgentGraph 预留了 interrupt_before 却没实现，要做需要 state 快照落库 + 幂等恢复。
4. **工具行级权限（题 24）** —— 真该补：现在所有数据工具查的都是全库数据，多店铺 / 多租户场景就是越权。最小方案：注册工具时注入 user_id / shop_id，SQL 层统一加过滤条件（和文档下载"路径写死 user_id"同一个思路）。
5. **多角色动态分派（题 16）** —— 讲法：现在单意图单路由，"分析这周数据并写成周报"这种跨角色任务只能做一半。**已经补了一半**：技能层让工具范围跟着**技能**走（技能可声明 `scopes: analysis, document`，registry 取并集），所以"这个流程需要哪些角色"现在有地方可表达了。**还差的一半是「顺序」**：子任务是 `asyncio.gather` 并行的，"查完数据 → 把结论落盘成文档"里第二步依赖第一步的输出，这就是升级路径 —— planner 输出带依赖的规划、executor 按拓扑序调度（依赖图 / DAG）。注意别把"技能声明了跨角色范围"讲成"跨角色任务已经能跑"：`subset_scopes` 目前只有单测覆盖，还没有真实技能用到跨角色。

## 七、面试时主动交底的三张"边界牌"（最能加分）

1. **死循环**：planner 的 id 重编号里 len() 是循环不变量 → 同步 CPU 自旋堵死整个事件循环；用 faulthandler 打出栈定位，改成滚动候选 + 补回归用例（**先验证用例在修复前会失败**）。
2. **异常隔离**：裸 asyncio.gather 会让一个子任务的异常中断整轮、丢掉其他子任务已查好的结果；改成逐格降级 + return_exceptions=True，并用测试断言"成功那格的结果真的进了综合报告"。
3. **记忆写库语义**：覆盖式写入对"全量快照"有效、对"增量提炼"就是丢数据 → 读-合并-写；进一步把"召回热度"与"语义重要性"拆开（召回不该让一条记忆变得更"重要"）。

## 八、怎么用这份文档（循环，而不是通读）

    抽一题 → 口述 60 秒（录音） → 翻第三节核对证据 → 不会就标红
      → 标红的当天补（第四节方案 / 分册文章） → 第二天先复述昨天标红的题 → 再抽新题

**判断"这题我会了"的唯一标准：不看文档，90 秒内说出「结论 + 项目里的一处具体证据 + 一个取舍」。**
