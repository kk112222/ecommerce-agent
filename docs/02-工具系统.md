# 02 · 工具系统

> 第 01 章的 LLM 会"思考"，但它只会说话、不会干活。
> 这一章给它装上"手"——把数据库查询、文案生成、知识库检索都包装成它**能调用**的工具。

---

## 本章目标

读完这一章，你会明白：

1. 一个工具由哪**三件套**组成（说明书 / 本体 / 结果）
2. 工具怎么**注册**、怎么让 LLM 看见
3. 为什么必须有一层**参数契约**，把 LLM 的脏输入收口
4. 怎么给工具划**能力边界**，不让子任务乱调

---

## 一、先看痛点：直接把函数丢给 LLM 会怎样

最朴素的想法：LLM 要查销售，那就把查销售的函数给它。

但马上撞上三个问题：

| 问题 | 后果 |
|---|---|
| **没有说明书** | LLM 不知道有哪几个工具、每个要传什么参数 → 它只能瞎猜 |
| **参数是脏的** | LLM 生成的参数完全不可信（中文日期"本周"、写错键名）→ 直接炸 |
| **什么都能调** | 10 个工具全摆出来 → 分析任务可能去调写文件的工具 |

所以工具不是"一个函数"，而是**三件套 + 一套契约**。

---

## 二、三件套：说明书 / 本体 / 结果

代码在 `backend/core/tool/base.py`，一共 23 行：

```python
class ToolSpec(BaseModel):
    """工具的 JSON Schema 说明书 —— LLM 据此判断何时调用"""
    name: str
    description: str
    parameters: dict

class ToolResult(BaseModel):
    success: bool
    data: Any
    error: Optional[str] = None

class BaseTool(ABC):
    spec: ToolSpec

    @abstractmethod
    async def execute(self, **kwargs) -> ToolResult:
        ...
```

| 件 | 作用 | 给谁看 |
|---|---|---|
| `ToolSpec` | 说明书：叫什么、干什么、参数长什么样 | **给 LLM 看** |
| `BaseTool` | 本体：真正干活的方法 | 给程序执行 |
| `ToolResult` | 结果：成功与否 + 数据 + 错误 | **给 LLM 看**（回灌） |

> 注意 `spec` 是**类属性**、`execute` 是**抽象方法**。继承 `BaseTool` 就必须实现 `execute`，想不写说明书都不行。

## 三、注册中心：ToolRegistry

工具有了，还得有个地方**集中管理**。`backend/core/tool/registry.py`：

```python
class ToolRegistry:
    def __init__(self):
        self.tools: dict[str, BaseTool] = {}

    def register(self, tool: BaseTool):
        self.tools[tool.spec.name] = tool        # ← key 是 spec.name

    def get_all_specs(self):                     # 转成 OpenAI 格式给 LLM
        return [{"type": "function", "function": {
            "name": t.spec.name,
            "description": t.spec.description,
            "parameters": t.spec.parameters,
        }} for t in self.tools.values()]
```

**这里有个容易踩的坑**：key 是 `tool.spec.name`，**不是类名、不是文件名**。

比如 `SalesQueryTool` 在 `sales_query.py` 里，但它的 `spec.name` 是 `query_sales`——**LLM 看到、调用时用的都是 `query_sales`**。写文档或排查问题时如果按文件名去找工具，会找不到。

**三层注册**（显式函数注册，不是自动扫描）：

```
backend/tools/__init__.py
    └─ register_all_tools(registry, llm, context)
         ├─ register_data_tools(registry)              # 5 个数据工具
         ├─ register_content_tools(registry, llm)      # 2 个内容工具（要 llm）
         ├─ register_service_tools(registry)           # 1 个知识库检索
         └─ register_document_tools(registry, llm, context)  # 2 个文档工具（要 context）
```

加一个新工具只要两步：写一个 `BaseTool` 子类 → 在对应子包的注册函数里加一行 `registry.register(...)`。

> 为什么不自动扫描？显式注册多写一行，但**依赖关系一眼可见**——内容工具需要 `llm`、文档工具需要 `context`，这些从注册函数的签名上就看得出来。

## 四、契约层：把 LLM 的脏输入收口

这是整个工具系统**最值钱**的一段（`registry.execute`）。参数是 LLM 生成的，属于**完全不可信输入**，所以统一在这里兜四类：

```python
async def execute(self, name: str, **kwargs) -> ToolResult:
    # 1. 工具名不存在 → 可读错误（还列出可用工具）
    tool = self.tools.get(name)
    if tool is None:
        return ToolResult(False, None, f"没有名为 {name} 的工具，可用工具：{list(self.tools)}")

    # 2. 缺必需参数 → 报错，并附上该参数该传什么（描述取自 spec）
    missing = [p for p in required if p not in kwargs or kwargs[p] in (None, "")]
    if missing:
        return ToolResult(False, None, f"调用 {name} 缺少必需参数：{detail}。请补齐后重新调用。")

    # 3. 多传 / 传错键名 → 过滤掉（LLM 常写错键名，工具签名接不住会抛 TypeError）
    clean = {k: v for k, v in kwargs.items() if k in props}

    # 4. 类型不对 → 能救的救，救不了当场报错
    ...

    try:
        return await tool.execute(**coerced)
    except Exception as e:
        return ToolResult(False, None, f"调用 {name} 失败：{type(e).__name__}: {e}。请检查参数后重试。")
```

**最关键的设计是"返回错误"而不是"抛异常"。**

因为抛出去会**打死整个 ReAct 循环**（讲义 01 的第 ④ 步就是 `registry.execute`）；而返回一个结构化错误，模型能**读懂并自我纠正**。它看到的是：

```
调用 query_sales 的参数 start_date 类型不对：应为字符串，实际收到 int（20260701）。请改正后重新调用。
```

下一轮它就把参数改对了。这正是讲义 01 那句话的落地：**错误不是终点，是下一轮的输入。**

**`_coerce` 的"能救的顺手救"**：`"3" → 3`、`3.0 → 3`、`True → 1`——LLM 传个数字字符串是常事，没必要为这个让它重试一轮。救不了（比如 `"本周"` 这种非日期字符串）才报错。

> 注意第 2、3 步是**配合**的：先把 spec 没声明的键全部过滤掉，如果 LLM 把 `start_date` 写成了 `start`，过滤后就变成"缺参数"，正好触发一条准确的错误提示。

## 五、能力边界：按角色隔离

工具越加越多，就要防"乱调"。`registry.py` 里写死了四组角色范围：

```python
TOOL_SCOPES = {
    "analysis": ["query_sales", "category_query", "check_stock", "user_profile", "product_query"],
    "content":  ["title_optimizer", "copy_generator"],
    "service":  ["search_knowledge_base"],
    "document": ["optimize_document", "write_document"],
}
```

```python
registry = self.registry.subset_scopes(scopes or ["analysis"])   # 按角色取工具子集
```

`subset_scopes` 返回的是**一个新的 Registry**，里面只有那几个工具——**模型连别的工具的说明书都看不到**，比"在 prompt 里叮嘱它别乱调"硬得多。

**为什么绑"角色"，不绑"单条子任务"？**（这是一次真实的教训，2026-09-16 调整）

最早的做法是"按 `tool_hint` 只给一个工具"。听起来更严格，其实是**绑错了层**：

> 子任务的语义是"**回答一个问题**"，它天然可能要用多个工具——查销售发现跌了、再去查库存、必要时看会员结构。锁成单工具时，planner 拆得不够细，子任务就会**静默给出残缺结论**：不报错、报告看着还挺完整，比"越界调用"更难发现。

现在边界绑在**角色**上，`tool_hint` 降级为"建议优先使用"的提示：

- **跨角色越界依然被挡**：分析子任务想调 `write_document` 写文件，schema 里根本没这个工具；
- **同角色内可以交叉验证**：5 个数据工具自由组合。

**降级原则**：范围名为空 / 工具没注册 → **放开全集**，但必须告警。宁可不隔离，也不能把子任务锁死；但**静默降级 = 没人查得到**，所以一定要留日志。

## 六、一个真实工具长什么样

### 6.1 最简单的：查销售 `query_sales`

```python
class SalesQueryTool(BaseTool):
    spec = ToolSpec(
        name="query_sales",
        description="查询某段时间的销售数据，返回总销售额和订单数",
        parameters={
            "type": "object",
            "properties": {
                "start_date": {"type": "string", "description": "开始日期"},
                "end_date":   {"type": "string", "description": "结束日期"},
            },
            "required": ["start_date", "end_date"],
        },
    )

    async def execute(self, start_date: str, end_date: str):
        start = datetime.strptime(start_date, "%Y-%m-%d")
        end = datetime.strptime(end_date, "%Y-%m-%d").replace(hour=23, minute=59, second=59)
        async with AsyncSessionLocal() as db:
            result = await db.execute(
                select(func.sum(Order.amount)).where(Order.order_date >= start, Order.order_date <= end)
            )
            total_amount = result.scalar() or 0
        return ToolResult(success=True, data={
            "时间段": f"{start_date}~~{end_date}",
            "总销售额(元)": round(total_amount / 100, 2),
            "总订单数": total_orders,
        })
```

两个细节：

- **`end` 要补到当天 23:59:59**：不然查"到今天"会把今天的订单漏掉（日期只到 00:00:00）；
- **`total_amount / 100`**：数据库里金额**存的是分**（避免浮点误差），返回给 LLM 时转成元。这个决策在第 03 章讲。

### 6.2 带依赖的：工具也能用 LLM

```python
class TitleOptimizer(BaseTool):
    def __init__(self, llm):
        self.llm = llm

    async def execute(self, product_name, keywords, platform):
        prompt = f"为'{product_name}'生成3条{platform}平台标题，关键词: {keywords}"
        response = await self.llm.chat([Message(role="user", content=prompt)])
        return ToolResult(success=True, data={"标题": response.content})
```

**工具内部也能调 LLM**——所以它拿到的 `llm` 就是那个带预算的 `BudgetedLLM`，这些调用同样算进本轮成本（这就是"预算为什么必须卡在 LLM 层"的原因）。

### 6.3 带上下文的：会话/用户隔离

```python
def register_document_tools(registry, llm, context=None):
    ctx = context or {}
    registry.register(OptimizeDocument(llm))
    registry.register(WriteDocument(
        user_id=ctx.get("user_id"),
        session_id=ctx.get("session_id"),
        on_document=ctx.get("on_document"),   # 落盘后立刻推 SSE 事件给前端
    ))
```

文档工具需要知道"**给谁写、写到哪**"，所以注册时把 `user_id/session_id` 注入进去（生成物隔离到各自的 `outputs/` 子目录）。**这层隔离同时是安全边界**——用户只能拿到自己的文件。

## 七、验证一下

工具系统的验证很直接：**绕过 Agent，直接调 `registry.execute`**。

```python
registry = ToolRegistry()
register_all_tools(registry, llm)

# 正常调用
print(await registry.execute("query_sales", start_date="2026-09-01", end_date="2026-09-07"))
# → ToolResult(success=True, data={'时间段': '...', '总销售额(元)': 12345.6, ...})

# 故意喂脏参数，看契约层有没有兜住
print(await registry.execute("query_sales", start_date=20260901, end_date="2026-09-07"))  # 类型错
print(await registry.execute("query_sales", start="2026-09-01"))                          # 键名错+缺参
print(await registry.execute("不存在的工具"))                                              # 工具名错
```

正确的结果是：**都不抛异常，都返回可读的 `success=False`**。

项目 `tests/` 目录里有 151 项**离线用例**（用假 LLM，不联网、不花额度）——这正是第 01 章依赖倒置的红利：`BaseLLM` 是抽象类，测试时换成假的就能跑。

## 本章小结

- 工具 = **说明书（ToolSpec）+ 本体（BaseTool）+ 结果（ToolResult）**
- 注册中心 key 是 **`spec.name`**，不是文件名；加工具 = 写类 + 注册一行
- **契约层**把 LLM 的脏参数收口成**结构化错误**，让它自己改——不抛异常打断循环
- **能力边界绑角色**（`subset_scopes`），跨角色挡住、同角色自由组合；单工具硬锁会**静默给出残缺结论**

## 练手挑战

**挑战一（必做）：写一个 `check_coupon` 工具**

查某个优惠券的使用情况，参数 `coupon_id`（字符串，必填）。实现 `ToolSpec` + `execute`，注册进 `data_tools`。

**验收**：`await registry.execute("check_coupon", coupon_id="C001")` 能返回结果；`coupon_id` 传成 int 也能被 `_coerce` 救回来。

**挑战二（推荐）：给它加一类"应该被拒绝"的参数**

让参数声明 `type: "integer"`，然后测试传一个 `"abc"`。确认契约层返回的是可读错误、而不是抛异常。

**挑战三（加分）：证明隔离真的生效**

构造一个只含 `content` 角色的 registry，尝试 `execute("query_sales", ...)`，确认返回的是"没有名为 query_sales 的工具"，并观察日志里的降级告警。
