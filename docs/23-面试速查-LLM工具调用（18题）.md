## 二、强项 6 题（讲满 90 秒，带证据）

### 第 1 题｜什么是 Function Calling？原理是什么？

**【开口第一句】**
Function Calling 不是模型真的去执行函数，而是**模型输出一段结构化的"调用意图"（工具名 + JSON 参数），由程序去执行、再把结果喂回对话**。模型只负责"点名"，执行权始终在程序手里。

**【你项目里的证据】**
- 工具说明书 `ToolSpec`（name/description/parameters 的 JSON Schema）→ `registry.get_all_specs()` → 每次 `llm.chat(messages, tools=...)` 带上；
- 模型返回 `tool_calls`（id + name + arguments）→ `registry.execute(name, **args)` → 结果作为 `role=tool` 消息回灌，**必须带 `tool_call_id`** 与请求配对（OpenAI 协议要求成对出现，缺一半下次请求 400）；
- ReAct 循环：`for _ in range(max_rounds)` 直到模型不再返回 tool_calls。

**【可能追问】模型是怎么"知道"该调哪个工具的？**
答：全靠**工具描述**和参数 schema（以及 prompt 里的硬规则）。所以工具描述写得清不清楚，直接决定选择准确率 —— 我项目里还额外用 `tool_hint`（首选工具）和角色范围收窄来降低选错概率（见第 17 题）。

### 第 9 题｜Skill 是什么？

**【开口第一句】**
Skill 是**固化的流程知识**：它不新增任何能力，只回答"这件事该怎么做"（分哪几步、按什么口径、输出什么形状）。和 Tool 的区别是：Tool 回答"能做什么"（一次原子调用）。

**【你项目里的证据（你刚实现的）】**
- `backend/skills/*.md`：front-matter 声明 `name / title / when / scopes / save`，正文写口径与输出要求 —— **目录即注册表**，加技能不用改代码；
- **渐进披露**：常驻 planner prompt 的只有元数据（name + 一句话 when，几十 token）；只有 planner 判定命中，才把正文拉进 context **重新规划一次**；没命中一个字都不加载；
- 命中后：`scopes` 决定 executor 的工具范围（`registry.subset_scopes()`），`save` 决定报告产出后由 `save_node` 自动落盘；
- 降级留痕：编造技能名 → 忽略 + 告警；命中后二次规划输出废 → **回退第一轮计划且技能不计命中**（否则"权限放宽了、流程没生效"）。

**【可能追问】技能和"把 prompt 写长"有什么区别？**
答：常驻 prompt = 每加一个技能永久多几百 token，会像工具 schema 一样越堆越大；渐进披露的账是"常驻成本 ≈ 技能数 × 几十 token，正文只在命中时付一次"。

### 第 11 题｜Function Calling、Skill、MCP 三者区别？

**【开口第一句】**
三者是**三个层次**：Function Calling 是"模型怎么表达调用意图"（协议格式）；Skill 是"这类事该怎么做"（流程知识）；MCP 是"能力怎么标准化接进来"（接口标准）。

**【你项目里的证据】**
- FC：`ToolSpec` + `tool_calls` 回灌（第 1 题）；
- Skill：`backend/skills/`（第 9 题）；
- MCP：**我没落地**，但我的 `ToolRegistry` 天然能映射成 MCP tool（工具名 + description + JSON Schema 就是 MCP tool 的三要素），差的只是一层 server 封装。

### 第 14 题｜WebSocket 和 SSE 的区别与局限？

**【开口第一句】**
SSE 是**单向**（服务端 → 客户端）、基于 HTTP、文本、浏览器原生支持且自动重连；WebSocket 是**全双工**（双向），但要自己处理心跳/重连/鉴权，协议更重。

**【你项目里的证据】**
- 我用 **SSE** 做整个 Agent 执行过程的流式：事件类型 `intent / plan / subtask / token / report / usage / document`，前端活动流据此实时渲染（每步耗时、工具名、失败标红）；
- 为什么 SSE 够：Agent 的推送是**单向**的（客户端只要发一个 POST 就等着收事件），不需要双向；而且 SSE 走 HTTP，和现有 FastAPI/JWT/中间件天然兼容；
- 工程细节：`asyncio.Queue` 桥接后台任务与响应流、`None` 当结束哨兵、`finally` 必送结束信号（否则前端永久转圈）、`X-Accel-Buffering: no` 防 Nginx 缓冲。

**【可能追问】那什么场景必须上 WebSocket？**
答：需要客户端**中途频繁上行**的场景 —— 语音实时对话（边说边发音频）、协作编辑、需要服务端主动问客户端要数据的交互。纯"提问 → 流式看结果"用 SSE 更省事。

### 第 17 题｜工具很多时怎么做 Tool Routing，省 token 又避免选错？

**【开口第一句】**
核心思路是**别把所有工具都给模型**：按角色/技能收窄可见工具集，工具再多就上"动态检索"。我给子任务的工具范围是**角色级白名单**，不是全量。

**【你项目里的证据（这条你踩过两轮，最有讲头）】**
- `TOOL_SCOPES` + `registry.subset_scope("analysis")`：分析子任务只拿到 5 个数据工具（不是全部 10 个）→ 每轮少传一半 schema；跨角色工具（写文件、生成文案）**根本不在 schema 里**；
- `tool_hint` 从"权限边界"降级成"建议优先使用"的提示（因为按单条子任务锁死工具会让拆解不准时**静默给出残缺结论**）；
- 技能可以声明多个 scope，`subset_scopes()` 取并集（为跨角色流程准备）；
- 再往上（工具上百个时）才是**动态工具检索**：把工具描述向量化，每轮按意图召回 top-k 再拼进 schema（Dynamic ReAct 那条路线）—— 我没实现，因为 10 个工具用不上。

**【可能追问】那"职责隔离"和"能力完整"怎么平衡？**
答：**边界绑在角色上，不绑在单条子任务上**。判据是"约束作用的对象是不是系统里真实存在的职责单元" —— 子任务是一次性执行实例，角色才是。

### 第 18 题｜工具调用格式非法、参数错、超时或失败时怎么容错？

**【开口第一句】**
三条原则：**失败不让链路崩、错误要变成模型能看懂的反馈、结果不能是空的**。我的工具层（registry）把所有不可信输入收在一处兜。

**【你项目里的证据（你最强的一题）】**
- **四类兜底**（全在 `registry.execute`）：工具名不存在 → 列出可用工具；缺必填参数 → 附参数说明；多传/传错键名 → 过滤；**工具本体抛异常 → 兜成可读 error**（不是抛出去打死循环）；
- **类型校验**：按 spec 声明的 type 校验并能救就救（`"3"` → 3），救不了直接回可读错误 —— 让模型一次改对的概率更高；
- **错误回灌**：`_result_text` 把 error 一起喂回对话 —— 早期只喂 `data`（失败时是 None），模型看到一个 None 就懵了，没法自我纠正；
- **超时/预算**：ReAct 轮次上限 + LLM 层全局预算（12 万 token / 240s），超限**降级出报告**而不是抛 500；
- **并行容错**：`gather(return_exceptions=True)` + 逐格降级（一个子任务失败只影响那一格）；注意 `gather` 抛异常时**不会取消兄弟协程**（token 白烧，但结果要保住）；
- **评测兜底**：编排评测里"报告数字有据率"专筛"报告里编的数"。

## 四、缺口 2 题（诚实 + 方案，不用背）

### 第 6 题｜MCP 和 Function Calling 的区别？有没有实际跑过 MCP？

**【答法】**
"区别在于**标准化与复用范围**：Function Calling 是我自己系统内部的调用约定（工具名 + JSON Schema + 结果回灌）；MCP 是把这套约定标准化，让**同一个 server 能被任何兼容客户端复用**，也让我能接第三方工具。"
"**我没实际跑过 MCP**（诚实）。但它和我的工具层是一一对应的：`ToolRegistry` 里每个工具的 name / description / JSON Schema 就是 MCP tool 的三要素，`execute` 就是调用入口 —— 缺的只是一层 server 封装（FastMCP 几十行），逻辑不用重写。这也是我抽象工具层的收益：**接口早抽象好了，标准化只是加件外衣。**"

### 第 15 题｜为什么要用 WebRTC？它和 WebSocket 在 AI 对话流中的核心差异？

**【答法】**
"核心差异是**传输语义**：WebSocket 跑在 TCP 上、适合文本/二进制消息；WebRTC 走 UDP + 有丢包补偿与回声消除，是为**实时音视频**设计的。所以语音实时对话（边说边传音频、要求低延迟、允许丢一点包）用 WebRTC；文本流式对话用 SSE/WS 就够。"
"**我项目里是纯文本交互**，所以用 SSE；如果要加语音，我会在前面加一层实时音频通道（WebRTC 或厂商的实时 API），Agent 编排层（意图/计划/工具）不用改。"
