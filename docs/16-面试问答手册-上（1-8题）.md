## 第 1 题｜什么是 Agent？与大模型有什么本质不同？

**【开口第一句】**
大模型只会「生成文本」，Agent 能「循环决策 + 调工具 + 看结果再决定下一步」。

**【60 秒口播】**
本质区别在于**有没有闭环**。我项目里 backend/core/llm/qwen.py 的 chat 方法就是纯大模型：给它一段对话，它回一段文本，一次结束；它没有你的数据库，问「这周充电宝卖得怎么样」只能编。

Agent 多的是那个 while 循环（backend/agents/data_analysis/simple_agent.py）：把工具的 JSON Schema 一起传给模型，模型说「我要调 product_query(keyword=充电宝)」，程序真的去查库，把结果塞回对话，模型再基于**真实数据**总结。这个「决策 → 执行 → 观察 → 再决策」的循环就是 Agent 和聊天机器人的分水岭。

还有一点很关键：**工具的说明书（schema）和执行代码是分开的**，模型只能点名，执行权始终在程序手里 —— 这是可控性的基础。

**【项目证据】**
- 纯 LLM 一次调用：core/llm/qwen.py 的 chat
- Agent 循环：simple_agent.py 第 30-53 行，五个动作
- 工具只暴露 schema：registry.get_all_specs()

**【可能追问】Agent 一定要循环吗？**
答：不一定。单跳查询（「查一下库存」）一次工具调用就够；循环是为了「一次不够、要根据中间结果再决定」的任务。我项目里两种都有：客服/内容链路基本一轮，分析链路的子任务是真的多轮。

**【状态】** ✅

## 第 2 题｜Agent 的基本架构由哪些核心组件构成？

**【开口第一句】**
五个部分：LLM（决策）、Tools（执行）、Memory（记忆）、Planning（拆解）、Runtime（调度与观测）。我按三层落地：引擎层 → 角色层 → 编排层。

**【60 秒口播】**
- **LLM 层**：抽象成 BaseLLM（core/llm/base.py），统一 Message / ToolCall / TokenUsage / LLMResponse，换模型只改工厂一行；外面还包了一层 BudgetedLLM 做预算。
- **工具层**：ToolSpec（JSON Schema 说明书）+ BaseTool + ToolRegistry（按名字取、按 spec 校验参数、兜住工具本体异常）。现在注册了 10 个工具：5 个数据、2 个内容、1 个知识库检索、2 个文档。
- **记忆层**：会话消息（chat_messages）、长期记忆（long_term_memories，分 semantic 画像和 episodic 情景两类）、兜底一句话画像。**SQLite 是事实源，qdrant 只当向量索引。**
- **规划层**：planner 把目标拆成 2~5 个互相独立的子任务，并给每条标注该用哪个工具。
- **运行时/编排**：自研 AgentGraph（48 行状态图，支持异步节点与条件边）+ 事件流（SSE）把执行过程推给前端。

**【项目证据】**
- core/llm/、core/tool/、core/memory/、agents/（planner/executor/synthesizer/supervisor）、core/agent/base.py
- 10 个工具：query_sales、category_query、check_stock、user_profile、product_query、title_optimizer、copy_generator、search_knowledge_base、optimize_document、write_document

**【可能追问】这些组件能不能少一个？**
答：能。单轮工具调用可以没有 Planning 和 Memory（我项目里客服链路就几乎不依赖规划）；但**只要开始多轮，Memory 和 Runtime 观测基本是必需品**，否则出问题无从排查。

**【状态】** ✅

## 第 3 题｜Workflow、Agent、Tools 三个概念和区别？

**【开口第一句】**
Tools 是原子能力，Workflow 是预先定死的调用流程，Agent 是让模型自己决定调用流程。**我项目里三者同时存在，而且是嵌套的。**

**【60 秒口播】**
- **Tools**：查销售额、查库存、检索知识库、写文档……都是一个函数 + 一份 schema。
- **Workflow**：我的分析链路就是 Workflow —— supervisor 里定义好的固定图：intent → planner → executor（并行）→ synthesizer，走哪条边基本是代码写死的（只有意图那一个条件边）。
- **Agent**：这个 Workflow 里的**每个子任务内部**又是 Agent —— executor 交给 ReActAgent，模型自己决定查几次、查什么。

所以我不是「选一个」，而是**用 Workflow 管住 Agent**：外层流程可预测、可观测、可降级；内层保留自主性。这是我做这个项目最重要的架构判断。

**【项目证据】**
- 固定图：agents/supervisor.py（add_edge / add_condition_edges）
- 子任务自主：agents/executor.py + simple_agent.py

**【可能追问】为什么不让模型决定整条流程？**
答：能，但代价是不可预测 —— 生产系统里我需要「最少几步、最坏几步、超了怎么办」是确定的。我现在每步都设了上限和预算，超限降级出报告。

**【状态】** ✅

## 第 4 题｜了解哪些 Agent 设计范式？Agent 和 Workflow 的区别？

**【开口第一句】**
我知道并用过四种：Router（路由）、Plan-and-Execute（计划-执行）、ReAct（推理-行动）、Supervisor（编排者-工人）。前三种我都落地了。

**【60 秒口播】**
- **Router**：一次廉价 LLM 分类把问题分到四条链路（analysis / content / service / document），用状态图的条件边实现。
- **Plan-and-Execute**：分析类问题先拆成 2~5 个子任务再并行执行，避免模型一口气算多步出错。
- **ReAct**：每个子任务内部自主循环调工具。
- **Supervisor（编排者-工人）**：整张图就是一个编排者带四种角色干活，角色之间不直接对话，只通过共享 state 交换结构化产物。

**Agent 和 Workflow 的区别**：Workflow 的路径是人写死的，Agent 的路径是模型运行时决定的。我倾向把两者组合 —— **人负责不确定性的边界（几条边、几步上限、什么情况降级），模型负责边界内的决策**。

**【可能追问】Reflection 范式呢？**
答：我没做，见第 15 题 —— 我的替代方案是把反思做成编排层的 replan 回路，而不是让模型自评。

**【状态】** 🟡（第四个范式要主动讲清「做了什么、没做什么」）

## 第 5 题｜Agent 推理模式有哪些？ReAct 是啥？具体怎么实现的？

**【开口第一句】**
ReAct = Reasoning + Acting 交替：模型先想「我要调什么工具」，程序执行，再把结果回灌给模型，它看着结果决定下一步，直到不再需要工具为止。

**【90 秒口播】**（这段最该背熟）
我的实现就是 simple_agent.py 里一个 for 循环，五个动作：

1. **决策**：llm.chat(messages, tools=工具 schema) —— 传的是「说明书」不是函数，模型只能点名；
2. **终止判断**：响应里没有 tool_calls 就返回 content —— 模型不再要工具，说明它认为信息够了；
3. **记账**：把模型的 tool_calls 作为 assistant 消息存进 messages；
4. **执行**：registry.execute(工具名, 参数) —— 这里集中处理了全部不可信输入（名称/必填/类型/异常）；
5. **回灌**：结果作为 role=tool 的消息塞回 messages，**必须带 tool_call_id**，因为 OpenAI 协议要求「请求调用」和「返回结果」成对出现，缺一半下次请求直接 400。

循环用尽（max_rounds=10）还没结论，就再调一次模型强制作答，那次**不传 tools**，否则它可能又要调工具。

还有一个我踩过的坑：**工具失败时不能只回灌结果**，必须把错误也喂回去。早期 data 是 None，模型看到一个 None 就懵了；现在 registry 把它变成「参数 start_date 格式不对」这种可读反馈，下一轮它自己就改对了。

**【项目证据】**
- simple_agent.py：结果回灌函数（第 7-15 行）、主循环（第 30-53 行）、流式版（第 55-94 行）
- registry 四类兜底：core/tool/registry.py

**【可能追问】一轮里要调多个工具怎么办？**
答：我的代码是 for 循环**顺序**执行。模型一次返回三个工具调用时它是串行的 —— 这里可以改成 asyncio.gather 并发，是明确的优化点。

**【状态】** ✅（这题是你最强的一题，务必讲满 90 秒）

## 第 6 题｜ReAct、Plan-and-Execute、Reflection 的核心区别与选型？

**【开口第一句】**
三者解决不同问题：ReAct 解决「单任务不知道要走几步」，Plan-and-Execute 解决「多步骤想并行、想可校验」，Reflection 解决「一次做不对要自我修正」。

**【60 秒口播】**
- **ReAct**：边想边做，灵活但容易绕圈，适合探索型单任务。
- **Plan-and-Execute**：先出计划再执行，可并行、可校验、可观测，适合「多维度分析」；缺点是计划错了整轮就偏了。
- **Reflection**：对产物自我批评再改一轮，质量提升明显但 token 翻倍。

**我的选型是外层 Plan-and-Execute + 内层 ReAct**：分析类问题先拆成互相独立的子任务（可并行），每个子任务内部用 ReAct 自主查数。原因是我的场景对「可解释、可审计」要求高 —— 运营要看清楚每一步在干嘛。

**Reflection 我确实没做**。我想清楚过为什么：让模型自评容易自我肯定，收益不稳定；我倾向做成**编排层的 replan 回路** —— 综合器判断「数据不足以回答原始目标」时回 planner 补一轮，最多一次。这样「反思」由**证据（数据够不够）**触发，而不是模型自己觉得好不好。

**【项目证据】**
- 外层：supervisor.py（planner → executor 并行 → synthesize）
- 内层：executor.py → ReActAgent
- 未实现：Reflection（替代方案 = replan 回路）

**【状态】** ❌ 第三范式按上面「诚实 + 方案」讲

## 第 7 题｜复杂任务怎么做拆分？为什么要拆？效果如何提升？

**【开口第一句】**
拆分的目的有三个：**并行、可观测、可复核**。我的做法是用 planner 拆成 2~5 个互相独立的子任务，每条只允许配一个工具。

**【60 秒口播】**
- **为什么拆**：让模型一口气算多步，错误率随步数累积；拆成独立子任务后能 asyncio.gather 并行，还能逐个看结果、逐个重试。
- **怎么拆（重点）**：planner 的硬规则是 —— 2~5 条、**必须互相独立**（不能依赖其他子任务的输出）、按「要回答的问题」拆而不是按「工具」拆（一条子任务内部可以调多个工具交叉验证）。这里我踩过两轮坑：先是**按工具拆**，把「为什么销量跌」这种需要链式查证的问题拆碎；改成**单工具硬隔离**后又发现 —— planner 拆得不够细时，子任务被锁成只有一个工具、**静默给出残缺结论**（2026-09-16 把边界上移到「角色」才解决，见 executor.py 的 subset_scope）。
- **代码侧兜底**：planner 输出还会过一遍结构校验 —— id 去重、缺 task 丢弃、编造的工具名清空、超过 5 条截断。因为 LLM 输出的 JSON 是脏的，不能直接信。
- **效果**：从「一次调用给一段文字」变成「4 条可并行、可溯源、可降级的调查」，报告能交叉印证（销售、库存、会员互相验证）。

**【项目证据】**
- agents/planner.py（prompt 硬规则 + 结构校验函数）
- agents/supervisor.py 的 executor_node（gather 并行）
- agents/executor.py（按**角色**收窄工具集 + tool_hint 降级为「建议优先使用」的提示）

**【可能追问】子任务之间真的独立吗？失败了怎么办？**
答：我要求独立，但**失败是必然的**，所以做了异常隔离：gather 带 return_exceptions=True，单个子任务失败只把那一格降级成「该子任务失败：原因」，其余结果照样进报告。

**【状态】** ✅

## 第 8 题｜介绍一下 AI Agent 的记忆机制，实际怎么设计记忆模块？

**【开口第一句】**
记忆要按「时间尺度」分层，不能一锅炖。我做三层：会话消息（这次聊了什么）、长期记忆（这个人是谁）、兜底画像。

**【60 秒口播】**
- **第一层·会话消息**：chat_messages 表按 session_id 存，用于多轮上下文；注入时有预算（超 8000 字从最旧的**整条**丢，不截半条，避免消息语义被劈开）。
- **第二层·长期记忆**：long_term_memories 表，分两类 —— **semantic**（语义画像：负责什么类目、关注什么指标）和 **episodic**（情景记忆：这周转化率掉了、要跟进某件事）。
- **第三层·兜底画像**：user_profile 表存一句话画像，向量库出问题时也不至于完全没有个性化。
- **关键设计**：**SQLite 是唯一事实源，qdrant 只当向量召回索引**（每条记忆的 point id 记在行上）。这样每条记忆都能单独查看、单独删除（有 GET / DELETE /api/memory 接口），而不是「删光重建」。

**为什么这么分**：会话历史回答「刚才说了什么」，长期记忆回答「你是做什么的、在意什么」，两者生命周期完全不同 —— 删掉一个会话不该把用户画像也删掉。

**【项目证据】**
- core/memory/store.py、db/models/user_memory.py
- GET / DELETE /api/memory（记忆可解释、可删除）
- 历史预算 MAX_HISTORY_CHARS = 8000

**【可能追问】记忆写错了怎么办？**
答：记忆是**可管理的资源**不是黑盒 —— 有查看/删除接口；写入失败会落 memory_extract_tasks 表、启动时重放，不会静默丢失。

**【状态】** ✅
