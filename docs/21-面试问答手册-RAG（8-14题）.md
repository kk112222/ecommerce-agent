## 第 8 题｜什么是向量数据库？做过对比选型吗？

**【开口第一句】**
向量库负责三件事：**高维向量的近似最近邻搜索（ANN）**、**元数据过滤**、**持久化**。我选 Qdrant，理由是"本地跑得起来 + 过滤好 + 迁移不亏"。

**【60 秒口播】**
对比过的备选：
| 方案 | 强项 | 我的顾虑 |
|---|---|---|
| **Qdrant**（选用） | 本地文件模式免部署；payload 过滤强（我按 user_id 隔离用户记忆）；HNSW；Python 客户端轻 | 本地模式是单进程锁，上生产要 Server 模式 |
| Chroma | 更轻，入门快 | 生产特性弱（过滤/性能/运维都薄） |
| FAISS | 纯 ANN 库、性能强 | **是库不是服务**：持久化、过滤、并发都得自己写 |
| pgvector | 和业务库同库、能事务、少一个组件 | 我需要 SQLite 开发；数据量小时它的优势体现不出来 |
| Milvus / Pinecone | 大规模 / 托管 | 部署重 / 数据出境与成本 |

选型判据我总结成四条：**部署成本、过滤能力、能否本地跑、迁移代价**。我的知识量很小（32 块），所以选型的核心不是性能，而是"开发期零运维 + 过滤能隔离多用户"。

**【可能追问】那为什么不直接上 pgvector？**
答：这是一个真实取舍 —— 如果我的业务数据本来就在 Postgres，pgvector 更省运维（少一个组件、还能和订单表 join）；我现在是 SQLite 开发 + Qdrant 本地，两端都不用装服务。生产化时我会优先考虑 pgvector 或 Qdrant Server，取决于数据量级和是否需要和关系数据做联合查询。

**【状态】** ✅

## 第 9 题｜讲讲你用的向量库：量级、性能、瓶颈？

**【开口第一句】**
Qdrant 本地模式，kb_docs 集合 **32 个点（1024 维）**，另有 user_memories 存用户长期记忆。量级小到 ANN 根本不是瓶颈 —— **我的瓶颈全在外部 API 往返和本地锁**。

**【60 秒口播】**
真实瓶颈三处（都是踩出来的）：
1. **外部 API 往返**：一次检索至少两次远端调用 —— embed query（DashScope）+ rerank（gte-rerank-v2）；而且用户记忆召回还要再 embed 一次。这是延迟的主要来源，不是向量搜索本身。
2. **本地模式单进程文件锁**：Qdrant 本地模式同时只允许一个进程访问，我踩过——评测脚本和后端抢锁直接报 `Storage folder ... is already accessed by another instance`。所以脚本注释里写着"跑评测前先停后端"。
3. **BM25 语料是进程内缓存**：知识库改了如果不重建索引，检索到的还是旧语料（我加过指纹失效来治它）。

生产化改造顺序：① Qdrant Server 模式（或多实例共享 pgvector）② embedding 批量化 + 语义缓存（相同/相近 query 直接复用结果）③ rerank 只在候选多时开启，或换更小的模型 ④ 索引按 collection 分片、按 user 分区。

**【项目证据】**
- backend/infrastructure/vector_store/qdrant_client.py（两条 collection：kb_docs / user_memories；search_similar 支持 user_id 过滤）
- rag_search.py 的指纹重建 + build_kb.py 末尾显式 `c.close()`（本地模式靠 close 落盘）

**【可能追问】那你的性能优化做了什么？**
答：应用层的比检索层的更有效 —— ① LLM 预算（12 万 token / 240 秒）封顶单轮成本 ② SSE 事件带每步耗时、`usage` 事件报 calls/tokens/elapsed，能定位到"慢在哪一段" ③ 记忆召回只取 top3 ④ 知识库指纹避免每次重查重建索引。

**【状态】** ✅（数字 + 三个真实瓶颈 + 改造顺序）

## 第 10 题｜用户输入进 RAG 后，系统的工作流程？

**【开口第一句】**
一次请求走：**意图分类 → 客服链路 → ReAct 循环里模型调检索工具 → 片段回灌 → 基于证据作答 → SSE 流式回前端**。

**【60 秒口播】**
展开：
1. `intent_classifier` 把问题判成 service（客服问答）；
2. supervisor 的条件边走到 service 节点，客服 Agent 的 prompt 是："先检索知识库拿到政策原文，再据此回答；知识库没有就如实说没查到，不要编造"；
3. ReAct 循环里模型产出 tool_call：`search_knowledge_base(query="退货 运费")`；
4. 工具内部：语料指纹校验（变了就重建 BM25）→ BM25 + 向量各 top10 → RRF → rerank → top5 → 每段裁 300 字 + 带 `[source]`；
5. 片段作为 tool 消息回灌 → 模型据此作答 → 逐 token 流式推前端；
6. 前端活动流显示这一步"调用了 search_knowledge_base"及耗时。

两个工程细节：**检索为空时返回"未找到相关文档"**（而不是让模型自由发挥）；**片段带来源**（便于答案标注出处，也是反幻觉的一部分）。

**【项目证据】**
- backend/agents/customer_service/service_agent.py（人格 + 流程约束）
- backend/tools/service_tools/rag_search.py（返回 `[source] text[:300]`）
- supervisor 的 service 链路 + 前端 TracePanel 的活动流

**【可能追问】如果模型没调检索工具就直接答了呢？**
答：这是任务幻觉的一种，我有三道防线：① prompt 写死流程 ② 评测里的 bypass 扰动测试（资料被清空时还答出旧值，就说明它在背预训练）③ 回答层检查"数字有没有出处"。

**【状态】** ✅

## 第 11 题｜向量检索 vs 关键词检索？

**【开口第一句】**
向量检索比的是**意思**（同义、改写、跨表述），关键词检索比的是**字面**（专有名词、型号、精确条款词）。两者失败模式不相关，所以互补 —— 这就是我做混合检索的原因。

**【60 秒口播】**
各自的典型表现：
- 用户问"**退钱**要多久"，知识库里写的是"退货退款"—— BM25 按字切匹配不到（"退钱"这个词没出现），向量能靠语义命中；
- 用户问"**运费险 8 元**"，BM25 精确命中；向量可能把"运费 8 元"和"顺丰 18 元""偏远加收 15 元"混在一起，因为它只比语义。

融合方式我选 **RRF**：公式 `Σ 1/(k + rank)`（我取 k=60），**只看排名位置、不看原始分数**。原因是 BM25 的分数和 cosine 相似度量纲完全不同，直接加权需要调参且不稳；RRF 免调参、对任一路的异常分数不敏感。融合后再用交叉编码器精排（它看 query 和 doc 的交互，比任何一路单独打分都准）。

**【项目证据】**
- retriever.py：`bm25_search` / `vector_search` / `_rrf_fuse(k=60)` / `search`（各取 top_k*2 融合后 rerank 取 top_k）
- BM25 分词：`list(text)` 按字切（中文短查询够用，我特意没引 jieba）

**【可能追问】中文 BM25 按字切合理吗？**
答：**能凑合，不是最优**。按字切的坏处是"退货运费"会被切成 5 个字，词序信息丢失、还会带来高频字的噪声；更好的做法是 jieba 分词 + 停用词表，或者直接用中文优化的稀疏检索（如 BM25 + 同义词扩展）。我没引依赖是刻意的（项目原则：不装未经确认的包），这一条我明确知道是取舍点。

**【状态】** ✅

## 第 12 题｜如何润色 Query（Query Rewrite）？目的？

**【开口第一句】**
Query Rewrite 是把用户**口语化、省略、带指代**的提问改写成"适合检索"的查询，目的是缩小 **query 与文档之间的表述 gap**。**说实话，这个我基本没做 —— 只做了很轻的一层。**

**【60 秒口播】**
常见做法五类：
1. **补全指代与省略**：多轮里的"那它呢" → "退货政策里的运费谁出"；
2. **术语归一**：口语 → 业务术语（"退钱/退款/退货"统一成一个词）；
3. **拆成多个子查询**（multi-query）：一个复杂问题拆成几条并行检索再合并；
4. **HyDE**：先让模型生成一个"假想答案"，用假想答案去检索（答案和文档的表述更接近）；
5. **历史扩展**：把上文关键信息拼进检索 query。

**我的现状**：多轮历史确实会注入 prompt（模型回答时用得到），但**没有改写检索 query**，也没有把 history 拼进 `search_knowledge_base` 的 query 参数。所以多轮追问里的指代（"那运费呢"）命中率会明显低于单轮 —— 这是我知道的缺口，而且我知道该怎么做：在 service 链路加一个轻量改写步骤（一次小模型调用或规则拼接），或者直接把 history 摘要拼进检索 query。

**【项目证据】**
- 现状：`service_agent.py` 把 history 注入 prompt，但 `rag_search.execute(query)` 收到的只是模型自己写的 query
- 判据（怎么决定做不做）：先看金标集里多轮指代类问题的 Recall@5；我现在的 51 条基本是单轮，所以**第一步是补多轮用例**，而不是直接写改写逻辑

**【可能追问】改写会不会让检索跑偏？**
答：会 —— 改写等于让模型"替用户重新提问"，改错了就召回到无关内容，而且它引入一次额外 LLM 调用（延迟 + 成本）。所以我的做法会是"**能不改就不改**"：先用规则/历史拼接这种确定性手段，效果不够再上模型改写，并且用金标集前后对比验证收益。

**【状态】** ❌（缺口，按"诚实 + 方案 + 判据"讲；面试官会记住这种回答）

## 第 13 题｜什么是多路召回？具体怎么做？

**【开口第一句】**
同一个 query 用**多种检索方式各召回一批**候选，再融合成一份，取长补短。我就是两路：**BM25 关键词 + 向量语义**，融合用 RRF，之后走精排。

**【60 秒口播】**
为什么多路有效：关键在于两路的**失败模式不相关** —— 关键词死在同义改写上，向量死在专有名词和精确数字上。取并集后，只要任一路能找到，候选里就有它；RRF 用排名融合，避免"两种分数不可比"的问题。

更完整的"多路"还包括：
- **不同切块粒度**：小块（精准）+ 大块/父块（完整上下文）；
- **不同表征**：稠密向量 + 稀疏向量（SPLADE/BM25）+ 甚至关键词精确匹配；
- **不同索引/来源**：知识库 + 用户上传文档 + 数据工具结果；
- **结构化过滤当一路**：按类目/时间/权限先缩范围。

我的实现细节：两路各取 `top_k * 2`（即 10）→ RRF(k=60) 按 text 前 100 字去重 → 融合后整体送去 rerank（top_n=10）→ 最终取 top_k=5。

**【项目证据】**
- retriever.py 的 `search()` 与 `_rrf_fuse()`
- 去重键的取舍：用"text 前 100 字"当 key（而不是 uuid），保证两路命中同一块能合并、避免同一片段出现两次

**【可能追问】多路召回的成本？**
答：候选变多 ⇒ 精排输入变多（这是主要成本，因为 rerank 是逐条打分）；每路如果是远端调用，网络往返也线性增长。所以我把融合后的候选控制在 10 条再精排，而不是"每路都取 50"。

**【状态】** ✅

## 第 14 题｜RAG 检索优化策略有哪些？

**【开口第一句】**
按阶段分三段：**入库前**（切块 / 语料清洗 / 元数据）、**检索时**（多路召回 / 融合 / 精排 / 过滤）、**检索后**（上下文组织）。

**【90 秒口播】**
**入库前（我做了）**：结构化切块（答案单元粒度、32 块）+ 40 字 overlap + 多格式解析（md/pdf/docx/html/csv，csv 用 `|` 拼成表、Excel 的 BOM 头也处理了）。

**检索时（我做了）**：BM25 + 向量双路 → RRF(k=60) → gte-rerank-v2 精排 → top5；用户记忆那一路还加了 **payload 过滤**（按 user_id 隔离）。

**检索后（我做了）**：片段裁到 300 字、带 `[source]` 来源标注进上下文（省 token + 可溯源）。

**我没做、但能说清收益与代价的（这是加分项）**：
| 优化 | 收益 | 代价 |
|---|---|---|
| Query 改写 / HyDE | 召回率（尤其多轮指代） | 一次额外 LLM 调用、可能跑偏 |
| 父子块（小块召回、大块喂上下文） | 上下文完整度 | 索引与存储翻倍、实现复杂度 |
| 元数据过滤（类目/时间/版本） | 精准度、抑制过期条款 | 要先把 KB 元数据补齐 |
| 语义缓存 | 相同/相近 query 秒回、省成本 | 缓存失效策略、相似度阈值要调 |
| 向量维度/模型升级对比 | 整体召回质量 | 要重跑金标集 + 重建索引 |

**【可能追问】如果只能加一项，你加哪个？**
答：**先用评测决定**。如果失败案例多是"检索到了但片段不完整" → 加父子块；如果是"根本没召回" → 先做 query 改写；如果是"召回对了但答案编了" → 那不是检索问题，该改 prompt 与生成约束（第 17 题）。我的 51 条金标集 + 四策略对比就是为这种决策服务的。

**【状态】** ✅（做了的三段 + 没做的五项带取舍，最后落到"用评测决定优先级"）
