## 一、先看痛点：数据放哪？

工具要查销售、库存、会员——这些是**结构化数据**，得有地方存。最省事的做法是放内存字典：

```python
sessions = {}   # 重启就没了
```

项目**真的这么干过**（会话历史早期就在内存字典里），代价很直接：**服务一重启，所有会话全丢**。后来换成了 `chat_messages` 表。

选型：

| 阶段 | 选择 | 为什么 |
|---|---|---|
| 开发 | **SQLite** | 一个文件就是数据库，零配置、零部署 |
| 上线 | PostgreSQL | 并发、类型、运维都更强；连接串换一行 |

> 关键设计：连接串**从配置读**，不硬编码。`config.py` 里默认指向项目根的 `data_v3.db` **绝对路径**——"不管从哪个目录启动都指向同一个库"（相对路径会让你在不同目录启动时连到不同的库，这是个隐蔽的坑）。

## 二、从一张表学会 ORM 2.0 写法

先看最简单的一张，`backend/db/models/product.py`：

```python
class Product(Base):
    __tablename__ = "products"
    id:         Mapped[int]      = mapped_column(primary_key=True)
    name:       Mapped[str]      = mapped_column(String(200))
    category:   Mapped[str]      = mapped_column(String(100))
    price:      Mapped[int]      = mapped_column(default=0)   # 售价（单位：分）
    cost:       Mapped[int]      = mapped_column(default=0)   # 成本（单位：分）
    stock:      Mapped[int]      = mapped_column(default=0)
    created_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now())
```

这是 SQLAlchemy 2.0 的新风格，两个概念：

- **`Mapped[类型]`**：这是 Python 的**类型标注**，同时也是给 ORM 看的类型声明；
- **`mapped_column(...)`**：真正定义列（主键、长度、默认值）。

好处是**类型检查和 ORM 映射是同一份声明**——IDE 能补全，ORM 也能建表。`base.py` 只是一个 `DeclarativeBase` 子类，所有表继承它。

## 三、金额存分不存元（本章最重要的一节）

注意 `price` 的类型是 **`int`**，而且注释写着"单位：分"。

**为什么不用 `float` 存元？** 因为浮点数存不准：

```python
>>> 0.1 + 0.2
0.30000000000000004
```

金额一旦累加（100 笔订单求和），误差会被放大，对账时就会"差几分钱"。而 **SQLite 根本没有 DECIMAL/NUMERIC 类型**（它只有 REAL），想用精确小数都做不到。

所以项目的规矩是：**数据库里一律存整数分，只在展示/返回时转成元。**

这条规矩贯穿全项目：

```python
# 工具返回时转元（backend/tools/data_tools/sales_query.py）
"总销售额(元)": round(total_amount / 100, 2)

# dashboard 统计同样 /100
```

> 面试话术：**"金额用最小货币单位存整数"**——避开浮点误差，也避开了"不同数据库 DECIMAL 行为不一致"的坑。代价是每处展示都要 `/100`，属于用一点麻烦换正确性。

## 四、外键把业务表串起来

`orders` 是业务的核心表：

```python
class Order(Base):
    __tablename__ = 'orders'
    id:         Mapped[int]      = mapped_column(primary_key=True)
    product_id: Mapped[int]      = mapped_column(ForeignKey('products.id'))
    quantity:   Mapped[int]      = mapped_column(default=0)      # 购买数量
    amount:     Mapped[int]      = mapped_column(default=0)      # 订单金额（分）
    order_date: Mapped[datetime] = mapped_column(DateTime, server_default=func.now())
    user_id:    Mapped[int]      = mapped_column(ForeignKey('users.id'))
    status:     Mapped[str]      = mapped_column(String(20), default="pending")
```

两个外键把三张业务表连起来：

```
users ──< orders >── products
        (user_id)  (product_id)
```

有了这个结构，5 个数据工具才能回答那些问题：

| 工具 | 查的表 | 回答的问题 |
|---|---|---|
| `query_sales` | orders | 这段时间卖了多少 |
| `category_query` | orders + products | 哪个类目涨了、哪个跌了 |
| `check_stock` | products | 哪些货快没了 |
| `user_profile` | orders + users | 各等级会员消费怎么样 |
| `product_query` | products + orders | 某个商品卖得怎么样 |

> `server_default=func.now()` 表示**由数据库**填默认时间（不是 Python 端），这样即使绕过 ORM 直接插入也有值。

## 五、9 张表全景

| 分组 | 表 | 解决什么问题 |
|---|---|---|
| **业务数据** | `products` | 商品：售价、成本、库存 |
| | `orders` | 订单：金额、数量、状态、时间 |
| | `users` | 用户：账号、密码哈希、会员等级 |
| **会话与交互** | `chat_sessions` | 会话本身：标题、最近活跃、**软删除** |
| | `chat_messages` | 每条 user/assistant 消息（**替代了内存字典**） |
| | `uploaded_doc` | 用户上传文件的解析文本（注入 Agent 做对比分析） |
| **记忆** | `user_profile` | 用户画像兜底（一句话长期偏好） |
| | `memory_extract_tasks` | 记忆提炼失败的**重试表** |
| **缓存** | `insight_cache` | AI 经营洞察的当天缓存 |

几个值得单独说的设计：

**`chat_sessions` 用软删除**：

```python
is_deleted: Mapped[bool] = mapped_column(Boolean, default=False)   # 记录留着，列表不再显示
```

删会话只改标记、不删行——**记录留着**（审计/排查用得上），但列表不再显示。

**`chat_messages` 按 `session_id + user_id` 双归属**：

```python
session_id: Mapped[str] = mapped_column(String(50), index=True)
user_id:    Mapped[int] = mapped_column(ForeignKey('users.id'))
```

只按 `session_id` 查也能工作，但**加上 `user_id` 是隔离**——保证 A 用户拿不到 B 用户的会话（认证那章会用到）。

**`memory_extract_tasks` 是一张"重试表"**：记忆提炼是"回复之后"的后台任务，LLM 偶发失败或进程重启，这一轮记忆就静默丢了（用户只会觉得"它有时候记得我、有时候不记得"）。所以把失败的提炼**连整轮原料一起落一行**，启动时重放。**重放安全的前提是写路径幂等**——这个第 07 章讲。

## 六、异步引擎与会话

`backend/db/session.py`：

```python
DB_URL = settings.database_url

# 1. 异步引擎（echo 跟着 debug 走：默认安静，排查时才开）
engine = create_async_engine(DB_URL, echo=settings.debug)

# 2. 会话工厂（expire_on_commit=False：commit 后对象属性仍可读）
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)

# 3. 快捷函数：FastAPI 依赖注入用
async def get_db():
    async with AsyncSessionLocal() as session:
        yield session
```

在工具里就这样用（不需要依赖注入）：

```python
async with AsyncSessionLocal() as db:
    result = await db.execute(select(func.sum(Order.amount)).where(...))
    total = result.scalar() or 0
```

两个细节：

- **`echo=settings.debug`**：调试时才打 SQL，否则日志刷满、还可能把业务数据泄进日志；
- **`expire_on_commit=False`**：默认情况下 commit 后对象属性会过期，再访问会触发懒加载查询（异步场景下容易报错）；关掉它，commit 后还能直接读属性。

## 七、表是怎么被"发现"的

SQLAlchemy 建表靠 `Base.metadata`，前提是**每个模型类都被 import 过**。项目用了一个小技巧——「自包含注册」：

```python
# backend/db/models/user_profile.py
from backend.db.models.user import User  # 注册 users 表，让外键能解析（自包含）
```

每个引用别的表的模型文件，**自己把依赖的模型 import 进来**，这样单独 import 任意一个模型，它依赖的表也就注册好了。注释里写得很直白：*让外键能解析*。

然后统一建表：

```python
# scripts/init_db.py
Base.metadata.drop_all  →  create_all      # 初始化（清空重建）
# backend/api/app.py startup
Base.metadata.create_all                    # 启动时幂等补表（不删已有数据）
```

> 用一个笨但有效的办法保证"新加了模型但忘了注册"不会发生：**启动时 create_all 一次**，缺表就补上。

## 本章小结

- **9 张表**分四组：业务数据 / 会话交互 / 记忆 / 缓存
- **金额存分不存元**：浮点存不准 + SQLite 没有 DECIMAL，只在展示时 `/100`
- **连接串走配置 + 绝对路径**：不管从哪启动都连同一个库
- **软删除**（`is_deleted`）与**双归属**（`session_id + user_id`）是两个隔离/审计设计
- **自包含注册**：模型自己 import 依赖的表，保证 `create_all` 时外键能解析
