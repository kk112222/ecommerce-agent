## 第 17 题｜Agent 的上下文工程怎么设计？

**【开口第一句】**
上下文工程就是回答一个问题：**这一次调用，模型到底该看到哪些字**。我的原则是「按角色给、按预算截、能不传就不传」。

**【90 秒口播】**
1. **按角色给（角色专属上下文）**：文档 Agent 才注入上传文档；内容/客服 Agent 注入历史 + 用户画像；planner 和 synthesizer 拿历史 + 画像 + 上传数据。不是所有人都塞同一坨。
2. **固定注入顺序**：人格 prompt → 历史对话 → 用户画像 → 上传文档 → 本次目标。顺序稳定，出了问题好排查，也避免「把工具清单当目标」这类坑（我踩过：planner 的 user 消息里放错了内容，模型就不知道要规划什么）。
3. **按预算截**：历史超 8000 字从最旧的**整条**丢（不截半条）；上传文档注入截 6000 字但标注「原文共 X 字」；报告喂给记忆提炼时截 1600 字。每一处截断都是显式的、可解释的。
4. **能不传就不传（省 token 的硬手段）**：executor 的注册中心收窄成**分析角色**的 5 个数据工具（不是全集 10 个）—— 每轮少传一半 schema；跨角色的工具（写文件、生成文案）根本不进 schema。
5. **记忆只召回 top 3**：不是把所有长期记忆都塞进去，而是按 相似度 × 重要性 × 新鲜度 排序取前 3。
6. **该由程序给的事实不让模型猜**：当前日期直接注入 prompt（LLM 没有时钟感，会瞎猜年份）。

**【项目证据】**
- 角色上下文组装：content_agent.py / service_agent.py / document_agent.py
- 预算常量：MAX_HISTORY_CHARS = 8000、MAX_DOC_CHARS = 6000
- 工具范围：executor.py + registry.subset_scope("analysis")（角色级白名单，见 registry.TOOL_SCOPES）
- 日期注入：executor.py 的 system prompt 第一句

**【可能追问】怎么判断上下文是不是太长了？**
答：我有两条硬指标 —— 每轮的 token 用量（usage 事件会报 calls / tokens / elapsed）和预算上限（12 万 token / 240 秒）。超了就降级出报告，而不是硬跑。

**【可能追问】每个 executor 只暴露一个工具，那万一要调多个工具呢？工具很多呢？**
答：先分清一件事 —— **"一个目标涉及很多工具"不等于"一次要调很多工具"**。判据是这些查询**互相有没有依赖**，不是工具有几个：
- **有依赖的链式查询**（查完这周销售、发现某品类掉了、再去查该品类库存）→ **不拆**。planner 的硬规则本来就要求子任务"互相独立、不依赖其他子任务的输出"；这种链条该在**一条子任务内部的 ReAct 多轮**里跑完（前提是这条子任务 hint 留空、拿到全集 —— 见下面那条边界）—— 一条子任务调 10 个工具 = 同一格的 10 轮（子 agent `max_rounds=10`），不是 10 个格子。ReAct 存在的意义就是这个，别把它让给并行拆解。
- **先把话说准，免得被追问**：收窄的是子 agent **可见的工具集**（按角色收窄），**不是它的调用次数**。同一个工具调多次（不同商品、不同时间范围、分页）完全不受影响，就在那 10 轮里换参数调。
- **互相独立的多个维度** → 拆条，但拆的是**维度**不是**工具**（查销售是维度、查库存是维度）。**实测**：金标集第 1 条"这周营业额为什么低"期望工具就是 `query_sales` + `check_stock` 两个，planner 自己拆成两条子任务，工具召回 **2/2**、全局 hint 合规 **13/13** —— 不是"设计上应该拆"，是真机跑出来确实拆对了。
- **真有 10 多个独立维度** → 两道闸门会挡，**这是真边界，我会主动说**：planner 硬规则 2~5 条 + `MAX_TASKS = 5` 截断，**超过 5 个维度现在会被静默丢掉**。不放宽是因为子任务数是**成本闸门**：实测平均 5.3 次 LLM 调用 / 51s 一轮，拆到 10+ 条是线性放大，而预算上限（12 万 token / 240s）就是为封顶设的 —— 为边缘场景打穿主路径的延迟预算不划算。正解是**分层收敛**：用户要的是最关键的 3 个维度（所以有"必要维度覆盖率"这个指标兜着，真机 18/18）；5 条真不够就走 synthesize 判"证据不足"→ 回 planner **分批补查**，也就是我讲的 replan 回路（**待做项**，不是已实现）。
- **边界我说清（2026-09-16 已改）**：原来的设计确实是"填单个工具（硬隔离）/ 留空（放开全集）"两档、没有中间态，链式查询只能靠留空退回软约束。现在**边界从"单条子任务"上移到"角色"**：子任务固定拿 `analysis` 角色的 5 个数据工具，`tool_hint` 降级成 prompt 里的一句「建议优先使用」。所以"隔离"和"多工具链路"现在能同时拿到 —— 隔离变成角色级（跨角色才拦），角色内可自由交叉验证。
一句话收口：**"需要几个工具"是任务的属性，"拆几条"是成本决策**；拆条的判据是查询**互不独立**，不是工具有几个。

**【状态】** ✅

## 第 18 题｜多轮对话状态怎么管理？怎么防止跑偏？怎么支持中断恢复？

**【开口第一句】**
状态分两处存：会话元信息（chat_sessions）和消息（chat_messages）；防跑偏靠「意图固定路径 + 代码硬约束」；**中断恢复我没做，是明确缺口**。

**【90 秒口播】**
**状态管理**：
- 每次请求把用户消息落库、跑完把助手回复落库，按 session_id 取历史；
- 会话元信息和消息**分两张表**：侧边栏列表只查小表（不用扫消息表），删除会话是物理删消息 + 清上传文档；
- 前端切换会话靠重挂载（chatKey 自增），保证状态不串。

**防跑偏（这块我有三层）**：
1. **路径固定**：意图定了之后走哪条链路是代码写死的，模型不能中途改路线；
2. **职责按角色硬隔离**：子任务拿到的是「分析角色」的 5 个数据工具，写入类工具根本不在 schema 里（跨角色才拦，不是靠 prompt 叮嘱）；
3. **契约校验**：工具名/必填/类型统一校验，编造的工具名在 planner 输出阶段就被清空。

**中断恢复**：
这个我没做。现状是：会话历史能恢复（在 SQLite 里），但**执行到一半的图不能断点续跑** —— 进程挂了这一轮就没了。我的自研引擎在数据结构上预留了 interrupt 字段，但没实现。要做需要三步：把每一步的状态快照落库、恢复时按快照重建、并且保证工具幂等（否则重放会重复下单/重复写文件）。

**【项目证据】**
- 分表：db/models/chat_session.py、chat_message.py
- 三层防跑偏：supervisor.py / executor.py / registry.py
- 未实现：core/agent/base.py 里预留但没用的中断字段

**【状态】** ❌ 第三问按「诚实 + 实现路径」讲（主动说出预留字段没实现，比被问出来强）

## 第 19 题｜如何评估一个 Agent 的效果？评测集和指标怎么设计？

**【开口第一句】**
Agent 的失败发生在**不同层**，所以要分层评：检索层、回答层、编排层。我三层都有尺子。

**【120 秒口播】**（这是你最能拉开差距的一题，讲满）
**第一层·检索质量（离线可复现）**：51 条人工标注金标集（每条是「问题 → 该命中的原文片段」），跑四种策略对比：BM25、纯向量、RRF 混合、混合 + 精排，指标是 Recall@5 / Hit@1 / MRR。价值在于**改切块或改检索前后能对比同一份集合**，而不是凭感觉。真值我特意选「预训练背不到」的虚构条款（运费、保修天数），这样答错就一定是没检索到。

**第二层·回答质量**：① 幻觉数字筛查 —— 答案里的每个数字必须能在召回片段里逐字找到（确定性判据，不看 LLM 脸色）；② 扰动测试 —— 把知识库里的包邮门槛改掉再问同一题，答案跟着变才证明**真走了检索**而不是背预训练。

**第三层·编排质量（这是我加的第三层，也是最容易被忽略的）**：15 条目标 + 六项指标 —— 意图路由准确率、工具调用召回率与精确率、必要维度覆盖率、hint 合规率、报告数字有据率、成本与耗时。为什么必须单独量？因为**路由错、漏维度、报告编数这些失败，在检索指标里完全看不见**。
真机实测（qwen3.7-flash，15 条全过）：意图路由 **15/15**、必要维度覆盖 **18/18**、hint 合规 **13/13**、工具召回 **100%**（精确率 76%）、报告数字有据 **166/177（94%）**；平均每轮 5.3 次 LLM 调用 / 51s。
**数字要主动解释**：工具精确率 76% 是因为模型**主动多查**（该查的都查了，偶尔多查一两个工具换可靠性）；数字有据 94% 的判据是"报告里的数字能否在子任务结果里逐字找到"，那 6% 是**待人工复核**而不是"已确认编造"——脚本提示里就写着报告自己算出来的比值会被误报，这个指标是筛查不是判罪。并且明确说明这是**单次运行**的数字，LLM 非确定性下同一题两次跑会差几个数（实测过），要更稳得多跑几次取均值。

**方法上还有两条**：① 可判定优先 —— 能写成断言的就不交给 LLM 判（数字越界、工具集合、维度关键词）；② 离线优先 —— 15 个测试文件、108 项用例全用假 LLM，不联网不花额度，改代码随时回归。

**【项目证据】**
- scripts/rag_eval.py（51 条金标，四策略）
- scripts/rag_answer_eval.py（幻觉判据 + 扰动测试）
- scripts/agent_eval.py（15 条编排金标 + 六指标，支持 dry-run 演练；2026-09-15 真机 15/15 全过，指标见上）
- tests/（假 LLM 离线回归）

**【可能追问】这些指标谁定的？为什么是这几个？**
答：按**失败模式**倒推的 —— 每条指标对应一种我真实遇到过的失败：路由错（意图准确率）、该查没查（工具召回）、只查一面就下结论（维度覆盖）、planner 不守契约（hint 合规）、报告编数（数字有据）。指标不是越多越好，是要能指回一次真实的翻车。

**【状态】** ✅✅（最强的一题）

## 第 20 题｜Agent 为什么会出现路径震荡、重复调用和死循环？怎么检测和治理？

**【开口第一句】**
归根到底是三个原因：**模型不确定性、工具描述模糊、以及终止条件不明确**。治理手段是「给上限 + 给确定性反馈 + 按角色收窄工具范围」；检测侧我目前偏弱，只有日志。

**【90 秒口播】**（含一个真实故事，务必讲）
**成因**：① 模型每轮都在重新决策，同一件事可能来回试；② 工具描述含糊 → 它挑不准工具；③ 参数校验松 → 报错信息不可读 → 它改不对就又试一次；④ 没有步数/成本上限 → 停不下来。

**我的治理清单**：ReAct 轮次上限（max_rounds=10）、**LLM 层全局预算**（12 万 token / 240 秒，超限降级而不是抛错）、按角色收窄工具范围（减少乱调空间）、工具错误结构化回灌（让它一次改对）、以及并行子任务的异常隔离（一个炸掉不拖垮其余）。

**一个真实的死循环故事（很值得讲）**：我的 planner 有个「id 去重」逻辑，写成了 while 循环里用长度当候选名 —— 而长度在循环里**是不变量**，于是候选名永远算成同一个，一旦被占用就原地自旋。可怕的地方是它是**同步 CPU 自旋、还在请求路径上**，堵的不是一个请求，是整个事件循环，所有用户都卡死，只能重启进程。我用 faulthandler 打出栈定位到那一行，改成滚动候选，并补了一条「修复前会失败」的回归用例。这件事教会我：**Agent 系统里最危险的不是模型犯错，而是程序自己的不变量写错** —— 模型的错误有预算兜着，程序死循环没有。

**检测侧的缺口（要主动说）**：我现在只有日志（tool_hint 违规会告警），没有把「重复调用率、hint 违规率、单轮调用次数分布」做成指标上报。这是下一步要补的。

**【项目证据】**
- 治理：budget.py、simple_agent.py 的 max_rounds、executor.py 的角色级工具范围（subset_scope）、supervisor.py 的异常隔离
- 真实故事：planner.py 的 id 重编号 + tests 里的回归用例

**【状态】** ✅（故事 + 治理都有，检测缺口坦白说）

## 第 21 题｜线上 Agent 延迟升高时，如何用 Trace 定位和优化？

**【开口第一句】**
Agent 的延迟必须**分段看**，因为它不是一次调用，而是「路由 + N 个子任务 + 综合」的串并联。我用 SSE 事件流 + usage 汇总 + 请求耗时头三样定位。

**【90 秒口播】**
**观测三件套**：
1. **SSE 事件流**：intent / plan / subtask / token / report / usage / document 七类事件，每个子任务完成时前端会显示它的耗时 —— 相当于一条简易 Trace；
2. **usage 事件**：这一轮总共几次 LLM 调用、多少 token、耗时多少秒（超限会标出来）；
3. **请求耗时头**：中间件给每个响应写 X-Request-Time-ms，能区分「慢在 HTTP 层」还是「慢在 Agent 内部」。

**怎么定位**：先看是哪条链路（客服/内容链路本来就只有 1~3 次调用，慢肯定是模型慢）；分析链路看**最慢的那个子任务**，因为并行执行时总时长由最慢的分支决定；再看是 LLM 慢还是工具慢（工具里可能是 SQL 或 embedding 调用）。

**优化手段（按收益排序）**：① 按角色收窄工具 schema 降低每轮 prompt（executor 只带 5 个数据工具的 schema）；② 减少 ReAct 轮次（把模糊任务拆清楚，模型就少绕）；③ 并行化（子任务已经并行，未来可以把一轮里的多个工具调用也并发）；④ 缓存（知识库检索已按语料指纹缓存，重建才失效）。

**【项目证据】**
- 事件流与耗时：backend 的 on_event + frontend 的 TracePanel（活动流）
- 用量：core/llm/budget.py 的 snapshot()
- 请求耗时：api/middleware.py 的 X-Request-Time-ms

**【可能追问】为什么不做 OpenTelemetry 那种标准 Trace？**
答：现在是轻量自研（事件流就好）。要上生产我会接标准链路追踪，把「一次用户请求」当一个 trace、每个子任务当一个 span —— 我的事件结构本来就是按这个设计的，迁移成本不高。

**【状态】** ✅

## 第 22 题｜Multi-Agent 如何处理子 Agent 超时、失联和并发修改冲突？

**【开口第一句】**
三类问题：**失败隔离**（一个子任务炸了不能拖垮整轮）、**预算隔离**（一个子任务不能吃光额度）、**并发写冲突**（同一份状态被同时改）。前两个我做了，第三个在记忆写入上做了。

**【90 秒口播】**
**1. 超时/失联（失败隔离）**：并行子任务用 asyncio.gather，但**必须带 return_exceptions=True** —— 默认行为是一个协程抛异常就立刻抛给调用方，异常穿过 executor → 图直接中断 → 综合步骤永远不执行，**其他三个子任务已经查好的结果全被丢掉，用户看到「分析失败」**。我改成逐格降级：每个子任务自己 try，失败就把那一格写成「该子任务失败：异常类型 + 原因」并记日志，其余结果照常进报告。这里有个细节：`gather` 出异常时**不会取消兄弟协程**，它们会跑完但返回值被丢弃 —— 也就是说 token 已经烧了，所以更要保住结果。

**2. 预算隔离**：预算账本是一轮共享的，但「超限」是在每个子任务内部被捕获的 —— 一个子任务把额度吃光，只影响它自己那一格（降级文案），不会让整轮 500。

**3. 并发写冲突**：最典型的场景是记忆提炼 —— 它是「读旧画像 → 合并 → 写回」的读改写，同一用户并发两轮就会互相覆盖丢记忆。我用 **per-user 的 asyncio.Lock** 把同一用户的提炼串行化；锁本身用 WeakValueDictionary 存，避免用户多了之后锁字典无限增长。另外提炼失败会落一张任务表，进程重启后重放，不静默丢。

**【可能追问】如果子任务真的超时了（不是抛异常，而是卡住）怎么办？**
答：我现在靠**预算的时间上限**兜（240 秒），到点之后新的 LLM 调用被拒绝、节点降级出报告；严格意义的「单个子任务超时取消」我还没做（要 asyncio.wait_for + 保证工具幂等）。这是我知道的下一步。

**【项目证据】**
- supervisor.py 的 executor_node（逐格降级 + return_exceptions）
- chat.py 的 per-user 锁 + WeakValueDictionary
- db/models/memory_task.py（失败重放）

**【状态】** ✅（这题你答得比大多数候选人都扎实，含一个反直觉细节：gather 不取消兄弟协程）

## 第 23 题｜什么是「任务幻觉」？怎么避免没执行工具却声称已经完成？

**【开口第一句】**
任务幻觉就是「模型说做了，其实没做」—— 它输出一段像模像样的结论，但根本没调工具，或者工具返回失败它当作成功。我的防护有三层，而且有一层是**评测**而不是代码。

**【90 秒口播】**
**第一层·逼它调工具**：工具的 JSON Schema 里描述尽量具体（什么场景用什么工具）；子任务里给一个「建议优先使用」的起点提示（executor 的角色范围里就那几个数据工具，写入类工具不存在）。
**第二层·失败必须可见**：工具失败时把 error 结构化回灌给模型（不是给个 null），它下一轮就不会把失败当成功；子任务返回空结果时，写入的是「该子任务未获取到数据」的显式文案，绝不流进报告当结论。
**第三层·评测兜底（这层最关键）**：我的编排层评测里有一项「**报告数字有据率**」—— 把报告里出现的每个数字拿去子任务结果里逐字比对，找不到就是待复核的「编造数字」。这是对任务幻觉最直接的自动化检测，因为它不管模型怎么说，只看**结论里的数字有没有出处**。
**另外还有一个领域级的硬规则**：客服链路的知识库工具直接在 prompt 里写明「知识库里没有答案就如实说没查到，不要编造」—— 因为售后政策编错是要赔钱的。

**【项目证据】**
- 结构化错误回灌：registry.py + simple_agent.py 的结果回灌函数
- 空结果兜底：executor.py
- 数字有据判据：scripts/agent_eval.py 的 grounding 函数

**【可能追问】有没有可能它编了一个不在报告里的谎？**
答：可能。数字有据率只管数字，「过程性撒谎」（比如声称调了工具但没调）需要另一类检测 —— 比如在工具层记录调用日志，和报告的声称做交叉核对。这是我知道的下一步。

**【状态】** ✅

## 第 24 题｜连数据库时怎么防止越权、敏感数据泄漏和查询幻觉？

**【开口第一句】**
分三件事答：**不给它写 SQL**（防查询幻觉）、**连接时就固定身份**（防越权）、**只回结果不回原始行**（防泄漏）。我做到了前两件的一半，第三件做了但还有缺口。

**【90 秒口播】**
**1. 防查询幻觉：不给模型 SQL 能力。** 我的 10 个工具全是**固定语义的聚合查询**（按日期查销售额、按分类查、库存低于阈值…），模型只能选工具 + 给参数，不能拼 SQL。参数还要过类型校验 —— 它传「本周」这种中文相对时间会被拒掉并回灌可读错误，而不是拼进 SQL。

**2. 防越权（现状 + 缺口）**：
- **工具级**：工具按角色白名单调用（子任务拿不到写入/文件类工具）；文档下载接口把 user_id **写死在路径里**（outputs/user_<id>/...），不是事后比对 owner，别人的文件一律 404，而且不区分「不存在」和「没权限」，不给探测机会；
- **缺口（要主动说）**：我的数据工具本身**没有行级权限** —— 查销售额就是查全库，没有按用户/店铺过滤。单店铺场景没问题，多租户就是越权。补法是：注册工具时注入当前 user_id / shop_id，SQL 层统一加过滤条件，和文档下载是同一个思路。

**3. 防泄漏**：工具返回的是**聚合结果**（总销售额、订单数、库存量），不返回用户手机号/地址这类明细；金额统一存分避免精度问题。**另外我发现一个小隐患**：子任务失败时我把异常信息截 200 字写进报告给用户看，里面可能带上游 API 的报错原文 —— 更严格的做法是日志留全量、给用户只看异常类型。这条我记在缺陷清单里了。

**【项目证据】**
- 无裸 SQL：tools/data_tools/ 全部是固定查询
- 参数校验：registry.py（类型校验 + 结构化错误）
- 路径写死归属：documents.py + doc_output.py（含目录穿越双保险）
- 缺口：数据工具无行级过滤

**【可能追问】那你怎么防止它把敏感数据写进长期记忆？**
答：目前记忆只提炼「负责类目、关注指标」这类画像，prompt 里明确「只提炼关于用户的稳定特征」；严格做法是在写入前加一层脱敏/敏感词过滤，这也是待补的点。

**【状态】** 🟡（三件事讲清、缺口主动交底）

## 收尾：这三份手册怎么用

1. **第一遍**：按题号顺序，每题先自己口述 60 秒（录音），再读「口播稿」比对 —— 找出「说不出来」的题；

4. **标 ❌ 的四题**（6、15、18、24 后半）：不要背，也不要装 —— 按手册里的「诚实 + 方案 + 为什么」讲，这类回答在面试里是加分项。
