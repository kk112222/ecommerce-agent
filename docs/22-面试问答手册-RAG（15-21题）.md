## 第 15 题｜了解哪些更复杂的 RAG 范式？

**【开口第一句】**
按"检索发生几次、由谁决定"分四档：**单轮 RAG → 迭代/多跳检索 → 自适应检索（模型决定要不要检索）→ Agentic RAG（把检索当工具、由 Agent 规划多步）**；另一条独立的线是**图结构**（GraphRAG）。

**【60 秒口播】**
- **单轮 RAG**：一次检索一次作答（大多数问答场景够用）；
- **迭代/多跳**（IRCoT、self-ask）：先检索→发现缺信息→再检索，适合"先查 A 再拿 A 的结果查 B"；
- **自适应检索**（Self-RAG 一类）：让模型判断"这个问题需不需要检索"，省成本；简单寒暄不检索、政策问题才检索；
- **Agentic RAG**：检索被封装成**工具**，由 Agent 的 ReAct 循环决定调几次、用什么 query，还能和别的工具（查数据库、写文档）混用；
- **GraphRAG**：先把文档抽成实体-关系图 + 社区摘要，擅长"跨文档的全局性问题"，代价是抽取成本高、增量维护复杂。

**我的系统本质就是 Agentic RAG**：`search_knowledge_base` 就是 BaseTool 的一个实现，和 `query_sales` 平级，由 ReAct 决定调用 —— 这一点比"我用了某种花活"更值得讲，因为它是架构层面的判断。

**【项目证据】**
- rag_search.py（RAGTool 继承 BaseTool）+ simple_agent.py（ReAct 循环自主决定调几次）
- 我的场景（政策条款问答）单跳足够，所以**主动没上** GraphRAG/多跳 —— 判断依据是问题类型，不是技术新鲜度

**【可能追问】Agentic RAG 相比固定 pipeline 的代价？**
答：① 模型可能不检索（任务幻觉）② 延迟不可预测（多轮 ReAct）③ 成本更高。换来的好处是能跨工具组合（查完数据再检索政策）、能多轮追问。我用预算（12 万 token/240s）+ prompt 流程约束 + bypass 评测来兜这三条代价。

**【状态】** ✅（能报全范式 + 说清自己属于哪种 + 为什么不上花活）

## 第 16 题｜什么时候用图数据库增强向量检索？

**【开口第一句】**
当答案需要**跨文档的实体关系或多跳遍历**，而不是"找到某个片段"时 —— 比如"哪些供应商同时供货给 A、B 两个类目"、"这次政策变更影响了哪些商品线"。

**【60 秒口播】**
两种技术的强项正好互补：**向量擅长模糊语义匹配**（同义改写、自然语言入口），**图擅长显式关系与多跳**（A→B→C 的路径、聚合统计、"这两个实体怎么关联"）。所以常见组合是：向量做语义入口找种子节点，图做关系扩展与约束（GraphRAG 的 local / global 两种检索就是这条路）。

**我的现状：没有图，而且我认为用不上** —— 我的 KB 是条款型短文本（退货政策、物流说明、FAQ），问题类型是"单跳事实查找"（运费谁出、几天能到），既不需要多跳、也没有实体关系可抽。诚实的说法是：不是技术不行，是场景不匹配；如果要扩展成"品类-商品-供应商-退货率"这种经营分析，图才有价值。

**【可能追问】那你怎么判断该不该上图？**
答：先看问题类型 —— ① 单跳事实找片段：向量/混合检索足够；② 多跳关系（谁影响了谁）：图或迭代检索；③ 全局性问题（"这批反馈里反复出现的问题是什么"）：分层摘要或 GraphRAG 的社区摘要。**先分类问题，再选技术**，而不是反着来。

**【状态】** 🟡（知道原理与判据，项目里没用；按"场景不匹配 + 判断依据"讲）

## 第 17 题｜如何规避 RAG 幻觉？

**【开口第一句】**
分三层防：**入库质量**（切块正确、语料无歧义）→ **检索质量**（该召回的召回到、别召回无关的）→ **生成约束 + 检测**（prompt 要求有据 + 确定性判据筛）。

**【90 秒口播】**
我这套具体做法：
1. **prompt 约束**：客服 Agent 明确"先检索知识库拿到原文，再据此回答；知识库里没有答案就如实说没查到，**不要编造**"；
2. **可溯源**：检索片段带 `[source]` 标注进上下文，报告里要求写明数字来自哪个工具/片段；
3. **检索为空时不硬答**：工具返回"未找到相关文档"，而不是把空上下文丢给模型自由发挥；
4. **确定性检测（最关键的一层）**：`numeric_overflows` 把答案里的每个数字拿去召回片段里逐字比对 —— 找不到的进"待人工复核"清单（数值幻觉是最典型的形态，而且法律/售后场景代价最大）；
5. **忠实度 judge**：独立的 judge prompt 判"每个事实性陈述能否在资料里找到出处"，1~5 分；
6. **扰动测试（反 bypass 的杀手锏）**：把知识库里的包邮门槛从 99 改成 199 再问同一题 —— 答案跟着变，才证明它**真在查资料**；再把资料清空问同一题，如果还答出旧值，就说明它在背预训练常识（bypass）。

**【项目证据】**
- scripts/rag_answer_eval.py：数字越界（纯函数）+ judge 忠实度 + 扰动测试
- scripts/rag_quality_eval.py：另一种扰动（V1 换值 / V2 清空）+ 无关块作答时应说"资料里没有"
- tests/test_rag_answer_eval.py：把"数字越界""包邮门槛抽取"两个判据单独钉成离线单测（尺子本身也要校准）

**【可能追问】数字有据会误报吗？**
答：会。模型自己算出来的数（8+18=26）会被判"无据"，因为片段里没有 26 这个字符串。所以我把输出定义成"**待人工复核清单**"而不是直接扣分 —— 这是我在设计里显式写下的取舍：**判据偏松（子串匹配）宁可漏报也不误杀**，代价是需要人工看一眼。

**【状态】** ✅✅（这题最能体现你踩过真坑：三层 + 扰动测试，讲满 100 秒）

## 第 18 题｜怎么量化 RAG 效果？

**【开口第一句】**
分两层量：**检索层**用确定性指标（Recall@k / Hit@1 / MRR），**回答层**用 judge + 确定性筛查（事实命中 / 忠实度 / 数字越界 / bypass）。

**【120 秒口播】**
**检索层**：我手工建了 **51 条金标集** —— 每条是「问题 → 该命中的原文片段 → 来源文件」。然后跑四种策略对比：纯 BM25、纯向量、RRF 混合、混合+精排，指标是 **Recall@5 / Hit@1 / MRR**，还按来源文件拆开看（哪个文档最差）。
真值的选择有讲究：我专门挑**预训练背不到的虚构条款**（运费 8 元、保修 1 年、SVIP 门槛 20000 元）—— 这样答错只可能是检索没做到，不会和"模型本来就会"混在一起。另外脚本有**完整性自检**：片段必须在语料里存在、最好只命中一个块，否则真值有歧义会污染指标。

**回答层**：① 数字越界（确定性，我前面讲过）② 忠实度 1~5（judge）③ 扰动测试证明真走检索。

**怎么用**：改任何检索逻辑（切块 → 200 字结构化、加 rerank、换融合策略）前后各跑一次**同一份**金标集，看指标是涨是跌 —— 这就是"改好了没"的唯一判据，而不是感觉。

**【项目证据】**
- scripts/rag_eval.py（51 条 + 四策略 + Recall@5/Hit@1/MRR + 按来源拆分）
- scripts/rag_answer_eval.py（回答层 + 扰动）
- scripts/rag_quality_eval.py（切分质量 + 换值/清空扰动）
- tests/test_rag_answer_eval.py（判据离线单测）

**【可能追问】51 条够吗？指标怎么定阈值？**
答：**不够**，它是"够用来做相对比较"的量级（同一份集合上的 A/B），不是统计意义上的充分样本。所以我只把它用于**同集合前后对比**，不对外宣称"我的召回率是 xx%"这种绝对结论。要更可信需要：扩充到几百条 + 分层抽样（按文档/问题类型）+ 多人标注一致性。这是明确的边界。

**【状态】** ✅✅（这是你整份 RAG 材料里最强的一题）

## 第 19 题｜知识库如何实现动态与持续更新？

**【开口第一句】**
分两块：**离线重建**（我现在的做法，够用且可靠）和**在线增量**（生产要做的）。

**【60 秒口播】**
**我做的（离线全量重建）**：改 md → 跑 `build_kb.py` → **先清空旧块再写**（避免重复跑导致新旧叠加）→ 重新 embedding → 写回。配套两个坑我都填了：① Qdrant 本地模式的 `delete_collection` 不可靠（删了旧点还在），所以改成**按点删除**，和 upsert 走同一条验证过能落盘的路；② 进程内 BM25 语料**靠语料指纹自动失效重建**，不用重启后端（指纹 = 全部 (source, text) 排序后取 md5）。
指纹为什么不用"点 id 集合"：现在 id 是 uuid4，每次重建都变、比 id 也能发现；但哪天改成内容决定的确定性 id，同长度重建就会被漏掉 —— 直接对**内容**取指纹两种策略都覆盖。

**我没做、但知道要做的（在线增量）**：① 文档级 upsert/删除（按 doc_id 定位，而不是全量覆盖）② 增量 embedding（只处理变更块）③ 版本与生效时间（元数据带 effective_date，检索时按时间过滤）④ 定时同步/回调触发（文档系统 webhook）⑤ 多实例部署时的缓存一致性（指纹是进程内的，多实例得靠版本号或 TTL 校验）。

**【项目证据】**
- build_kb.py（先删后写 + 按点删除的坑 + batch_size=10 的 API 上限 + 显式 close 落盘）
- rag_search.py 的 `_fingerprint_of` / `get_retriever(force)`

**【可能追问】线上多实例部署，你的指纹机制还成立吗？**
答：**不成立** —— 指纹是进程内缓存，每个实例各存一份。生产要改成：Qdrant Server + 版本号（构建完成时写一个全局版本，各实例按 TTL 校验）或直接把索引重建做成发布流程的一步。我在代码注释里写明了这个边界。

**【状态】** ✅（离线部分有实现和踩坑，在线部分讲得清方案与自己的边界）

## 第 20 题｜落地 RAG 最难的地方？

**【开口第一句】**
**最难的不是搭起来，而是"判定它到底好不好"**；其次是切块粒度与提问粒度之间的错配。

**【90 秒口播】**（讲三个真实踩过的）
1. **切块粒度决定上限，而且它不是代码问题**：我最早按 300 字纯段落切（7 块），后来改成"答案单元"导向的结构化切块（200 字 + 40 overlap → 32 块）。同一份文档、同一套检索，召回质量完全不同 —— 这类改动没有报错、没有测试能发现，只能靠评测。
2. **没有评测就没有"改好了"这个说法**：所以我先建 51 条金标集 + 四策略对比，之后调切块/融合/精排才有依据。**这是我这个项目里最有价值的一件事**，比多加几个功能值钱。
3. **"看起来对"和"真的有据"是两回事**：模型会给出格式漂亮、语气合理的答案，但可能没看资料。所以才有数字越界筛查和扰动测试 —— 扰动测试（改掉 KB 里的数值再问）是我做过**最有效的反 bypass 手段**。
另外还有一堆组件层的现实坑：Qdrant 本地单进程锁、DashScope 批量 embedding 一次最多 10 条、知识库更新后索引不重建就静默用旧语料、PDF 扫描件抽不出文字（要 OCR，我没做）。

**【可能追问】如果重来一次你会先做什么？**
答：**先建评测集，先定"答案单元"再写检索代码**。我实际是先写检索、后补评测，中间多绕了一圈；而且我后来发现"切块粒度"和"评测集"应该一起设计（因为评测集的真值就是按块标注的）。

**【状态】** ✅（有真实经历 + 把"评测优先"这个判断讲出来）

## 第 21 题｜不同来源文档冲突时信谁？

**【开口第一句】**
按 **权威性 → 时效性 → 具体性** 三级排序，并且把冲突**显式暴露**给用户，而不是让模型自己挑一个它觉得合理的说出来。

**【60 秒口播】**
排序判据：① **来源权威**（官方政策 > 内部 FAQ > 第三方/用户上传）；② **时效**（新版 > 旧版，元数据带生效日期）；③ **具体性**（专项条款 > 通用说明）。
工程实现：payload 里加 `doc_type / effective_date / priority` 字段，检索时按优先级加权或硬过滤（比如默认只检索"已生效且权威度 ≥ 内部 FAQ"的块）；冲突时在答案里**并列说明**："两份资料口径不一致（A 说 7 天，B 说 15 天），以 A 为准，来源 xxx"。

**我的现状（诚实）**：payload 现在只有 `text / source` 两个字段，**没有权威度、没有版本/生效日期**，所以本质上是"谁排名靠前信谁"—— 这是我明确知道的缺口。补法很清楚：给切块加元数据（`doc_type / effective_date`）+ 检索侧加过滤与加权。
一个已经做到的降冲突手段：用户上传的第三方文档（竞品数据）和我的知识库是**分开注入**的（上传内容走 chat state，知识库走检索工具），不会混在同一路检索里被当成同源信息。

**【项目证据】**
- qdrant payload 现状：`{"text", "source"}`（build_kb.py 写入处）
- 分离注入：`get_uploaded_docs` 走 state，`search_knowledge_base` 走检索

**【可能追问】那你怎么知道知识库内部有没有自相矛盾？**
答：**现在不知道**，我没有一致性检查。可补的做法：把 embedding 相近（阈值以上）但关键数字不同的条款批量比对，输出"疑似冲突清单"给人工确认 —— 这本质上是把"知识治理"从一次性动作变成持续检查。

**【状态】** ❌→🟡（机制没做，但判据、实现路径、现有缓解手段都讲得清）

## 怎么练这三份 RAG 手册

1. **第一遍**：按题号顺序，每题先自己口述 60 秒（录音）→ 再看口播稿 → 标出说不出来的；
2. **第二遍**：只练标出来的，重点背"开口第一句"；
3. **第三遍**：找人随机抽题，**90 秒内说完并给出一处具体证据**（数字 / 文件 / 一次翻车）；
4. **两题 ❌ 不要背**（第 12、21 题）：按手册里的"诚实 + 方案 + 判据"讲 —— 这两题反而容易聊出深度，因为你有具体判据（先补多轮金标用例 / 先给 payload 加元数据）。
