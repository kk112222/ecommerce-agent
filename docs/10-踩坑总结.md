## 一、LLM / Agent 特有坑（最值得讲，面试亮点）

### 坑 1：LLM 没有时钟感，乱猜日期 🔥

**现象**：让 Executor 查"本周营业额"，工具参数里的日期被 LLM 猜成 2023/2024 年 → 查出来全 0 → 报告得出"业务停摆"假警报。更离谱的是两个子任务猜的年份还不一样（t1 猜 2023、t2 猜 2024），这正是"猜"的铁证。

**原因**：LLM 的训练数据有截止日期，当前日期对它是盲区。它不会"知道今天几号"，只会按概率猜一个。

**解法**：prompt 里显式注入 `今天是 {today}` + 硬规则"相对时间（本周/上周）先换算成具体日期再调工具"。

**反思**：**LLM 不是数据库**。凡是"事实性"上下文（当前时间、公司名、业务口径），都必须由程序注入，不能指望 LLM 自带。

### 坑 2：结构化输出是脏数据，不能直接 json.loads 🔥

**现象**：让 Planner 输出 JSON 数组，返回的却常带 ```json 代码块、前后缀废话，直接 `json.loads` 就抛异常。

**解法**：三层容错：
1. 用正则剥掉 markdown 代码块 `^```(?:json)?|````
2. `json.loads` 包 try/except
3. 解析失败兜底降级（返回一个包含原目标的单任务 plan，保证流程不崩）

**反思**：LLM 的输出永远假设是脏的，解析层必须容错到底。

### 坑 3：LLM 会跑题 —— user 消息传错

**现象**：Planner 的 `Message(role="user", content=tool_list)` 把工具清单当成了目标，LLM 根本不知道要规划什么，规划出来的任务乱七八糟。

**解法**：user 消息必须放 goal 本体。

**反思**：每个角色只喂它该看的上下文（**关注点分离**）。这也是为什么提示词从 chat.py 搬到了各子 Agent 自己的文件里——提示词跟随角色，而不是堆在接口层。

### 坑 4：模型"全返回空"，别急着怪模型名 —— 先查调用端点 🔥（2026-08-19 新踩）

**现象**：想升级 `qwen3.7-flash` / `qwen3.7-plus`，配置后 LLM 全返回空；dashscope SDK 报 `400 url error, please check url`。一度以为这些模型名不存在，连试 `qwen3.5-ocr`、`qwen-vl-ocr` 全部 400，差点放弃。

**原因**：dashscope SDK 的 `Generation.call` 走的是**旧端点**（`/api/v1/services/aigc/text-generation/generation`），它**不认 2026 年的新模型**。qwen3.7 系列只挂在 **OpenAI 兼容端点**（`compatible-mode/v1/chat/completions`）。同一个模型名，两个端点一个 200 一个 400 —— 容易被误判成"模型名不存在"。

**解法**：用 requests 直连兼容端点验证 + 改造：
1. **验证别信 SDK 的 400**：`requests.post(BASE_URL, json={"model": 模型名, "messages": [...]})`，对比两个端点，200 的才是对的
2. qwen.py 从 `Generation.call` 改为 requests 直连 `compatible-mode/v1/chat/completions`
3. 格式适配：usage 是 OpenAI 命名的 `prompt_tokens/completion_tokens`（不是 dashscope 的 `input_tokens`）；tool 消息必须带 `tool_call_id`、assistant 必须带 `tool_calls`（OpenAI 格式）
4. 顺手把"API 报错静默返回空"改掉 —— 非 200 直接抛 `RuntimeError`，错误不再被吞

**反思**：**报错要信第一手信息，别信被包装过的**。`_parse_response` 静默返回空串，把 400 吞成了"模型返回空"，排查走了大弯路。另外 **2026 年起厂商统一推 OpenAI 兼容格式**——一次对接、全厂商通用，换 DeepSeek 只改 BASE_URL + model。

### 坑 5：Executor 偶发返回空结果（已修 ✅）

**现象**：5 个子任务里偶发某个返回空串，报告里就缺了一块。

**解法（已实现）**：`executor.run()` 空输出时兜底返回"该子任务未获取到数据"，已 mock 验证通过，空串不再流到综合报告。

## 二、Python 语言层坑

### 坑 6：`{...}` 是 set，不是 dict！🔥

**现象**：`headers={...}` 一字之差，SSE 接口直接 500：`AttributeError: 'set' object has no attribute 'items'`。

**原因**：Python 的花括号字面量默认是 **set**，dict 必须是 `{key: value}` 带冒号的形式。

**反思**：这是 Python 新手最经典的坑之一，面试常考。

### 坑 7：dict 推导式 vs set 推导式

**现象**：`{t["id"]: r for t, r in zip(plan, results_list)}` 是 dict，`{x for x in ...}` 是 set。类型写错，后面 `results.items()` 就崩。

**诀窍**：推导式花括号里**有没有冒号**决定它是 dict 还是 set。

### 坑 8：缩进即作用域

**现象**：`return r` 缩进在 `if on_event:` 里面，当 `on_event` 为 None 时函数返回 None → 子任务结果全丢。

**反思**：Python 没有块级大括号，缩进错了就是逻辑错，review 时重点盯缩进。

### 坑 9：构造参数顺序写反

**现象**：`ReActAgent(self.registry, self.llm)` 和构造签名 `(llm, registry)` 顺序相反，不报错，但运行时拿错对象。

**反思**：Python 无类型检查，这类错只能靠构造函数的参数命名约定 + 仔细 review。新代码尽量用关键字参数调用，能避开一大半这类问题。

## 三、环境 / 部署坑（Windows 三座大山）

### 坑 10：bash 的 python 指向了错误的 venv

**现象**：`ModuleNotFoundError: bcrypt`，但明明装过依赖。

**原因**：Windows 的 PATH 里有多个 Python，直接敲 `python` 命中了父目录的 venv，而不是项目的 `.venv`。

**解法**：启动一律写死 `.venv/Scripts/python`，不要裸敲 `python`。

### 坑 11：Windows 终端 GBK，打印 emoji 直接崩

**现象**：脚本打印 "📋 执行计划" 直接 `UnicodeEncodeError`。

**原因**：Windows 控制台默认 GBK 编码，和 UTF-8 源码是两套编码体系。

**解法**：脚本开头加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。

### 坑 12：文件名大小写

**现象**：`Planner.py` 大写 P 开头。

**原因**：Windows 文件系统不区分大小写能正常 import，但 Linux 区分，部署时 `from backend.agents.planner import Planner` 直接 ImportError。

**反思**：跨平台项目，文件名从第一天就小写下划线。

## 四、架构 / 异步 / 存储坑

### 坑 13：SSE 后台任务推不出去 🔥

**现象**：图在后台跑，事件要实时推给前端，直接写 `yield` 会卡住整个响应。

**解法**：**asyncio.Queue 桥接**——后台任务 `queue.put(evt)`，SSE 生成器 `await queue.get()` 边等边推，`None` 当结束信号。

```python
queue: asyncio.Queue = asyncio.Queue()
async def run_graph():
    graph = build_supervisor(llm, registry, on_event=lambda evt: queue.put(evt))
    await graph.invoke({"goal": goal})
    await queue.put(None)          # None = 结束信号
task = asyncio.create_task(run_graph())
while True:
    evt = await queue.get()
    if evt is None:
        break
    yield f"data: {json.dumps(evt, ensure_ascii=False)}\n\n"
await task
```

**反思**：这是"后台跑 + 前台流式"的标准解法，面试能讲深。

### 坑 14：asyncio.gather 既要回调又要返回值

**现象**：直接 `gather(*[executor.run(t) for t in plan])` 收不回 on_event 汇报。

**解法**：包一层 `run_one(t)`——先 `await on_event(...)` 再 `return r`。

### 坑 15：sessions[sid].append 直接 KeyError

**现象**：新会话没初始化 `sessions[sid]`，直接 append 崩。

**解法**：`sessions.setdefault(sid, []).append(...)`。

### 坑 16：数据过期，比没数据更危险

**现象**：seed 数据停在 8/6，只覆盖过去 30 天，问"本周"查出来全是边界数据，报告结论失真。

**解法**：演示前清库重新 seed。

**反思**：**脏数据比没数据更危险**——它会产出看起来很专业、其实是错的结论。Demo 前先确认数据新鲜度。

### 坑 19：Qdrant 本地模式 point id 必须是 UUID（2026-08-22 新踩）

**现象**：给用户记忆向量化存 qdrant，测试时 id 用 `"m1"`、`"m2"` 这种自定义字符串，写入直接抛 `ValueError: Point id m1 is not a valid UUID`。

**原因**：Qdrant（本地模式也一样）强制 point 的 id 必须是 UUID 格式，不接受任意字符串。项目里 `build_kb.py` 一直用 `str(uuid.uuid4())` 所以从没踩到，阶段 2 手写写入时才暴露。

**解法**：写 Qdrant 的 id 一律 `str(uuid.uuid4())`。

**反思**：**组件有约定，造数据前先看项目里已有的用法**。`build_kb.py` 就是活教材——同一个库的既有写法就是"正确用法"，照抄能避开绝大多数 API 约定坑。

### 坑 20：Qdrant 新版 `scroll()` 返回元组，不是对象（2026-08-25 新踩）

**现象**：验收脚本里 `c.scroll(collection_name="user_memories").points` 直接抛 `AttributeError: 'tuple' object has no attribute 'points'`。

**原因**：qdrant_client 版本差异——新版 `scroll()` 返回 `(points, next_page_offset)` 元组，老版才返回带 `.points` 属性的对象。照老教程写 `.points` 就崩。

**解法**：`points, next_offset = c.scroll(collection_name=...)`。

**反思**：延续坑 19 的教训——**第三方库的返回结构也会随版本变**。写完立刻用真实数据跑一遍，别等验收才暴露。这也是保留 `scripts/verify_stage2_db.py` 这类验收脚本的价值：每次跑都是给库 API 做体检。

### 坑 21：覆盖式写入的陷阱——"保存"不等于"累积"（2026-08-25 新踩）🔥

**现象**：验收阶段 2 时，第一轮对话明明表达了"负责男装、关注转化率、突出促销卖点"等 6 条画像，但第二轮对话后再查库，**只剩最后提炼的 1 条，之前全被冲掉**。

**原因**：`save_user_memories` 用了**覆盖式写入**（先 `delete_by_user` 清掉该用户旧记忆，再插入本轮提炼的）。初看是对的——避免重复积累。但提取器每轮只提炼"本轮对话"的新信息，覆盖式写就把上一轮的画像整个丢了。**覆盖式写入对"全量快照"有效，对"增量提炼"就是数据丢失。**

**解法**：改**读-合并-写**——写入前先读旧画像（`user_profile` 表），把「旧画像 + 本轮对话」一起喂给 LLM 合并成**全量画像**，再覆盖写。这样每轮写入的都是"当前最完整的画像"。核心变化：`_extract_and_save` 先 `get_user_profile` → `extractor.extract(goal, old_profile)` → 再覆盖写。

**反思**：**写库前先想清楚数据语义**——这数据是"全量快照"还是"增量事件"？覆盖式只适合快照；增量数据要么追加、要么先合并再写。面试能讲：这是"数据写入策略"层面的设计决策，不是简单 bug，是验收（真实跑两轮对话）才暴露的隐藏缺陷。

### 坑 22：工具报的错，LLM 根本收不到（2026-09-12 新踩）🔥

**现象**：LLM 调工具时参数传错键名（比如把 `content` 写成 `document`），工具里精心写的错误提示「参数不完整：需要 content 和 instruction」写了等于没写——LLM 收到的工具结果是字符串 **`"None"`**，完全不知道为什么失败，只会用同样的坏参数再试一遍，或者干脆自己编一个结果往下走。

**原因**：链路上断了两节。
1. **error 字段设计了但没人消费**。`ToolResult` 明明有 `success` / `error` 两个字段，但 `ReActAgent` 往 messages 里塞的是 `str(result.data)`——工具失败时 data 是 `None`，于是 `error` 从没进入 LLM 的上下文（3 处都这么写：`run()` 一处、`run_stream()` 两处）。
2. **参数校验散在每个工具里，靠别名兜底**。每个工具都得自己写 `kwargs.get("text") or kwargs.get("document") or kwargs.get("original")` 去猜 LLM 可能用的键名。猜不全就一直漏（LLM 想写哪个词就写哪个词），而且 10 个工具抄 10 遍，改一处漏九处。

**解法**：
1. **错误也是工具结果**。加 `_result_text(result)`：成功喂 `data`，失败喂 `调用失败：{error}`。三处统一走它，LLM 下一轮才有依据自纠（比如改用正确的参数名重调）。
2. **校验上收到注册中心**。`ToolRegistry.execute()` 一处做三件事：工具名不存在 → 可读错误 + 可用工具列表；缺必需参数 → 错误里**带上 spec 里这个参数的说明**（LLM 知道该补什么）；多传/传错键名 → 按 `spec.parameters` 过滤掉（传错键名的正好触发缺参错误，报出可读提示）。所有工具共享同一套，工具作者再也不用写 `**kwargs` 猜键名。
3. 删掉 `optimize_document` / `write_document` 里的全部别名兜底。

**反思**：
- **"设计了字段"≠"接通了链路"**。`ToolResult.error` 一直存在，但没人读它——这种"看起来做了、其实没接线"的缺陷比崩溃更难发现，因为它不报错，只是让 Agent 悄悄变笨。写完要顺着数据流走一遍：这个字段从哪产生、经过谁、最终谁消费？
- **ReAct 能自我纠错的前提是失败信息回到上下文里**。Agent 的"自主性"不是 LLM 凭空来的，是你把错误如实喂回去换来的。丢掉 error，等于把一个能自纠的 Agent 降级成只会重试的脚本。
- **约定优于兜底**。`spec.parameters` 本来就是给 LLM 看的对外契约，那它就该是唯一真相源——校验、报错、过滤全从它派生，而不是每个工具各写一套"我猜你会传什么"。别名兜底是在给错误打补丁，越打越厚。

**验证**：`scripts/verify_tool_args.py`（7 项：未知工具名 / 9 个工具零参数拦截 / 传错键名 / 多余键过滤 / None 与 0 的判定 / ReAct 链路 error 真的喂回 / 成功路径不受影响）；回归 `verify_document_agent.py` 全绿，另静态核对过 10 个工具的 execute 参数都在 spec 里声明过（过滤不会误伤可选参数）。

## 五、认知 / 概念坑（新手特有）

### 坑 17："state 里没有 goal 啊？"

**现象**：反复问 `state["goal"]`、`state["plan"]` 在哪定义，看代码找不到。

**本质**：state 就是 `graph.invoke({"goal": goal})` 传进来的那个 dict，**"赋值即定义键"**——不需要预先声明，`state["plan"] = ...` 执行完，键就诞生了。

**类比**：state 是一叠便签纸，写上去就存在，没写就是没有。

### 坑 18："graph.invoke({"goal": goal}) 没写进 state 里呀？"

**本质**：invoke 的参数**就是** state 本体。第一个节点读 `state["goal"]`，读的就是它。不用再"写一遍"。

## 本章小结

- LLM 类坑是**面试亮点**：无时钟感、脏输出、跑题，都是真实开发才会遇到的事
- 新坑 4：**报错要信第一手**——SDK 静默吞错 + 旧端点不认新模型，排查要直连端点验证
- 新坑 19：**写向量库先看项目既有写法**——Qdrant point id 必须 UUID（`build_kb.py` 就是教材）
- 新坑 20：**第三方库返回结构会随版本变**——Qdrant `scroll()` 新版返回元组，写完用真实数据跑一遍

- Windows 三座大山：**venv / GBK / 大小写**，工程化必备意识
- SSE + Queue 是流式输出的标准解法，值得画图讲深
