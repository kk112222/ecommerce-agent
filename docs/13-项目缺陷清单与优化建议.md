## 二、🔴 P0 —— 会炸 / 安全

### P0-1 全局关闭 TLS 证书校验（上轮已提，仍在）

- **现象**：`backend/core/llm/qwen.py` 第 18-28 行 monkey-patch 了整个 `requests.Session.request`，给进程内**所有 HTTPS 请求**加上 `verify=False`。
- **证据**：`qwen.py:24` 定义 `_patched_request`，`qwen.py:28` 执行 `requests.Session.request = _patched_request`；注释自称"临时方案…上线前务必删除"。
- **影响**：DashScope API Key 走不校验证书的连接 → 中间人可截获；且**影响范围是全进程**，不止 LLM 调用。任何有经验的评审者看到这一行，会直接判定"这代码不能上生产"。
- **怎么修**：删除 monkey-patch；若确有本地证书问题，改为按请求传 CA bundle / `verify=<path>`，或单独建一个带 verify 配置的 Session。
- **状态**：❌ 未修

### P0-2 工具内部异常穿透 registry，打死整个 ReAct 循环（已实测复现）

- **现象**：
  ```
  await reg.execute("query_sales", start_date="本周", end_date="今天")
  → RAISED ValueError: time data '本周' does not match format '%Y-%m-%d'
  ```
- **证据**：`registry.py:57` 是 `return await tool.execute(**clean)` —— 只兜住了"工具名不存在 / 缺必需参数"，**没有 try/except 包住工具本体**；`simple_agent.py:44` 的 ReAct 循环里对 `registry.execute` 同样没有 try。
- **影响**：异常一路上抛 → executor 子任务死 → 整轮对话返回"分析失败"。**这恰好命中《10 · 踩坑总结》里的坑 1（LLM 无时钟感、乱传日期）**：LLM 最常犯的错，现在不是"看到错误自我纠正"，而是整条链路崩。日期格式只是例子，任何工具内部的 ValueError / TypeError / 网络错误都一样。
- **怎么修**：在 `registry.execute` 里包一层
  ```python
  try:
      return await tool.execute(**clean)
  except Exception as e:
      return ToolResult(success=False, data=None,
                        error=f"调用 {name} 失败：{type(e).__name__}: {e}。请检查参数后重试。")
  ```
  配合已有的 `_result_text`（把 error 回传 LLM），LLM 就能自己改参数重试 —— 这才是 Agent 该有的韧性。
- **状态**：❌ 未修（**建议第一优先**）

### P0-3 文档功能是"半截的"：生成的文档用户拿不到

- **现象**：Agent 回复"已保存到 outputs/xxx.md"，但网页上既看不到也点不开。
- **证据**：`doc_output.py` 写到项目根 `outputs/{user_x}/{session}/`；grep 整个 `backend/` 无 `FileResponse` / `StaticFiles` / 下载类路由；grep `frontend/src` 无任何下载/文档入口；`.gitignore` 里**没有 `outputs/`**（`Test-Path outputs` = True，目录已存在）。
- **影响**：① 功能不可用（用户只能去服务器磁盘找文件）；② 生成物可能被误提交进 git；③ 写进应用目录 → 容器化部署重启即丢。
- **怎么修**：加 `GET /api/documents/{filename}` 下载接口（**必须校验文件归属当前 user_id，防越权下载**）+ 前端在报告里渲染下载链接；`.gitignore` 加 `outputs/`；长期把存储换成对象存储（`infrastructure/oss/` 目录已经在等着）。
- **状态**：❌ 未修

## 三、🟠 P1 —— 数据正确性 / 功能断链 / 配置失效

### P1-4 记忆合并：作废无护栏 + 相似度判据判别力不足

- **现象 A（无护栏）**：合并规则是"旧行没被任何新句认领 = 判定不再成立 → 作废"（`store.py:186-188`）。这**完全依赖 LLM 每次输出的全量画像都完整**：LLM 少写一条、输出被截断 → 那条记忆被静默作废，没有任何"本轮作废比例异常就拒绝/告警"的保护。
- **现象 B（判据弱）**：`_ratio` 用 difflib 字面相似度分三档（≥0.9 同条 / 0.45~0.9 变化版 / <0.45 新增）。实测：

  | 对比 | ratio | 落档 | 是否符合预期 |
  |---|---|---|---|
  | 负责男装类目 vs 负责女装类目 | 0.833 | 变化版（作废旧行+写新） | ✅ 符合 |
  | 关注退货率 vs 关注退款率 | 0.800 | 变化版 | ⚠️ 两条**平行** KPI 会被反复"作废重写"，id/importance/向量每轮重来；某轮 LLM 只输出一条 → 另一条真被删 |
  | 不关注美妆 vs 关注美妆 | 0.889 | 变化版 | ⚠️ 语义相反也落同一档，说明它分不出"相关"与"相反" |
  | 关注转化率 vs 关注客单价 | 0.400 | 新增 | ✅ 符合 |

- **影响**：记忆抖动（churn）+ 静默丢记忆；`importance` 因每轮重写而永远攒不起来（与 P2-8 叠加）。
- **怎么修**：① 加护栏——单轮"作废数 / 原生效数"超阈值（如 50%）时拒绝本轮合并并记日志；② 判据升级——0.45~0.9 区间交给向量相似度或让 LLM 判"同一偏好的更新 vs 两条不同偏好"；③ 给合并逻辑补 DB 级测试（见 P3-17）。
- **状态**：❌ 未修

### P1-5 SQLite 与 Qdrant 之间没有原子性、也没有对账机制

- **现象**：写路径顺序是**先动向量（删作废 / 插新）再提交 SQLite**。
- **证据**：`store.py:202-210`（`delete_points` / `upsert_docs`）早于 `store.py:215-230`（DB 事务 commit）。
- **影响**：
  - 向量已删、DB 提交失败 → 该行永久失去向量，**召回静默降级**（不报错，用户永远看不到它）；
  - 向量已插、DB 提交失败 → **孤儿向量**永久残留（`pid2row` 查不到会跳过，属泄漏）；
  - 设计文档声称"SQLite 是唯一事实源，qdrant 只当索引"，但代码没有让这句话成立（无启动对账、无孤儿清理）。
- **怎么修**：调换顺序（先 commit DB 再同步向量，失败可重试）**或**加 `scripts/reconcile_memory.py`（比对 `rows.qdrant_point_id` 与 qdrant 实际点，双向补/删），并把对账挂到启动或定时任务。
- **状态**：❌ 未修

### P1-6 Executor 的两个老洞都还在

- **现象 A**：planner 输出的 `tool_hint` 依然是**死字段** —— `executor.py:16` 只用了 `task['task']`。4 个并行子任务仍能看到**全部工具**，只靠 prompt 软约束，职责泄漏未堵。
- **现象 B**：`executor.run(self, task)`（`executor.py:10`）**不接收 `uploaded_data`**，所以"结合上传的竞品数据分析"这类子任务手里没有竞品数据 —— 文档链路已经能拿到 `uploaded_data` 了，分析链路仍断链。
- **怎么修**：`executor.run(task, uploaded_data=..., user_profile=...)`；按 `tool_hint` 过滤工具集（`get_all_specs(only=[tool_hint])`，需给 registry 加个参数），hint 为空时再放开全集。
- **状态**：❌ 未修

### P1-7 数据库配置：echo 常开 + 两个配置字段是死的

- **现象 A**：`session.py:10` 是 `create_async_engine(DB_URL, echo=True)` —— 跑探针时日志刷满 SQL（含业务数据）。
- **现象 B**：`session.py:6-7` 硬编码数据库路径，`config.py:9` 的 `database_url` **从未被使用**（grep 确认只在 config.py 出现）；`config.py:11` 的 `jwt_expire_minutes` 同样失效（`security.py:8` 自己写死 `60*24`）。
- **影响**：① 生产日志既吵又慢还泄数据；② 在 `.env` 改这两项**完全无效** —— 与"配置驱动"的设计目标自相矛盾，且会让"切 PostgreSQL"变成静默失败。
- **怎么修**：`create_async_engine(settings.database_url, echo=settings.debug)`；`security.py` 改读 `settings.jwt_expire_minutes`。
- **状态**：❌ 未修

## 五、🔵 P3 —— 测试 / 评测 / 文档

### P3-17 测试覆盖避开了风险最高的地方

- **现状**：`tests/` 5 个文件覆盖 `_ratio/_utcnow`（纯函数）、supervisor 路由接线、registry 参数校验、doc_output 路径安全 —— 这些做得不错。
- **缺口**：`merge_semantic_memories`、`recall_user_memories`、`executor`、`planner`、`synthesizer`、SSE 主链路 **零覆盖** —— 而 P0-2、P1-4、P1-5 全在这片区域。
- **怎么修**：优先补"记忆合并"的 DB 级测试（SQLite 内存库 + 已有 FakeLLM），断言：同义刷新不新增行 / 变化版作废旧行 / 旧行被漏写时不静默清空 / 召回命中与兜底行为。

### P3-18 RAG 评测只到"检索层"

- **现状**：`scripts/rag_eval.py` 55 条 golden set + 四策略对比（BM25 / 向量 / 混合 RRF / 混合+精排）+ Recall@5 / Hit@1 / MRR + 按来源拆分 + 真值完整性自检 —— **这批做得相当扎实**（真值选"预训练背不到"的虚构条款尤其专业）。
- **缺口**：衡量的是"片段有没有被召回"，**不是"回答忠实不忠实 / 有没有幻觉"**；回答层评测仍为零。另外运行前必须停后端（qdrant 本地模式单进程锁）——这本身也是"本地模式不适合上线"的证据。
- **怎么修**：加回答层评测：LLM-as-judge 判"答案是否忠于召回片段、有无片段中不存在的数字"，再抽样人工复核；做一次扰动测试（改 KB 里的运费金额 → 答对即证明真走了检索）。

### P3-19 文档与现实不一致

- `CLAUDE.md` 的结构图仍写着 `content_gen/`、`customer_service/` 是"空壳"（实际已是完整 Agent），且未体现新增的 `document` 链路与 `tools/document_tools`。
- `docs/` 实际只有 00、01、10、12、13，但 `00-项目概述.md` 的章节导航指向 02~09 六篇**不存在的文件**。
- **怎么修**：要么补齐章节，要么把导航改成"已发布章节列表"；`CLAUDE.md` 的结构图更新为当前实际。

## 六、值得肯定的部分（本次评审确认）

1. **上轮提出的洞已闭环**：`registry` 现在统一做工具名 + 必填参数校验，`simple_agent._result_text` 会把 `error` 回传给 LLM —— "LLM 自我纠正"的回路真的通了（探针实测前两项通过）。
2. **角色拆分延续得很干净**：content / service / document 三个角色文件结构完全对称，supervisor 只做组装；从 3 条链路扩到 4 条只加了"一个文件 + 一段路由"。
3. **文档落盘的路径安全很扎实**：只取末段文件名、剥盘符、清 Windows 非法字符、`is_relative_to` 双保险 —— 手工验证穿越/清洗/白名单/隔离 **9/9 通过**。
4. **记忆系统方向正确**：从"删光重建"改成"SQLite 事实源 + 增量合并 + 双桶（semantic/episodic）+ 管理接口"，P1-4/P1-5 是这条路上的收尾活而非方向错误。
5. **`rag_eval.py` 就是"尺子"该有的样子**：golden set + 真值完整性自检 + 多策略 A/B，改检索前后可直接对比数字。
6. **测试基建建立**：离线 FakeLLM、不联网、不依赖 `.env` —— 这正是 `BaseLLM` 抽象的设计红利被兑现。

## 七、优化建议（按优先级的三条路线）

### 路线 A｜止血包（约半天，收益最高）

3. `echo=settings.debug` + 让 `database_url` / `jwt_expire_minutes` 真正生效（P1-7）。

> 收益：把"LLM 传错参数就整条崩"变成"LLM 自己改对重试"，是稳定性上最大的一次跃迁。

### 路线 B｜记忆收尾（约一天）

1. 合并加"作废比例"护栏 + 升级 0.45~0.9 档的判据（P1-4）；
2. 向量/DB 顺序对调或加 `reconcile_memory.py`（P1-5）；
3. importance 加衰减、episodic 加 TTL、兜底补数不参与热度（P2-8/9/10）；
4. 给合并逻辑补 DB 级测试（P3-17）。

### 路线 C｜文档闭环（约半天到一天）

1. 下载接口（带归属校验）+ 前端下载入口 + `.gitignore` 加 `outputs/`（P0-3）；
2. 长期把本地落盘换成对象存储。

### 长期项（不紧急但值得排）

- Executor 工具白名单 + 打通 `uploaded_data`（P1-6）；
- 全局 token/时间预算与用量展示（P2-11）；
- 回答层评测 + 扰动测试（P3-18）；

## 八、这份清单的"面试用法"

修复时的三条最有讲头的故事（都是**自己发现 → 定位 → 有数字/复现 → 修复**的完整闭环）：

1. **P0-2 工具异常穿透**：可以讲"我用探针脚本复现了 LLM 传中文相对时间导致整条链路崩，定位到 registry 没兜工具本体异常，改成返回结构化错误让 LLM 自我纠正"——这是对 Agent"韧性"的正面回答。
2. **P1-4 记忆合并的阈值实证**：可以讲"我用 difflib 做了相似度分档，然后用六组真实短句测出它分不出'关注退货率 vs 关注退款率'这类平行偏好，所以把判据升级/加护栏"——展示了"用数据验证设计假设"的习惯。
3. **P3-18 RAG 评测**：55 条 golden set + 四策略 + Recall@5/Hit@1/MRR，能直接回答"你怎么知道检索改好了"。
