# 19 · 面试问答手册（RAG）：第 1~7 题

> 题目来自小林 RAG 分册（https://www.xiaolinnote.com/ai/rag/，共 21 题），答案**全部结合你自己的项目**。
> 配套数字（2026-09-16 实测）：8 个知识库文件 → **32 块**；CHUNK_SIZE=200 字 / OVERLAP=40 字；块长最小 6 / 中位 82 / 最大 223；
> 检索 top_k=5；RRF 的 k=60；rerank 用 gte-rerank-v2 对融合后 top10 精排；金标集 **51 条**、四策略对比。
> 用法同 Agent 手册：先自己口述 60 秒，再看口播稿；标记 ✅ 可直接答 / 🟡 要说清取舍 / ❌ 缺口（诚实+方案）。

## 第 1 题｜什么是 RAG？完整工作流程？

**【开口第一句】**
RAG = 检索增强生成：先把问题变成向量去知识库里捞出相关片段，再把片段当**证据**喂给模型作答。它分两条流程：**离线建库** 和 **在线检索作答**。

**【90 秒口播】**
**离线（build_kb.py 一条命令）**：解析多格式文档（md / pdf / docx / html / csv）→ **结构化切块**（我这套 KB 是 8 个文件 → 32 块）→ 调 text-embedding-v3 向量化 → 写进 Qdrant 的 kb_docs 集合（payload 带 text 和 source）。

**在线（用户问「退货要多久，运费谁出」）**：
1. 意图分类判为客服链路 → 客服 Agent 的 prompt 要求**先检索再回答**；
2. 模型调 `search_knowledge_base` 工具 → query 走两条路：BM25 关键词（中文按字切）+ 向量语义，各取 top10；
3. **RRF 融合**（只看排名不看分数，k=60）→ 得到一份候选；
4. 用 **gte-rerank-v2 交叉编码器**对候选精排（top10）→ 取 **top5**；
5. 片段裁到每段 300 字、带 `[source]` 标注回灌给模型 → 模型基于证据作答 → SSE 逐字推给前端。

**【项目证据】**
- 离线：scripts/build_kb.py（切块 + 向量化 + 全量覆盖式重建）
- 在线：backend/tools/service_tools/rag_search.py（RAGTool）→ retriever.py（BM25 + 向量 + RRF + rerank）

**【可能追问】RAG 为什么被封装成一个工具，而不是写死的 pipeline？**
答：因为我的上层是 Agent —— 把检索做成工具（和 query_sales 一样继承 BaseTool），模型自己决定**什么时候检索、检索几次、用什么 query**。代价是"模型可能不检索"这种任务幻觉，所以我在 prompt 里写死流程，并且在评测里专门做 bypass 检测（第 17 题）。

**【状态】** ✅

## 第 2 题｜RAG 主要解决什么问题？

**【开口第一句】**
三件事：**私有知识**（模型训练时根本没见过的数据）、**时效**（训练截止之后发生的事）、**幻觉与可溯源**（让它有据可依、能给出处）。

**【60 秒口播】**
我的知识库里全是**虚构条款**：退货运费 8 元、保修 1 年、SVIP 门槛 20000 元、包邮 99 元 —— 这些数字任何模型都背不到。所以只要答对，就一定是检索链路在工作，这一点让我的评测特别有判别力（第 18 题会展开）。

更新上：改一个 md 文件 → 重跑 build_kb → 进程内的 BM25 索引靠**语料指纹**自动失效重建，不用重启后端。这比"重新训练一个模型"便宜好几个量级。

**【项目证据】**
- backend/data/kb/（8 个文件：退货 / 物流 / FAQ / 会员 / 发票 / 账号 / 促销 / 跨境）
- 语料指纹自动重建：rag_search.get_retriever()

**【可能追问】什么场景 RAG 不适用？**
答：① 要改变的是**行为/风格/格式**（比如让输出严格符合某套公文格式）—— 那是 SFT/微调的活；② 需要**跨文档聚合推理**（"这些反馈里反复出现的共性问题是什么"）—— 单跳检索不够，要考虑分层摘要或 GraphRAG；③ 实时数值计算 —— 那该给工具，不是检索。

**【状态】** ✅

## 第 3 题｜RAG vs 微调，各自优劣？

**【开口第一句】**
一句话区分：**RAG 改「它知道什么」，微调改「它怎么表现」**。

**【60 秒口播】**
| 维度 | RAG | 微调 |
|---|---|---|
| 知识更新 | 改文档 + 重建，分钟级 | 重新训练，天级且要标注数据 |
| 可溯源 | 强（能给出处，我的片段带 source） | 弱（知识融进权重，说不出来源） |
| 幻觉控制 | 有据可依，还能做确定性筛查 | 依旧会编，且更难定位 |
| 成本 | 每次查询多两次 API 往返（embed + rerank） | 训练贵、推理便宜 |
| 适合改 | 事实、政策、口径 | 语气、格式、领域表达习惯 |

我的选择：政策条款是会变的（而且我 KB 里是虚构条款），所以知识层必须用 RAG；如果哪天要"所有周报都用同一套语气和段落结构"，那才是微调/SFT 的场景 —— 而且我现在用**技能层**（backend/skills/*.md）先把"口径和输出形状"固化了，成本比微调低得多。两者不冲突，可以叠加。

**【可能追问】为什么不做微调？**
答：① 数据量不够（我只有几十条金标问答，微调会过拟合）② 我的瓶颈不在"模型不会说"，而在**拆解与检索**（有评测数据支撑：检索层和编排层的指标都能定位到具体环节）③ 政策类知识要可溯源、可删改，微调这两点都给不了。

**【状态】** ✅

## 第 4 题｜文档怎么存、粒度多大、切块策略？

**【开口第一句】**
切块粒度**对齐「一个问题的答案单元」，不是固定字符数**。我这套 KB 的实测：8 个文件 → **32 块**，上限 200 字、块间重叠 40 字，块长中位数 82 字。

**【90 秒口播】**
存储：一块一行记录在 Qdrant 里（向量 + payload{text, source}），进程内还留一份同样的语料给 BM25 建倒排索引。

切块四步（`chunk_text`）：
1. **拆段落**：优先按空行；完全没有空行的纯文本（例如 PDF 抽成一整段）退回按行；
2. **超长段落先切**：没有内部结构的段落按行切到 ≤200 字，避免一块塞多个主题；
3. **组块**：遇到 `#` 标题**强制开新块**（md 的分节、html2text 转出的标题就是天然答案边界）；其余内容在 200 字内累积，**不腰斩段落**；
4. **overlap**：下一块开头补上一块结尾 40 字（标题块除外，保持干净），防"答案骑在块边界上"。

为什么是 200：我的 KB 是条款/FAQ 型，**一个条款就是 1~2 句话**（答案单元）。切太碎会缺前提（"7 天无理由"少了"自签收日起算"就不完整），切太大向量会被稀释成一个模糊平均语义、噪声也进来。这个数字是跟着"答案单元"定的，不是拍脑袋。

**【项目证据】**
- scripts/build_kb.py：CHUNK_SIZE=200、OVERLAP=40、chunk_text() 四步
- 实测统计：account.txt 2 块 / cross_border.pdf 2 / faq.md 6 / invoice.html 5 / membership.md 5 / promo.docx 2 / returns.md 5 / shipping.md 5 = 32 块

**【可能追问】怎么知道切得好不好？**
答：两个证据：① scripts/rag_quality_eval.py 是专门的切分质量评测；② 更直接的是 rag_eval 的 **Recall@5** —— 如果条款被切碎，真值片段就会漏出 top5，指标立刻掉。我改切块策略前后都用同一份 51 条金标集对比过。

**【状态】** ✅（这题有真实数字和实现细节，讲满 90 秒）

## 第 5 题｜怎么规避语义被切断？

**【开口第一句】**
四种手段叠加：**结构优先切**、**块间重叠**、**块自带主题**、**检索侧双路兜底**。

**【60 秒口播】**
1. **结构优先**：标题/条款是天然边界，我遇到 `#` 就强制开新块，所以每块自带"这段在讲什么"；
2. **超长先按行切**：避免一个块里塞两个主题（对应"语义被稀释"这种更隐蔽的切断）；
3. **overlap 40 字**：把上一块的结尾补到下一块开头 —— 整句劈两半时，两半都还在各自的块里；
4. **检索侧兜底**：BM25 关键词 + 向量语义双路 + RRF 融合 —— 即使某块被切碎，关键词路仍可能命中剩下那半；
5. **最后用评测兜底**：Recall@5 掉下来就说明切分有问题，我改过一版切块（300 字纯段落 → 200 字结构切 + overlap），块数从 7 涨到 32，就是为了让"一块 = 一个答案单元"。

**【可能追问】overlap 会不会让重复内容进上下文、浪费 token？**
答：会占一点，但 top5 里重复片段对答案无害。更彻底的做法是**父子块**（parent-child / small-to-big）：用小块做检索（语义更聚焦），命中后把它的**父块**（更大范围的原文）喂给模型 —— 既不切断语义，又不让向量被稀释。我没做父子块，这是明确的优化项。

**【状态】** ✅（前三招是实现的，父子块要作为"知道但没做"讲）

## 第 6 题｜Embedding 是什么？怎么选和评估 embedding 模型？

**【开口第一句】**
Embedding 是把一段文本映射到高维空间里的一个点，**语义相近的点距离近**；在 RAG 里它决定"能不能按意思找到"，是检索质量的地基。

**【60 秒口播】**
选型看六点：① **中文能力**（必须好，我的文档全中文）② **维度与成本**（维度越高越贵、存储越大）③ **最大输入长度**（决定单块能多长）④ **对称/非对称检索**（query 短、doc 长时，有些模型需要不同 prefix）⑤ 能不能**本地部署**（数据合规、延迟）⑥ 有没有配套 **rerank** 模型。

我用 text-embedding-v3，维度 1024（Qdrant 建集合时就按 1024 建的），rerank 用同门的 gte-rerank-v2，好处是同一家、鉴权和配额统一。

**评估方法（这才是重点）**：不要凭"感觉搜得准"，而是拿**自己的金标集**跑 Recall@k —— 换模型前后对比同一份 51 条集合。我的评测脚本是策略可替换的，换 embedding 只需改一行然后重跑。

**【项目证据】**
- backend/infrastructure/vector_store/embeddings.py（embed_text / embed_batch / rerank）
- 批量上限：DashScope text-embedding-v3 单次最多 10 条，超了整批 400（build_kb 里写死 batch_size=10）

**【可能追问】你横向对比过别的 embedding 模型吗？**
答：**没有**（诚实）。我的框架支持替换后重跑同一份金标集，但缺一次真实对比实验，这是我的待补项之一。另外我发现一处**文档与实现不一致**：embeddings.py 顶部注释写"1536 维"（那是上一代模型的维度），实际用 v3 默认 1024 —— 我把这条记进了缺陷清单，修法是显式传 `dimensions=1024` 并改注释，避免哪天默认值变了导致建集合维度不匹配。

**【状态】** 🟡（选型维度讲得清，但缺横向实验，主动认）

## 第 7 题｜Embedding 有哪几种算法？

**【开口第一句】**
三代：**静态词向量**（Word2Vec / GloVe，一词一向量、不分语境）→ **上下文相关**（BERT 类，取 [CLS] 或做 mean pooling，一词多义可区分）→ **对比学习双塔**（Sentence-BERT / BGE / GTE / text-embedding-v3 这一代，RAG 现在用的基本都是它）。

**【60 秒口播】**
第三代的关键是**对比学习**：同一个句子的两个增广版本在向量空间拉近、不相关的推远 —— 训练目标决定了它学的是"语义"而不只是"词形"。这也是"退钱"能命中"退款政策"的原因。

更实用的一个区分是**架构**而不是算法代际：
- **双塔（bi-encoder）**：query 和 doc **分别**编码，doc 可以离线算好存库 → 快，适合召回；
- **交叉编码器（cross-encoder）**：query 和 doc **拼在一起**送进模型输出相关性分数 → 准但慢（每个候选都要一次前向），只适合小候选集精排。

我的两段式检索就是这个理论依据：**双塔粗排**（BM25 + 向量各 top10 → RRF）＋ **交叉编码器精排**（gte-rerank-v2 对融合后的 top10 打分）。

**【可能追问】为什么不直接用交叉编码器做检索？**
答：成本 —— 检索要对全库打分（32 块还扛得住，生产上几十万块就完全不可行）；精排只对 10~20 条候选做，所以"粗排便宜召回 + 精排贵但准"是标准分工。

**【状态】** ✅
