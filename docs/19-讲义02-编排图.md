## 1. 先建立直觉：单 ReAct 循环为什么不够

讲义 01 的 ReAct 循环解决了"**一个任务内**怎么多次调工具"。但真实提问不是"一个任务"：

> "这周营业额为什么低？"

要回答它，得同时看：本期 vs 上期销售、类目涨跌、库存缺货、会员结构。四件事**互相独立、可以并行**。如果把它们全塞进一个 ReAct 循环，会出三个问题：

| 问题 | 后果 |
|---|---|
| **串行慢** | 一个循环里挨个查，四件事变四倍时间 |
| **互相污染** | 四套上下文挤在一个 messages 里，模型容易答着答着跑偏 |
| **不可观测** | 用户只看到"转圈 51 秒"，不知道它在干什么、卡在哪 |

所以架构上要分两层：

```
任务之间 → 编排（拆开、并行、汇总）   ← 这一讲
任务之内 → ReAct（调工具、看结果、再决定） ← 讲义 01
```

**这就是面试题 3「Workflow / Agent / Tools 的区别」的标准答案**：你两条都做了——analysis 链路是固定 Workflow（planner→executor→synthesize，路径写死），子任务内部是自主 Agent（ReAct），工具是原子能力。

## 2. 一句话定义（背下来）

    intent(分诊) → 条件边 → analysis : planner → executor×N(并行) → synthesize
                          ├ content : 一个角色 Agent 直接出稿

要能说出的三个关键词：**意图路由（条件边）**、**共享 state**、**并行 + 异常隔离**。

一句话版：

> **supervisor 是"分诊台 + 调度室"**：先用一次廉价 LLM 调用判断问题类型，分析类再拆成 2~5 条独立子任务并行跑（每条子任务是一个独立 ReAct 循环），最后综合成一份报告；整个过程通过事件流实时推给前端。

## 3. 逐段读代码

### 3.1 AgentGraph：48 行看懂"状态图"【骨架你写的】

整个引擎只有四个方法和一个 `while`。先看它的全部成员：

```python
class AgentGraph:
    def __init__(self):
        self.nodes: dict[str, Callable] = {}          # 节点名 → 函数
        self.edges: list[tuple[str, str]] = []        # (from, to) 普通边
        self.conditions: dict[str, Callable] = {}     # from 节点名 → 路由函数
        self.entry_point: str = ""                    # 起始节点名
        self.interrupt_before: set[str] = set()       # 暂停点（预留，目前没实现）
```

`add_condition_edges` 是唯一需要想一下的一行：

```python
def add_condition_edges(self, source, router, mapping):
    self.conditions[source] = lambda state: mapping[router(state)]
```

你传的是**路由函数 + 映射表**，它把两者合成一个闭包。这样 `invoke` 只管"问 conditions 要下一个节点名"，不用知道你的路由规则长什么样。

执行核心：

```python
async def invoke(self, state: State) -> State:
    current = self.entry_point
    while current:
        node_func = self.nodes[current]
        if inspect.iscoroutinefunction(node_func):    # 兼容 async / 同步节点
            state = await node_func(state)
        else:
            state = node_func(state)
        if current in self.conditions:                # 有条件边：问路由
            current = self.conditions[current](state)
        else:                                         # 没条件边：查普通边
            old_current, current = current, None
            for start, end in self.edges:
                if start == old_current:
                    current = end
                    break
    return state
```

**三个必须能讲的点**：

1. **state 就是一个 dict**，没有声明、没有 schema。"赋值即定义键"——`state["plan"] = ...` 执行完，这个键才诞生（这就是你文档里"state 里没有 goal 啊？"那个认知坑的答案）。
2. **节点返回 state，但不是必须返回新的**——大家都是原地改同一个 dict。整个系统靠"共享一个可变 dict"传递结果。
3. **`interrupt_before` 是死代码**：字段定义了，`invoke` 里从没读过它。被问到"中断恢复做了吗"，**主动承认这条很加分**（面试题 18）。

**为什么不用 LangGraph（面试题 13）**："我先用 LangGraph 做过 demo，自写是为了吃透 state 传递和条件路由（核心只有 48 行）；**生产我会选成熟框架**，自己维护编排引擎不划算。"——能上能下，比一味吹自研强。

### 3.2 图长什么样：7 个节点、4 条链路

```python
graph = AgentGraph()
graph.add_node("intent", intent_node)
graph.add_node("planner", planner_node)
graph.add_node("executor", executor_node)
graph.add_node("synthesize", synthesize_node)
graph.add_node("content", content_node)
graph.add_node("service", service_node)
graph.add_node("document", document_node)

graph.add_edge("planner", "executor")      # 分析链路：串行
graph.add_edge("executor", "synthesize")

def intent_router(state):
    return state.get("intent", "analysis")  # ← 必须是同步函数

graph.add_condition_edges("intent", intent_router, {
    "analysis": "planner", "content": "content",
    "service": "service", "document": "document",
})
graph.entry_point = "intent"
```

**追问点：router 为什么必须是同步函数？**

因为 `add_condition_edges` 里是 `mapping[router(state)]`——**直接调用、没有 await**。如果 router 写成 `async def`，`router(state)` 返回的是一个协程对象，拿它去查 mapping 会直接 KeyError。所以"要 LLM 判断的决策"必须提前在**节点里**做完（`intent_node` 里 await），router 只负责**读结果**。

这是个很典型的面试追问，答法：**节点负责"算"，路由负责"选"——把异步留在节点里，路由保持纯函数（可测、无副作用）**。

### 3.3 intent_node：一次廉价分类，换掉一堆复杂分支【你写的】

```python
async def intent_node(state):
    try:
        state["intent"] = await classifier.classify(state["goal"])
    except BudgetExceeded:
        state["intent"] = "analysis"      # 开局就没额度：走最通用的链路，后面各自降级
    if on_event:
        await on_event({"type": "intent", "intent": state["intent"]})
    return state
```

分类器本身（`intent_classifier.py`）有三个细节值得说：

- **`temperature=0`**：分类要确定性，不要创意；
- **user 消息放的是 goal 本体**（不是工具清单——那是你踩过的坑）；
- **三层容错**：剥 markdown 代码块 → `json.loads` → 失败兜底 `analysis`；拿到的值不在四类里也兜底 `analysis`。

**为什么单独花一次 LLM 调用做分类，不让主模型自己判断？**（面试题 4 的 Router 模式）

> "查数、写文案、答售后、处理文档四类任务的**上下文需求、输出契约、失败模式都不同**，塞进一个 prompt 会互相污染。花一次廉价分类（几乎没有输出 token）换来后面每一路都用最合适的 prompt，是笔划算的买卖。"

### 3.4 planner_node：拆任务 + 挑技能

planner 的输出是 `{"skill": 技能名, "tasks": [...]}`。为什么返回技能名而不只是任务列表——**因为 executor 的工具范围要跟着技能走**（3.5 讲）。

**五条硬规则**（写在 prompt 里）：

1. 拆成 2~5 条，每条**必须能独立完成、不依赖其他子任务**
2. `tool_hint` 填**首选工具**（可选，一个），判断不出留空
3. **按"要回答的问题"拆，不按"工具"拆**——一条子任务内部可以调多个工具交叉验证
4. 技能里写明的对照项（比如环比要取上一周期）不能省
5. 只输出 JSON

第 3 条是重点（面试题 7）：**"查销售 → 发现跌 → 再查库存"是一条子任务内部的事**（ReAct 自己会连查），不该拆成三条子任务——拆了反而拿不到"为什么跌"的结论。

**输出清洗 `_sanitize`** 兜四类脏数据：不是 list / 缺 task / **id 重复** / tool_hint 编造工具名。其中 id 重复那段藏着一次真实的线上事故：

```python
if tid in seen_ids:                      # id 重复 → 重编
    n = len(seen_ids) + 1
    while f"t{n}" in seen_ids:           # ← 候选名必须每次循环往前推
        n += 1
    tid = f"t{n}"
```

早先写成了 `while tid in seen_ids: tid = f"t{len(seen_ids) + 1}"`——`len(seen_ids)` 是**循环不变量**（循环里没 add），候选名永远不变，一旦被占就**原地自旋**；同步 CPU 跑在请求路径上，直接把整个事件循环堵死。用 `faulthandler` 才实锤。

> 面试题 20「死循环检测与治理」就拿这个讲：**"不自旋"这条纪律，是踩出来的，不是想出来的。**

**技能层（渐进披露）【09-16 新加的】**

```python
# supervisor 里：技能装配时读一次，planner 和 executor 共用
skills = load_skills()
planner = Planner(llm, registry, skills)
```

技能的定位一句话：**工具回答"能做什么"，技能回答"这件事该怎么做"**（拆哪几步、按什么口径、输出什么形状）。它**不新增任何能力**。

渐进披露是它的核心账：

| | 内容 | 什么时候进 context |
|---|---|---|
| 元数据 | `name + title + when`（约 75 字符/技能） | **常驻** planner prompt |
| 正文 | 口径 / 步骤 / 输出要求（约 553 字符） | **只有命中才加载** |

流程是两步：第一轮 planner 只看到元数据 → 判断命中某个技能名 → **带着技能正文重新规划一次**（`_replan_with_skill`）。

有个细节很能体现"想清楚了"：

```python
# 正文白展开了：这里当**没命中**处理（连工具范围也不放宽），而不是"算命中但用第一轮计划"
return {"skill": "", "tasks": tasks}
```

> 因为**权限跟着技能走**——技能声明 `scopes: analysis, document` 会把写文件的权限打开。如果"技能实际没生效"却仍按命中算，就会出现"**权限放开了，任务却是现编的**"。宁可退回普通规划。

**为什么技能写成 `backend/skills/*.md` 文件而不是 Python 常量？** 因为技能是**知识**不是**逻辑**：运营改一条口径，不该需要改代码、跑测试、发版。**目录即注册表**，加技能不用动代码。

（面试题 14「如何赋予 LLM 规划能力」答三层：prompt 硬规则 → 脏输出清洗 → 技能层固化流程口径。）

### 3.5 executor_node：并行 + 异常隔离【加固是后加的】

```python
async def run_one(t):
    try:
        r = await executor.run(t, uploaded_data=..., user_profile=..., scopes=scopes)
    except BudgetExceeded as e:
        r = _budget_note(e)                 # 一个子任务吃光额度，不连累其余三个
    except Exception as e:
        logger.exception("子任务执行失败：%s", t.get("id"))   # 降级不等于免责
        r = _fail_note(e)
    if on_event:
        await on_event({"type": "subtask", "id": t["id"], "task": t["task"], "result": r})
    return r

results_list = await asyncio.gather(*[run_one(t) for t in plan], return_exceptions=True)
```

这段是整个加固批次里最值钱的部分，**面试题 22 靠它**：

1. **两层捕获**：预算异常和普通异常分开处理，但都**只报销这一格**（`_fail_note` 生成占位文案），报告结构保持完整；
2. **`return_exceptions=True`**：连 `run_one` 自己都没接住的（比如 `on_event` 抛了）也不许冒到图外面——否则 `synthesize` 直接不执行，**上面那格降级就白做了**；
3. **降级不等于免责**：`logger.exception` 必须留，否则"偶发 500"只剩报告里一句软话，没人查得到。

**改造前是什么样**（讲对比最能体现你想过）：以前 `run_one` 只接 `BudgetExceeded`，别的异常穿过 gather 冒到 `AgentGraph.invoke`，图直接中断、`synthesize` 永远不执行——另外三个子任务**已经查好的数据全被丢掉**，用户看到的是"分析失败"。

> 话术：**"一格失败不拖垮整轮"**——并行系统里，部分失败是常态，要的是"带伤出报告"，不是"全有或全无"。

**工具范围按角色/技能收窄**（面试题 17 上下文工程）：

```python
skill = skills_by_name.get(state.get("skill") or "")
scopes = skill.scopes if skill else None      # 没命中技能 → 用默认 analysis 角色范围
...
registry = self.registry.subset_scopes(scopes or ["analysis"])
```

`registry.py` 里写死了四个角色范围（`TOOL_SCOPES`）：analysis 5 个数据工具、content 2 个、service 1 个、document 2 个。给子任务的是**角色范围**，不是单个工具。

> **2026-09-16 的那次调整值得单独讲**：最早是"按 `tool_hint` 只给一个工具"，粒度**绑错了层**。子任务的语义是"回答一个问题"，天然要用多个工具；锁成单工具时，planner 拆得不够细就会**静默给出残缺结论**（不报错、报告看着还挺完整，比"越界调用"更难发现）。现在边界绑在**角色**上，`tool_hint` 降级成"建议优先使用"的提示。

### 3.6 executor.run：子任务内部又是一个 ReAct【你写的】

```python
system_prompt = f"""你是数据分析子任务执行者,今天是{today}。你被分配了一个明确的子任务，只完成它，不要跑题。
【你的子任务】{task['task']}
【工作方式】1. 先判断要查哪些数据… 2. 一次不够继续调… 3. 数据收集完给结论
【输出要求】- 用 200 字以内总结：查到了什么 + 发现了什么问题」
"""
...
agent = ReActAgent(self.llm, registry)
result = await agent.run([Message(role="system", content=system_prompt)])
if not result or not result.strip():
    return "该子任务未获取到数据：工具查询无结果或执行器未返回内容。"
```

三个点：

- **`今天是{today}` 必须注入**（面试题里最值得讲的坑之一）：LLM 没有时钟感，不告诉它今天是几号，它会猜成 2023/2024 年，查出来全是 0，报告得出"业务停摆"的假警报。**事实性上下文（当前时间、业务口径）必须由程序注入，不能指望模型自带。**
- **只传一条 system 消息**：子任务是一次性执行、不需要多轮对话语义，任务本身写在 system 里，历史/画像/上传数据也一并拼进去，**保持单一入口**。
- **空结果兜底**：LLM 偶发返回空串，用占位文案挡住，不让空结果流到综合报告（面试题 23 任务幻觉的第一层防护）。

### 3.7 synthesize_node：流式综合 + 可视化

```python
full = ""
try:
    async for chunk in synthesizer.synthesize_stream(state["goal"], state["results"], ...):
        full += chunk
        if on_event:
            await on_event({"type": "token", "content": chunk})    # ← SSB 打字机
except BudgetExceeded as e:
    full = f"{full}\n\n{_budget_note(e)}" if full else _fallback_report(state)
state["report"] = full
```

- **边生成边推**：每个 token 都 `on_event`，前端就是打字机效果；
- **额度在最后一步用尽也不丢数据**：已经流式产出过半就保留，一个字都没有就用子任务结果拼一份兜底报告（`_fallback_report`）；
- **`VIZ_RULES`**：报告末尾可附一个 ```viz 代码块（内嵌图表 JSON），前端渲染成图表。规则里最狠的一条是「**数值必须逐字照抄子任务结果里出现过的数字，禁止自行计算**」——这是把"防编数字"落到了输出契约上。

### 3.8 预算：为什么卡在 LLM 层，而不是图层【09-13 加的】

```
intent + planner + 4×executor(每个≤10 轮) + synthesizer
最坏 40+ 次 LLM 调用 —— ReAct"调几次"是模型自己决定的，成本没有上限
```

`BudgetedLLM` 是个**装饰器**，套在任意 `BaseLLM` 外面：

```python
class BudgetedLLM(BaseLLM):
    async def chat(self, messages, tools=None, temperature=0.7):
        self.budget.check()                     # 还有额度吗？
        response = await self.inner.chat(...)
        self.budget.record(response.usage, ...) # 记账
        return response
```

**为什么不在 Graph 层卡？** 因为**调用次数是 ReAct 循环内部攒出来的**——planner 看不见、Graph 节点也看不见。只有包住 `BaseLLM` 才能覆盖全部调用点，**包括工具自己拿 llm 发起的调用**（比如 `title_optimizer`）。好处：所有 Agent 一行不改，加 Agent / 换模型都自动受控。

**超限的语义是"降级"不是"崩"**：`BudgetExceeded` 由 supervisor 各节点接住，已跑完的部分照样出报告，末尾注明提前结束。注意 `UsageBudget._over()` 的注释里那句话——**上限卡的是"还发不发下一次调用"**，所以已经付过费拿到的回复不会因为超限被丢掉（尤其流式报告，半截掐断用户拿到的是残缺内容）。

## 4. 一次真实执行的 state 流转（最重要的直觉，看三遍）

提问：**"这周营业额为什么低？"**

```
graph.invoke({"goal": "这周营业额为什么低？",
              "history": "...", "user_profile": "...", "uploaded_data": "..."})
   │
   ├─ intent_node      → state["intent"] = "analysis"
   │                     └─ 事件: {"type":"intent","intent":"analysis"}
   │
   ├─ planner_node     → state["plan"]   = [t1..t4]
   │                     state["skill"]  = "weekly-report"（命中周报技能时）
   │                     └─ 事件: {"type":"plan","plan":[...],"skill":"weekly-report"}
   │
   ├─ executor_node    → 4 条子任务 asyncio.gather 并行，每条内部是独立 ReAct 循环
   │                     state["results"] = {"t1": "...", "t2": "...", ...}
   │                     └─ 事件 ×4: {"type":"subtask","id":"t1","task":...,"result":...}
   │
   └─ synthesize_node  → 流式生成 → state["report"] = "完整报告"
                         └─ 事件 ×N: {"type":"token","content":"..."}
                         └─ 事件:    {"type":"report","report":"..."}
```

**state 的键是逐节点长出来的**：进来时只有 `goal/history/user_profile/uploaded_data`，出去时多了 `intent/plan/skill/results/report`。没有任何地方"预先声明"过它们——这就是"赋值即定义键"。

图外的两条尾巴（`chat.py`）：

```
finally: queue.put_nowait({"type":"usage","usage":budget.snapshot()})   # 这轮花了多少
         await queue.put(None)                                          # 结束信号：无论成败必达
```

> 注意最后那行注释里的坑：**Agent 链路失败也必须把结束信号送出去**，否则 SSE 永远挂起、前端无限转圈。`None` 当哨兵，`finally` 里必发。

## 5. 三个取舍（追问重灾区）

**5.1 为什么 analysis 用固定 Workflow，而不是让 LLM 自由决定路线？**
"analysis 这条链路的步骤是**稳定**的（拆→并行查→综合），固定下来可预测、可评测、可观测；自由度留给**子任务内部**的 ReAct。**该固定处固定，该自主处自主**——全自主的 Agent 在生产上难测难控。"（面试题 4）

**5.2 为什么不做反思（Reflection）回路？**（面试题 6 / 15）
诚实的答法："**没做**。我的替代方案是让 synthesizer 判定数据不足后回 planner 补一轮；如果做，我倾向做成**编排层的 replan 回路**，而不是让模型自评——自评容易自我肯定。"

**5.3 多角色能同时分派吗？**（面试题 16）
"现在**不能**：单意图单路由，'分析这周数据并写成文档'这种跨角色任务只能做一半。**已经补了一半**：技能层让工具范围跟着技能走（技能可声明多范围，`subset_scopes` 取并集），所以'这个流程需要哪些角色'有地方可表达了。**还差的一半是「顺序」**——子任务是 `gather` 并行的，而'查完数据 → 把结论落盘'里第二步依赖第一步，升级方向是 planner 输出带依赖的规划、executor 按拓扑序调度。"

## 6. 面试口播稿（90 秒，照着背）

> "我的编排是**自研的 48 行状态图**加一个 supervisor：用户问题先过**一次廉价意图分类**（analysis / content / service / document），由**条件边**路由到四条链路之一。
> 分析类会拆成 2~5 条**互相独立**的子任务，用 `asyncio.gather` **并行**执行，每条子任务内部是一个独立的 ReAct 循环，最后流式综合成报告。
> 三个我特别想说的设计：
> 一是**异常隔离** —— 并行子任务里某一格失败（超时、工具报错、预算耗尽），只把那一格转成占位文案，另外几格的结果照常出报告，不让整轮归零；
> 二是**预算卡在 LLM 层** —— ReAct 调几次是模型自己决定的，Graph 节点看不见，所以用装饰器包住 BaseLLM 统一记账，超限**降级出报告**而不是抛 500；
> 三是**能力边界绑在角色上** —— 子任务拿到的是'分析角色'的 5 个数据工具，不是单个工具。按单工具锁会**静默给出残缺结论**，这比越界调用更难发现。
> 另外整个过程的事件流（intent / plan / subtask / token / report / usage）实时推给前端，用户能看见它在干什么。"

## 7. 高频追问 + 答法

| 追问 | 怎么答 |
|---|---|
| 为什么 router 不能是 async？ | `add_condition_edges` 里是直接调用 `router(state)` 查表，async 会返回协程对象导致 KeyError。**节点负责算、路由负责选**，异步留在节点里 |
| state 是全局变量吗？并发安全吗？ | 每次 `invoke` 一个新的 dict，请求之间不共享；图内节点是串行推进的（只有 executor 内部 gather 并行，写的是不同 key） |
| 为什么不直接用 LangGraph？ | 自写是为吃透 state 传递与条件路由（核心 48 行）；**生产会选成熟框架**，不划算自己维护 |
| 子任务里又是 ReAct，会不会嵌套太深？ | 只有两层，且**层次不同**：任务之间是计划-执行（planner 拆、executor 并行），任务内部是 ReAct。两者配合而非二选一 |
| 技能和工具、prompt 的区别？ | 工具=能做什么（原子调用）；技能=这件事该怎么做（流程知识，写成 md，运营可改）；prompt=角色人格。**技能不新增能力**，只固化流程 |
| 技能为什么不做成常驻 prompt？ | 那等于每加一个技能永久多几百 token。渐进披露：元数据常驻、正文命中才加载。但说实话——**"省 token"在 10 个工具的规模下不成立**（schema 全集才 3556 字符），技能真正的价值是**流程可复用、可评测、运营能自己改** |
| 死循环怎么防？ | 三重：`max_rounds` 上限、LLM 层 token 预算、**角色/技能级工具范围**；planner 那次 id 重编号自旋是真实案例（`len()` 是循环不变量）。检测侧目前只有日志，是可补的点 |
| 用户中途刷新页面 / 断开怎么办？ | **执行中的图不能断点续跑**（`interrupt_before` 是预留死代码）；会话状态在 SQLite 可恢复，但图本身没有快照。要做需要 state 落库 + 幂等恢复 |
