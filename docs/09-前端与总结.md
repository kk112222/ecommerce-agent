# 09 · 前端与总结

> 后端整条链路都通了。这一章看**用户实际看到的东西**：
> 事件流怎么变成"看得见的进度"、报告里的图表从哪来、以及**整个项目做下来值得总结什么**。

## 本章目标

读完这一章，你会明白：

1. 后端推的一串事件，前端怎么变成**执行时间线**

## 一、把事件流变成"看得见的进度"

### 1.1 后端推什么，前端就要建什么状态

后端（第 05 章）通过 `on_event` 推一串事件，前端在 `ChatPage.handleSend` 里用一个大 `switch` 接住，**每类事件驱动"执行时间线"的一个步骤**：

```typescript
const [steps, setSteps] = useState<TraceStep[]>([]);   // 本次提问的执行时间线

case 'intent':
  setIntent(event.intent);
  finishStep('intent', { label: `识别意图 · ${INTENT_LABEL[event.intent] ?? event.intent}` });
  if (event.intent === 'analysis') {
    pushStep({ id: 'plan', kind: 'plan', label: '拆解执行计划', status: 'running', ... });
  }
  break;
case 'plan':
  finishStep('plan', { plan: event.plan, skill: event.skill });
  event.plan.forEach((p, i) => pushStep({ id: p.id, kind: 'subtask', label: `子任务 ${i+1}：${p.task}`, status: 'running', ... }));
  break;
case 'subtask':
  finishStep(event.id, { result: event.result.slice(0, 200) });
  break;
case 'token':
  pushStepIfAbsent({ id: 'report', kind: 'report', label: '生成最终报告', status: 'running', ... });
  appendAssistant(event.content);
  break;
case 'report':
  appendAssistant(event.report, true);
  finishStep('report', {});
  setLoading(false);
  break;
```

**本质是一个前端状态机**：`running → done`，靠事件驱动。

| 后端事件 | 前端动作 |
|---|---|
| `intent` | 完成"识别意图"，**analysis 才**新建"拆解执行计划" |
| `plan` | 完成计划步骤，**为每个子任务建一个 running 步骤** |
| `subtask` | 完成对应的子任务步骤（打勾 + 耗时） |
| `token` | 累积到当前 assistant 消息（打字机）+ 点亮"生成报告" |
| `report` | **用完整报告覆盖**（`replace=true`），结束 loading |
| `document` | 立刻插入下载入口 |
| `usage` | 挂一行用量小字 |
| `session` | 更新会话 id、通知外层刷新列表 |

### 1.2 三个必须处理对的细节

这三处任何一个写错，**界面就永远转圈**——而且是那种"数据明明都拿到了，就是转"的诡异状态。

**① 只有 analysis 链路才建"拆解计划"步骤**

```typescript
// 只有"数据分析"链路才有拆解计划 + 子任务阶段；
// 内容生成/客服问答是 ReAct 直接出结果，只推 report，不能加 plan 步骤（否则永远转圈）
if (event.intent === 'analysis') { pushStep({ id: 'plan', ... }); }
```

**这是前后端协议对齐的典型坑**。如果不管链路一律建 `plan` 步骤，那用户问"写三条标题"时：

```
intent=content → 前端建了 plan 步骤（running）
    → content 链路根本不推 plan 事件（它没有规划这一步）
    → 这个步骤永远不 done，界面永远转圈
```

**根因**：前端"猜测"了后端的行为。修法就是**让前端的分支条件跟后端的链路拓扑一致**。

**② `token` 事件会来很多次，步骤只能建一次**

```typescript
/** 仅当不存在时追加（防止 token 事件多次点亮"生成报告"） */
const pushStepIfAbsent = (step: TraceStep) => {
  setSteps(prev => prev.some(s => s.id === step.id) ? prev : [...prev, step]);
};
```

报告是**逐字**推的，`token` 事件会有几百上千次。用 `pushStep` 会瞬间多出几百个"生成报告"步骤。所以专门有个 `pushStepIfAbsent`。

**③ `error` 事件要把所有 running 标红并结束 loading**

```typescript
case 'error':
  // 后端链路异常（LLM 失败等）：标红 + 报错 + 结束 loading，别让界面永久转圈
  setSteps(prev => prev.map(s => s.status === 'running' ? { ...s, status: 'error' } : s));
  message.error(event.message || '分析失败');
  setLoading(false);
  break;
```

**这正是第 08 章那个"SSE 异常只能走流内 error 事件"的下游接应**：后端在 `run_graph` 的 `except` 里推一个 `error` 事件 → 前端在这里收口。

而 `handleSend` 最外层还有一个 `catch`：

```typescript
} catch {
  // 请求失败：把还卡在 running 的步骤标红，别让它一直转
  setSteps(prev => prev.map(s => s.status === 'running' ? { ...s, status: 'error' } : s));
  message.error('请求失败，请确认后端已启动');
} finally {
  setLoading(false);
}
```

**两个地方都要标红**，因为它们覆盖的是不同的失败：

| 失败 | 谁接 | 场景 |
|---|---|---|
| **流内失败** | `case 'error'` | 后端起来了，图跑到一半 LLM 挂了 |
| **流外失败** | `catch` | **后端根本没起来**，`fetch` 直接抛 |

**第二种情况下，`error` 事件永远不会来**——因为流压根没建立。只写第一种的话，后端没启动时点发送，界面会永远转圈。

### 1.3 展示顺序：活动流排在结论之前

```typescript
// 活动流排在"正在生成的回答"之前（Codex 的观感：先看它干了什么，再看结论）。
// 纯展示层重排，不动任何状态逻辑：最后一条若是 assistant，就把它拎出来放到时间线后面。
const lastIsAssistant = messages.length > 0 && messages[messages.length - 1].role === 'assistant';
const leading = lastIsAssistant ? messages.slice(0, -1) : messages;
const trailing = lastIsAssistant ? messages.slice(-1) : [];
```

```tsx
{leading.map((m, i) => renderMsg(m, i, false))}
{steps.length > 0 && <TracePanel steps={steps} />}
{trailing.map((m, i) => renderMsg(m, leading.length + i, loading))}
```

**渲染顺序是 `历史消息 → 执行时间线 → 正在生成的回答`。**

这里最值得学的是那句注释：**"纯展示层重排，不动任何状态逻辑"**。数据还是那个 `messages` 数组，只是在渲染前**切了一刀**。**UI 顺序的调整，不该污染状态管理的代码**——想改回"结论在上"只需要删三行。

## 二、报告里的图表从哪来

### 2.1 协议：报告末尾的 ```viz 代码块

第 05 章的 synthesizer 在 prompt 里要求模型**在报告最末尾追加一个可视化代码块**：

````
```viz
{"type": "line", "title": "近7日销售额趋势", "data": [{"x": "08-28", "y": 12000}]}
```
````

前端 `VizBlock.tsx` 负责**把它抽出来，渲染成真图表**：

```typescript
export function parseViz(content: string): ParsedMarkdown {
  const idx = content.indexOf('```viz');
  if (idx === -1) return { body: content, viz: null, incomplete: false };
  const rest = content.slice(idx + 6);
  const close = rest.indexOf('```');          // 找闭合
  if (close === -1) return { body: content.slice(0, idx), viz: rest, incomplete: true };
  const raw = rest.slice(0, close).trim();
  const tail = rest.slice(close + 3);          // 块后的残留（协议要求块在末尾，理论为空）
  return { body: content.slice(0, idx) + tail, viz: raw, incomplete: false };
}
```

### 2.2 为什么不设计成结构化接口

天真的想法是：后端解析出 `{report, charts}`，前端直接 `JSON.parse`。**更规范，但做不到。**

原因：**这个图表是 LLM 当场生成的**，不是后端算出来的。它的内容（用哪张图、画什么数据）由模型看着报告自己决定。后端能做的只是**约定一个格式**，然后把它从文本里"抠出来"。

> **代价**：文本是**流式到达**的——**你永远会先看到"块的开头"，几百毫秒后才看到"块的结尾"**。

### 2.3 容错三层（这是本节的重点）

| 情况 | 前端行为 | 代码 |
|---|---|---|
| **块还没闭合**（流式中） | 显示占位 `◐ 正在生成可视化…`，**正文照常打字** | `incomplete === true` |
| JSON 解析失败 | `〔可视化数据解析失败，以上方文字结论为准〕` | `catch { ... }` |
| `type` 不认识 / `data` 不是数组 | `〔可视化数据格式异常…〕` / `〔暂不支持的可视化类型：xxx〕` | 兜底分支 |

**每一条兜底文案都在做同一件事：把用户的注意力推回正文结论。**

图表只是"辅助呈现"（第 05 章 `VIZ_RULES` 里写死了"**正文结论必须仍用文字讲清，图/表只是辅助呈现，不能替代正文**"）。所以图表渲染失败**绝对不能影响正文**——这也解释了为什么 `MarkdownViz` 把正文和图表拆成两件事：

```tsx
function MarkdownViz({ content }: { content: string }) {
  const { body, viz, incomplete } = parseViz(content);
  return (
    <div className="prose">
      <ReactMarkdown>{body}</ReactMarkdown>
      {viz !== null && <VizBlock raw={viz} incomplete={incomplete} />}
    </div>
  );
}
```

**正文用 `ReactMarkdown`，图表是独立组件**——图表崩了，正文还在。

> 顺带说一句 `incomplete` 的处理很讲究：**流式过程中先把块从正文里摘掉并显示占位**，等 `report` 事件带来完整报告时（`appendAssistant(event.report, true)`）整体替换。所以打字机过程中**不会出现一段乱码 JSON**，用户看到的是"正文 + 正在生成可视化…"。

### 2.4 四种图形

```typescript
switch (cfg.type) {
  case 'line':   // 趋势 → 面积图
  case 'column': // 分类并排 → 纵向柱状
  case 'bar':    // 横向对比 → {x}=类目放 y 轴，{y}=数值放 x 轴
  case 'table':  // 明细 → 朴素表格
}
```

两个细节：

- **`bar`（横向）的轴是反的**：`xField="y" yField="x"`——类目名放纵轴、数值放横轴，这是横向条形图的标准长相（类目名长的时候不会挤在一起）。
- **`table` 没用 antd 的 `Table` 组件**，手写了个 `<table className="viz-table">`。注释说明了理由：*"不用 antd Table，省一层样式冲突"*。**在已经有一套自己样式令牌的地方，引入组件库的表格往往要跟它的默认样式打架**——手写 10 行更省事。

## 三、外壳：三段式布局 + 多会话

### 3.1 布局

```
┌────┬──────────────┬────────────────────────────┐
│rail│ SessionSide  │  ChatPage / DashboardPage  │
│ 掌 │   会话列表    │   消息流 + 时间线 + 输入区    │
└────┴──────────────┴────────────────────────────┘
```

- **rail**：窄窄一条图标栏（问答 / 看板 / 退出），看板视图下**会话列表整列隐藏**（看板不需要多会话）；
- **SessionSidebar**：会话列表 + 新建 + 重命名 + 删除；
- **content**：两个页面二选一。

### 3.2 `chatKey`：用"强制重挂载"来切会话

```typescript
const [chatKey, setChatKey] = useState(0);   // 新建/切换会话时自增，强制 ChatPage 重挂载

function newChat()      { setActiveSessionId(''); setChatKey(k => k + 1); }
function selectSession(sid: string) { setActiveSessionId(sid); setChatKey(k => k + 1); }

/** ChatPage 里会话确定/变化时回调：只更新高亮 + 刷新列表，
 *  不重置 chatKey（否则会清掉正在展示的对话） */
function handleSessionIdChange(sid: string) { setActiveSessionId(sid); refreshSessions(); }
```

```tsx
<ChatPage key={chatKey} initialSessionId={activeSessionId} onSessionIdChange={handleSessionIdChange} />
```

**React 的 `key` 变化 = 组件卸载重建**，于是 `ChatPage` 里所有 useState（消息、步骤、上传文件、用量）**全部回到初始值**，同时 `useEffect` 重新拉历史消息。

**为什么用这种"暴力"方式？** 因为它**避免了一整类 bug**：手动清空 8 个 state 时，漏清一个就会串台（切到新会话，上一轮的执行时间线还在）。**`key` 让它物理上不可能漏。**

**而 `handleSessionIdChange` 特意不重置 `chatKey`**——这个回调发生在**发完消息、后端返回真实 sid** 的时候。如果那里也重置，**正在展示的对话会被瞬间清空**（因为组件重挂了）。这个细节不写注释，下一个人一定会踩。

### 3.3 新会话的 id 从前端生成

```typescript
// 上传前确保有一个会话 ID：上传的文件挂在这个会话下，聊天时 Agent 才能读到
const ensureSessionId = () => {
  if (!sessionId) {
    const id = Math.random().toString(36).slice(2, 10);
    setSessionId(id);
    onSessionIdChange(id);
    return id;
  }
  return sessionId;
};
```

**为什么要前端生成？** 因为**上传文件必须带 `session_id`**——如果等到"发第一条消息"才由后端分配，那"先传文件再提问"的顺序就崩了（文件不知道该挂哪）。

后端也配合了这个设计：

```python
sid = request.session_id or str(uuid.uuid4())[:8]   # 前端没给就自己生成
```

**两边都能生成、以传入的为准**——这样"前端先建会话"和"直接用 API 调（不传 sid）"两种用法都能工作。

## 四、请求层：`api.ts` 一个文件收口

所有 HTTP 请求都在 `frontend/src/api.ts` 里，组件不直接 `fetch`。两个**只有踩过才知道**的坑：

### 4.1 两套请求头：为什么 multipart 要单独一个

```typescript
/** 构造带鉴权的请求头（自动附加 Bearer token） */
function authHeaders(): Record<string, string> {
  const token = getToken();
  return { 'Content-Type': 'application/json',
           ...(token ? { Authorization: `Bearer ${token}` } : {}) };
}

/** 构造仅带 token 的请求头 —— multipart 上传不能预设 Content-Type，
 *  否则 fetch 不会自动补 boundary，后端会解析失败 */
function authTokenHeaders(): Record<string, string> {
  const token = getToken();
  return token ? { Authorization: `Bearer ${token}` } : {};
}
```

**多文件上传（multipart/form-data）必须让浏览器自己设 `Content-Type`**——因为它要在里面带上 `boundary=----xxxx` 这个分隔符。你预设成 `application/json`，浏览器就不会补 boundary，**后端的 multipart 解析器找不到分隔符，直接解析失败**。

> 现象是"上传 400/422，但用 Postman 测又是好的"——因为 Postman 会自动处理。**这类坑的典型特征是"换个客户端就好了"。**

### 4.2 下载：`<a href>` 带不上 token

```typescript
/**
 * 下载生成文档 —— 走 fetch 拿 blob 再触发保存。
 * 不能直接 <a href="/api/documents/...">：接口要 Bearer token，a 标签带不上请求头。
 */
export async function downloadDocument(sessionId: string, filename: string): Promise<void> {
  const res = await fetch(url, { headers: authTokenHeaders() });
  ...
  const blob = await res.blob();
  const objectUrl = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = objectUrl; a.download = filename;
  document.body.appendChild(a); a.click(); a.remove();
  URL.revokeObjectURL(objectUrl);   // 及时释放，否则 blob 一直占内存
}
```

最"正常"的下载写法是 `<a href="/api/documents/...">`，浏览器会自己处理。**但认证接口不行**——`<a>` 发的是普通导航请求，**带不上 `Authorization` 头**（除非把 token 塞进 URL query，那更糟，token 会进浏览器历史和日志）。

所以只能：**`fetch` 拿 blob → `createObjectURL` → 造一个临时 `<a>` 点一下**。三行样板代码换来"token 只出现在请求头里"。

**最后那句 `URL.revokeObjectURL` 不能省**——每个 object URL 都会**钉住那份 blob 不放**，不释放就是内存泄漏（下载几十个文件后页面越来越卡）。

## 五、设计令牌：一处改，全局变

```
theme.ts         → antd 的 ConfigProvider 主题（codexTheme）
index.css        → CSS 变量（--text-3 / --warn / --grid …）+ 组件类（.viz-* / .chat-* / .rail）
VizBlock.tsx     → 图表专用的一小组色值（V.mark / V.grid / V.label）
```

```tsx
<ConfigProvider theme={codexTheme}>
```

三层的分工：

| 层 | 管什么 |
|---|---|
| `ConfigProvider` | **antd 组件**的颜色/圆角（Upload、message、Button…） |
| `index.css` 变量 | **自己写的组件**（聊天流、时间线、侧边栏） |
| `VizBlock.tsx` 的 `V` | **图表库**（`@ant-design/plots`）的色值 |

> **这层是"想改但没改完"的地方**（诚实记录）：图表色值和 CSS 变量是**两套并行的定义**。理想状态是把 `V` 换成读 CSS 变量（`getComputedStyle` 或者直接在 props 里写 `var(--x)`）。现在改主题色要动两个文件——**不算错，但是个明确的改进点**。

**一个值得一提的用法**：等宽字体只用在"元信息"上——`session {id}`、`usage`、`耗时`这类。**AI 生成的内容用正文字体，机器产生的元信息用等宽字体**，这个区分让界面立刻有了"工具感"。

## 六、跑起来

```bash
cd frontend
npm install
npm run dev          # http://localhost:3000
```

`vite.config.ts` 里配了代理，所以前端代码里写的一律是相对路径 `/api/...`：

```typescript
server: {
  port: 3000,
  proxy: {
    '/api': { target: 'http://localhost:8000', changeOrigin: true },
  },
}
```

**为什么用代理而不是写 `http://localhost:8000/api`？**

| | 代理 | 写死绝对地址 |
|---|---|---|
| 开发环境 | ✅ | ✅ |
| **生产** | ✅ 前端打包后同源部署，路径不用改 | ❌ 得改代码 / 加环境变量 |
| **CORS** | ✅ 同源，不触发预检 | ❌ 需要配 CORS 白名单 |

**同源代理让 CORS 问题在开发阶段就消失了**——当然生产环境如果前后端分开部署，CORS 还是得配（第 08 章的 `settings.cors_origins` 就是给那一刻准备的）。

**验证清单**（按顺序走一遍，整条链路就都验到了）：

1. 打开 → 登录页 → 注册一个账号（拿到 token）

7. 左侧新建对话 / 切换 → **时间线被清空**（`chatKey` 生效）
8. 切到看板 → 看 7 日趋势图 + AI 洞察

03 数据库设计      —— 9 张表、金额存分、异步 ORM
04 Agent 引擎      —— 48 行状态图 + ReAct 循环
05 多 Agent 编排   —— 路由 / 拆解 / 并行 / 综合 + 技能层 + 落盘
06 混合检索 RAG    —— 结构化切块 + BM25/向量/RRF + 重排
07 记忆系统        —— 三层记忆 + 增量合并 + 双存储对账
08 API 与认证      —— JWT + 依赖注入 + SSE
09 前端与总结      —— 事件流 → 时间线 + 图表协议
```

依赖关系是**从下往上**：01 给 04/05 提供 LLM；02 给 04/05 提供手；03 给 02 供数据；06/07 是 05 的两条链路各自的地基；08 把 05 包成 HTTP；09 把 08 画成人能看懂的样子。

### 7.2 五条贯穿全项目的主线

这五条是**每一章都出现、而且换一个场景还能复用**的东西。面试时讲这五条，比背任何单点细节都值钱。

**① 每一层都先定"契约"，再填实现**

| 层 | 契约 |
|---|---|
| LLM | `BaseLLM`（`chat` / `chat_stream`） |
| 工具 | `ToolSpec` + `registry.execute` 的四类校验 |
| 数据库 | `Base.metadata` 建表规则 |
| Agent | `AgentGraph` 的 node/edge/state |
| 前端 | `on_event` 的事件类型 + ```viz 协议 |

**先约定接口，实现就可以换**。所以换模型不动业务代码（01）、测试用假 LLM 能跑 150 项离线用例（02）、前端能独立于后端实现（09）。

**② 降级要"少给"，不要"崩"**

第 05 章那张降级总表有 **13 个降级点**。核心判断永远是同一个：

```
用户拿到不完整的答案   >>   用户拿到 500 或空白
```

**③ 静默失败是最贵的失败**

这条在项目里出现了**五次**，每次都是踩过之后补的：

| 章 | 原症状 | 补了什么 |
|---|---|---|
| 01 | `_parse_response` 返回空串，把 400 吞成"模型返回空" | 非 200 **直接抛** |
| 02 | 范围名对不上 → 放开全集但没人知道 | **告警** |
| 05 | 子任务偶发 500 只剩报告里一句软话 | **logger.exception** |
| 05 | 报告落到 `outputs/` 根目录（工具 context 缺 user_id）→ 文件在，但列表/下载都以 `outputs/user_<id>/` 为根，**谁都拿不到** | **落盘后校验路径 + 警告** |
| 07 | 记忆提炼失败只写日志 | **落表 + 计数进接口** |

一句话：**降级不是免责，每一次降级都要留下痕迹。**

**④ 幂等，换来的是一整类安全**

| 幂等的写路径 | 换来了什么 |
|---|---|
| 语义合并（同义只刷热度） | 提炼**可以安全重放**（07） |
| 情景 append（相似去重） | 同上 |
| `create_all` | 启动**可以反复补表**（08） |
| `reconcile_memory` | 启动**可以反复对账**（08） |

**"能不能重试"不是运气问题，是写路径设计出来的。**

**⑤ 边界要绑对层级**

| 绑错了 | 后果 | 改对了 |
|---|---|---|
| 工具边界绑"单条子任务" | **静默给出残缺结论**（不报错，更危险） | 绑**角色**（02） |
| 作废推断绑"一次缺席" | LLM 输出不全 = 静默丢真记忆 | 加**比例护栏**（07） |
| 路由绑异步函数 | 引擎是同步的，直接崩 | 结论**先写进 state**（05） |

**共同点**：这三处最初都是"看起来更严格/更简洁"的方案，**实际是把边界绑在了错误的层级上**。

### 7.3 如果重做，会改什么

诚实版（这部分面试很加分，因为它证明你知道边界在哪）：

| # | 现在 | 想改成 | 为什么 |
|---|---|---|---|
| 1 | `AgentGraph` 无环检测、无并行（并行在图外） | 加环检测 + 图内并行 | 现在靠"使用者不连环"，是**约定**不是**保证** |
| 2 | SQLite → 需要迁 PostgreSQL | 按 `config.database_url` 切（已经在做） | 并发写、DECIMAL、运维能力 |
| 3 | BM25 按字切中文 | 上分词（jieba 或模型）**或**保持现状 + 明确说明靠重排兜底 | 当前**够用但要说清是取舍** |
| 4 | 技能只有 1 个、`scopes` 还没跨角色 | 补 2~3 个真技能验证跨角色路径 | **预留的能力没被验证过 = 不知道有没有用** |
| 5 | 前端图表色值和 CSS 变量两套 | 统一读 CSS 变量 | 换主题要动两个文件 |
| 6 | `interrupt_before` 是死代码 | 删掉，或者真实现"人工审批" | 死代码会误导人（04） |
| 7 | 若干**注释漂移**（1536 维 / importance 召回+1） | 顺手改掉 | 代码对、注释错，**读的人会信注释** |

> 第 7 条是这个系列写下来**最意外的收获**：写文档时要逐行对代码，才发现有三四处注释已经和实现不一致了。**文档化的过程本身就是一次代码审计。**

### 7.4 面试怎么讲这个项目（三句话版）

```
做什么：一个电商运营的 AI 助手，运营用自然语言问业务问题，
         Agent 自己规划、并行调工具查数据、综合成带图表的报告。

技术上的两个抓手：
  一是"三个引擎全是自研的"——48 行状态图 + ReAct 循环 + 四角色编排，
     能讲清楚每个设计取舍（为什么自己写不用 LangGraph、边界为什么绑角色）；
  二是"每一层都在处理不可信输入"——LLM 的 JSON、LLM 生成的工具参数、
     混合检索的融合、记忆的合并、SSE 的异常，
     每一层都有自己的契约和不崩的降级路径。

最有说服力的不是功能多少，而是踩过的坑：
  旧端点不认新模型、while 自旋堵死事件循环、
  并发提炼互相覆盖丢记忆、从缺席推断作废会静默丢真记忆。
```

## 本章小结

- **事件流 → 执行时间线**：前端用 `steps` 数组做一个 `running → done` 的状态机，事件驱动
- **三个必须对的细节**：只有 analysis 才建 plan 步骤 / `token` 用 `pushStepIfAbsent` / **流内 error 和流外 catch 两处都要标红**
- **展示顺序重排不该污染状态逻辑**（`leading` / `trailing` 那三行）
- **图表走"约定代码块"而不是结构化接口**，因为图是 LLM 当场生成的；代价是要处理**流式半截**，容错三层的文案都在把注意力推回正文
- **multipart 不能预设 `Content-Type`**（浏览器要补 boundary）；**下载必须 `fetch` + blob**（`<a>` 带不上 token），记得 `revokeObjectURL`
- **`key` 强制重挂载**是切会话最省心的做法；新会话 id **前端先生成**（上传要先有归属）
- **五条主线**：先定契约 / 降级要少给 / 静默失败最贵 / 幂等换来安全 / 边界要绑对层级

## 练手挑战

**挑战一（必做）：给时间线加一条"技能"提示**

后端 `plan` 事件里带了 `skill` 字段（命中的技能名，`""` = 普通规划），但前端只把它透传给了 `TracePanel`。在步骤标签上显示出来（比如 `拆解执行计划 · 经营周报`）。

**验收**：问一句周报类的问题，时间线上能看到技能名；问普通问题时不显示。

**挑战二（推荐）：把时间线的耗时做成可对比的**

现在每个步骤算了 `costMs`。试着**按耗时给步骤加一个横向占比条**（比如最长的步骤 100% 宽度）。

**验收**：一眼能看出"哪个步骤最慢"——这通常直接指向优化点（多数情况是某个 LLM 调用）。

**挑战三（加分）：把 `VizBlock` 的色值改成读 CSS 变量**

现在 `V` 是硬编码色值。改成从 `getComputedStyle(document.documentElement).getPropertyValue('--x')` 读，或者在 CSS 里定义 `.viz-mark` 之类的类名。

**验收**：**只改 `index.css` 里的一处变量，图表颜色跟着变**——这就把 5 节那个"两套定义"的改进点真做掉了。
