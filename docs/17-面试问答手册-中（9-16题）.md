## 第 9 题｜Agent 的长短期记忆系统怎么做的？怎么存的？粒度是多少？怎么用的？

**【开口第一句】**
分三层存，粒度不一样：会话消息按「条」，长期记忆按「一句话」，兜底画像按「用户一条」。

**【90 秒口播】**
- **粒度**：长期记忆的粒度是**一条一句话、15 字以内、独立成立**（比如「负责男装类目」「关注转化率」）。为什么这么细？因为它要直接当**语义检索条目**用 —— 一条太长，向量会被稀释成一个模糊的平均语义。
- **怎么存**：SQLite 是事实源，一行一条记忆，字段有 kind（semantic/episodic）、text、importance、active、source_session、qdrant_point_id、created_at、last_access_at、expires_at；qdrant 里只存向量，point id 记在 SQLite 行上。
- **写入（增量合并，不是删光重建）**：LLM 每轮产出「当前全量画像」，我拿它和库里生效中的旧画像逐条比：
  - 相似度 ≥ 0.9 → 视为同一条，只刷新热度、不动数据；
  - 0.45~0.9 → 歧义档，交 LLM 判「同一偏好的更新」还是「两条并列偏好」；
  - < 0.45 → 新增；
  - 没有被任何新句认领的旧行 → 判定不再成立、作废（但加了护栏：一轮内未认领比例过高就不作废，防止 LLM 漏写把画像清空）。
- **怎么用**：召回时按 相似度 × 重要性 × 新鲜度 加权取 top 3，命中不足再补最近几条**语义**记忆；episodic 带 30 天 TTL。

**为什么不用「每轮清空重写」**：那是数据丢失 —— 提炼器只看「本轮对话」，覆盖写就把上一轮画像冲掉了。这是我在项目里真实踩过的坑（覆盖式写入对「全量快照」有效，对「增量提炼」就是丢数据）。

**【项目证据】**
- core/memory/store.py：合并逻辑、召回逻辑、对账 reconcile_memory
- db/models/user_memory.py：字段设计
- 相似度阈值用 difflib 字面相似度，0.45~0.9 档交 LLM 判断（因为实测「关注退货率 vs 关注退款率」字面相似度 0.8，字面判据分不出并列还是更新）

**【可能追问】SQLite 和向量库不一致怎么办？**
答：两个存储没有共享事务，所以我写了**对账函数**：启动时比对「生效行」和「qdrant 实际点」，行缺向量就重新向量化补上，没人引用的孤儿点就删掉（支持 dry-run）。承认 SQLite 是唯一事实源、定期拿事实源校准索引，比纠结写入顺序更实际。

**【状态】** ✅（这是你记忆这块最能讲深的一题）

## 第 10 题｜什么是 Multi-Agent？

**【开口第一句】**
Multi-Agent 是「多个有独立职责、独立上下文、独立输出契约的 Agent，由一个编排者调度」。我的是 **orchestrator-worker 模式**，不是多个 Agent 互相聊天。

**【60 秒口播】**
我的编排者先做意图分类，把问题分到四条链路：
- **analysis**：planner 拆子任务 → 多个 executor 并行 → synthesizer 综合；
- **content**：内容 Agent（写标题/文案）；
- **service**：客服 Agent（查知识库、只依据原文回答）；
- **document**：文档 Agent（解析/优化/落盘）。

四个角色各自有一份**人格 prompt**（写在各自文件里，比如 content_gen/content_agent.py），supervisor 只负责调度 —— 加一条链路等于「加一个角色文件 + 一段路由」，其他链路一行不用改。

角色之间**不直接对话**：它们通过共享 state（plan、results）交换结构化产物，编排者决定谁先谁后。我认为这是生产上更可控的形态 —— 点对点协商虽然听起来更「智能」，但可观测性和可调试性会崩。

**【项目证据】**
- agents/supervisor.py（图组装 + 条件边，四角色）
- agents/content_gen/、customer_service/、document/（角色人格与上下文各自独立）

**【可能追问】一个 Agent 加工具不也能做？为什么拆四个？**
答：因为四类任务的上下文需求、输出契约、失败模式完全不同 —— 客服必须只依据知识库不能编，文案要创作自由度，分析要拆解和并行。塞进一个 prompt 会互相污染。但我会主动说代价：多 Agent 换来延迟和 token，简单任务不值得。

**【状态】** ✅

## 第 11 题｜说说 Single-Agent 和 Multi-Agent 的设计方案？

**【开口第一句】**
判断标准不是「哪个更先进」，而是**上下文是否需要隔离、任务能不能并行**。

**【60 秒口播】**
**Single-Agent**：一个循环 + 全量工具。优点是简单、便宜、链路短（一次 LLM 调用能覆盖的就不该拆）；缺点是职责靠 prompt 软约束，工具一多就乱调，长任务上下文会被塞爆。

**Multi-Agent**：职责隔离 + 并行 + 可观测。代价是延迟变长、token 变多、调试变难（一次请求跨多个组件）。

**我在项目里的做法是「按需分层」**：
- 客服、内容这类**单跳任务**就用单 Agent（一个角色 + 自己那几个工具）；
- 分析类**多维度任务**才拆：planner 拆 2~5 条、executor 并行、synthesizer 综合；
- 而且 executor 的工具范围按**角色**收窄：子任务拿「分析角色」的 5 个数据工具（不是全部 10 个）—— 既省 token，也让「职责隔离」从 prompt 软约束变成**代码硬约束**；跨角色的工具（写文件、生成文案）根本不在 schema 里。

**【项目证据】**
- 单角色链路：service_node / content_node / document_node（各一个角色 Agent）
- 多角色链路：planner → executor(gather) → synthesizer
- 角色范围：executor.py 用 registry.subset_scope("analysis")（范围定义在 registry.TOOL_SCOPES，跨角色才拦）

**【可能追问】什么时候你**不**会上 Multi-Agent？**
答：任务单跳、上下文能塞下、或者对延迟极其敏感时。我的客服链路如果拆成「意图 → 检索 → 回答」三个 Agent，只是徒增两次 LLM 调用，没有任何质量收益。

**【状态】** ✅（能说出「什么时候不该上」才是真懂）

## 第 12 题｜Agent 记忆压缩通常有哪些方法？

**【开口第一句】**
常见四类：滑动窗口、摘要压缩、分层摘要、关键信息抽取。**我目前主要用第一类和第三类的简化版。**

**【60 秒口播】**
- **滑动窗口**：只保留最近 N 轮。我的实现是 8000 字预算，超了从最旧的**整条**丢 —— 不截半条，避免消息语义被劈开。
- **摘要压缩**：把旧对话总结成一段话再塞回上下文，省 token 但会丢细节（而且摘要本身要花一次 LLM 调用）。
- **分层摘要**：近期保留原文、中期用摘要、远期只留要点/事实。
- **关键信息抽取**：把长对话抽成结构化事实存进长期记忆。**我做的就是这个** —— 每轮后台提炼 semantic/episodic 记忆，之后按语义召回 top 3，而不是把整段历史塞进 prompt。

**取舍**：我选的路线是「**历史窗口 + 结构化记忆**」，而不是「摘要旧对话」。原因是我的场景要的是「这个运营负责什么、关注什么」这类稳定事实，抽成结构化记忆比压成一段散文更好召回、也更好删改。另外还有一处截断：上传文档注入时截 6000 字（DB 仍存全文），报告喂给记忆提炼时截 1600 字。

**【项目证据】**
- MAX_HISTORY_CHARS = 8000（整条丢策略）
- MAX_DOC_CHARS = 6000（文档截断 + 标注原文字数）
- 结构化记忆：long_term_memories + 语义召回 top 3

**【状态】** 🟡（概念要能报全四类，然后说清「我选了哪条路、为什么」）

## 第 13 题｜为什么有时候选择「手搓」Agent，而不是用成熟框架？

**【开口第一句】**
为了吃透机制。我**先用 LangGraph 做过 demo**，再自己写了一个 48 行的状态图引擎 —— 但生产我会选成熟框架。

**【60 秒口播】**
自写的收益：
1. **必须想清楚状态怎么传**：我的 state 就是一个 dict，节点读写都是它，条件边用同步 router 决定下一步 —— 这三件事想明白之后，框架的黑盒就变成透明的了；
2. **可控性**：我要在节点级做降级（预算耗尽时保住已完成结果出报告）、在 LLM 层做全局预算，这些在框架里要绕；
3. **调试成本低**：没有框架抽象层，出问题直接看栈。

选择框架的场景：需要**持久化执行**（断点续跑）、需要多人协作、需要生态里的现成组件（各种向量库、观测平台）。我的判断是：**学习和做小项目可以手搓，生产要算维护成本**。

**【项目证据】**
- core/agent/base.py（48 行：节点注册、普通边、条件边、异步兼容）
- 项目里的降级与预算：supervisor.py + core/llm/budget.py

**【可能追问】你那 48 行有什么做不到的？**
答：缺持久化与断点恢复（interrupt 只在数据结构上预留了、没实现）、缺并行分支的 join 语义、缺可视化。这些正是框架的价值，我不装。

**【状态】** ✅（能上能下，是加分项）

## 第 14 题｜如何赋予 LLM 规划能力？

**【开口第一句】**
三步：给它结构化的输出约定、给它明确的硬规则边界、然后**把它的脏输出洗干净再用**。

**【60 秒口播】**
1. **输出约定**：要求只输出 JSON 数组，格式是 id / task / tool_hint 三个字段；
2. **硬规则**：2~5 条、互相独立、一条只配一个工具、需要多工具就拆条 —— 这些不是「建议」，是必须遵守的边界，因为下游按这个假设写代码；
3. **容错三层**：剥掉 markdown 代码块 → json.loads 包 try → 解析失败兜底成「把原始目标当单任务」，保证流程不会因为模型输出格式崩掉；
4. **结构校验（关键）**：解析出来后还要洗一遍 —— id 去重（防下游 dict 塌缩丢结果）、缺 task 丢弃、**编造的工具名清空**、超过 5 条截断；
5. **注入事实**：LLM 没有时钟感，会瞎猜日期（我踩过：让它查「本周」，它猜了 2023 年，结果全 0），所以 prompt 里显式注入今天日期，并要求相对时间先换算成具体日期再调工具。

**【项目证据】**
- agents/planner.py：prompt 硬规则 + 解析 + 结构校验
- 同款容错在 intent_classifier（意图分类）和记忆提炼器里都有

**【可能追问】为什么不让模型自己决定拆几条？**
答：它确实自己决定（2~5 由它选），但**上限和下限由代码兜**：超过 5 条截断（成本可控），全部无效就降级成单任务（流程不崩）。

**【状态】** ✅

## 第 15 题｜讲讲 Agent 的反思机制？为什么要用反思？具体怎么实现？

**【开口第一句】**
反思是让 Agent 对产物做自我批评再改一轮。**说实话，我项目里没做这一步** —— 但我把它换成了另一种更可控的形式，并且想清楚了原因。

**【60 秒口播】**
反思的一般实现是：主 Agent 产出 → 一个 critic 角色按标准挑毛病 → 主 Agent 按批评重做，循环若干轮。收益是质量提升，代价是 token 翻倍、而且**模型自评容易自我肯定**（同一个模型很难批评自己的输出）。

**我的替代方案是「证据触发的 replan 回路」**：让 synthesizer 判断「手上的子任务结果是否足以回答原始目标」，不足就回 planner 补一轮（最多一次）。区别在于：**反思的触发条件是客观证据（数据缺没缺），不是模型主观感受**。

**另外我已经有一个「自动 critic」了**：我的编排层评测里有一项「报告数字有据率」—— 检查报告里出现的每个数字，能不能在子任务结果里逐字找到。**这就是针对「报告编数」这一最危险失败模式的自动检查**，比让模型自评更客观。

**【项目证据】**
- 未实现：反思/ critic 角色
- 替代与现状：synthesizer 的判定 + replan（设计完成、待实现）；agent_eval.py 的数字有据率判据（已实现并在用）

**【可能追问】那为什么不干脆现在补上？**
答：因为反思的收益要在「质量瓶颈是推理错误」时才明显；我现在的瓶颈更多在**工具覆盖和拆解粒度**上，先补这些 ROI 更高。这也是我用评测数据做的判断，不是拍脑袋。

**【状态】** ❌（按「诚实 + 替代方案 + 为什么」讲；这三步讲完反而加分）

## 第 16 题｜如何设计多 Agent 的协作与动态切换机制？

**【开口第一句】**
分两半答：**协作我做了**（共享 state + 结构化契约），**动态切换我只做了一半**（单意图单路由，还不能同时分派多个角色）。

**【60 秒口播】**
**协作机制**：
- 角色之间不直接对话，通过 state 交换产物：planner 写的 plan（每条含 id / task / tool_hint）就是给 executor 的契约；executor 把结果按 id 写回 results，synthesizer 读 results；
- 契约是**结构化**的，不是自然语言 —— 所以能校验（id 唯一、工具名合法）、能并行、能序列化；
- 失败也有契约：某个子任务失败就写入「该子任务失败：原因」，综合器看到的是结构化降级信息，而不是缺一块。

**动态切换机制**：
- 我现在是**一次分派**：意图分类选一条链路，之后不再改变角色。对「单一意图」的问题够用；
- 缺口是**跨角色任务**：比如「分析这周数据并写成周报存下来」需要 analysis + document 两个角色，现在只能做一半；
- 升级路径很清楚：让编排者拿到第一轮结果后再决定是否再派一个角色（也就是把「路由一次」改成「可重入的调度」），并在状态里记录「哪些角色已经跑过」避免重复。

**【项目证据】**
- 协作：supervisor.py 的 state 流转（plan → results → report）+ 事件流
- 动态切换：intent 的 add_condition_edges（一次性路由）

**【状态】** 🟡（前半强、后半诚实讲缺口和升级路径）
