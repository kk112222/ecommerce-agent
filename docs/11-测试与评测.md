# 11 · 测试与评测

> 前九章讲的是**怎么把它建起来**，这一章讲**怎么证明它真的建对了**。
> 一个"能跑起来"的系统和一个"能讲清楚为什么它是对的"的系统，中间隔着的就是这把尺子。

---

## 本章目标

读完这一章，你会明白：

1. `tests/`、`scripts/smoke_*`、`scripts/verify_*`、`scripts/*_eval.py` 这四类东西各管什么，为什么不能合成一种
2. 151 个用例是怎么做到**不联网、不读真库、不写真文件**的
3. "测试"和"评测"的区别 —— 一个防回归，一个出数字
4. 一套可以复跑的评测地图：改代码前后各跑一次，**用数字说话，而不是"我感觉变准了"**

## 一、四类东西，别混着用

项目里跟"验证"沾边的脚本有几十个，但它们其实是四种完全不同的东西：

| 类别 | 位置 | 有断言？ | 要真 LLM？ | 要停后端？ | 干什么用 |
|---|---|---|---|---|---|
| **自动化测试** | `tests/` | ✅ | ❌ 假 LLM | ❌ | 防回归，改代码后必跑 |
| **冒烟脚本** | `scripts/smoke_*.py` | ❌ 只打印 | ✅ | 看情况 | 手工看一眼"链路通不通" |
| **验证脚本** | `scripts/verify_*.py` | ✅ | 看情况 | 看情况 | 端到端验一个具体功能 |
| **评测脚本** | `scripts/*_eval.py` | ✅ | ✅ | 常需要 | **出数字**，改检索/改编排前后做 A/B |

这个划分不是洁癖，是踩出来的：

- **冒烟脚本没有断言**，所以它永远"通过"。它只能回答"跑没跑起来"，不能回答"对不对"。
  项目里 `verify_document_agent.py`、`verify_tool_args.py` 的核心断言**后来都搬进了 `tests/`** ——
  因为一个没有断言的脚本，放进 CI 里等于没有。
- **评测脚本和测试脚本目的相反**：测试是"给定输入，结果必须等于某个值"（二值）；
  评测是"给定一堆输入，算一个比率"（连续）。前者防回归，后者**指导优化方向**。
  把两者混在一起写，最后就是既不能当回归用、数字也没法对比。

跑法：

```bash
uv run pytest                       # 151 个用例，全程离线，不需要 .env
```

> `pyproject.toml` 里配了三件事，都是为了让测试好写：
> `testpaths = ["tests"]`（`scripts/` 里的冒烟脚本不算测试）、
> `asyncio_mode = "auto"`（async 测试不用每个都挂 `@pytest.mark.asyncio`）、
> `pythonpath = ["."]`（让 `tests/` 里能 `import backend.*`，等价于运行时那句 `PYTHONPATH=.`）。

## 二、测试为什么能离线跑：01 章埋的伏笔在这里兑现

整份测试套件**不联网、不读 `.env`、不碰 `data_v3.db`、不写 `outputs/`**。能做到这一点，全靠一个 27 行的文件：

```python
# tests/conftest.py
class FakeLLM(BaseLLM):
    """按预设脚本依次返回；脚本用尽后返回 default。记录每次收到的 messages 便于断言。"""

    def __init__(self, responses=None, default: str = "（假回复）"):
        self._responses = list(responses or [])
        self.default = default
        self.calls: list[list] = []          # 每次 chat 收到的 messages 快照

    async def chat(self, messages, tools=None, temperature=0.7) -> LLMResponse:
        self.calls.append(list(messages))
        if self._responses:
            r = self._responses.pop(0)
            return r if isinstance(r, LLMResponse) else LLMResponse(content=r)
        return LLMResponse(content=self.default)

    async def chat_stream(self, messages, tools=None, temperature=0.7):
        self.calls.append(list(messages))
        for chunk in ("假", "流式"):
            yield chunk
```

它继承 `BaseLLM`，所以它就是一个合法的 LLM。把它塞进 `Planner(llm)`、`ReActAgent(llm, registry)`、`ProfileExtractor(llm)`，
**整条 Agent 链路就原地跑起来了**，不花一分钱 token，结果还完全确定。

这就是第 01 章"依赖倒置"的回报。反过来想：如果当初 Agent 里写的是
`from backend.core.llm.qwen import QwenLLM` 然后 `self.llm = QwenLLM()`，
今天这 151 个用例一个都写不出来 —— 你得联网、得花钱、得忍受 LLM 每次输出都不一样。

> 所以"依赖倒置"不是设计模式课上的名词。它的真实收益是：**这一层能被替换，这一层就能被测试。**

## 四、两个写测试的手法

### 4.1 在边界上打洞：`monkeypatch` 换掉外部世界

记忆层是最难测的部分：它同时依赖 SQLite、Qdrant 和 LLM 三样东西。做法是把**这三样全部换成假的**：

```python
# tests/test_memory_merge.py
@pytest.fixture
async def memdb(monkeypatch):
    """内存 SQLite + 假向量库；返回 (sessionmaker, 假 qdrant 记录器)"""
    engine = create_async_engine(
        "sqlite+aiosqlite://",
        poolclass=StaticPool,                      # 内存库必须共用同一条连接，否则每次连接都是空库
        connect_args={"check_same_thread": False},
    )
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all,
                            tables=[LongTermMemory.__table__, UserProfile.__table__])
    monkeypatch.setattr(store, "AsyncSessionLocal",
                        async_sessionmaker(engine, expire_on_commit=False))

    # 假 qdrant：points 就是"库里的点 id 集合"，能真实反映删/插的效果
    state = {"points": set(), "upserted": [], "deleted": [], "hits": []}
    ...
    monkeypatch.setattr(store, "search_similar", lambda *a, **k: state["hits"])
    yield state
    await engine.dispose()
```

三个值得抄的细节：

1. **`poolclass=StaticPool`** —— 内存 SQLite 的经典坑：不共用同一条连接的话，每次新连接都是一个**空库**，
   你会看到"刚插进去的行不见了"。这个坑不踩一次很难想到。
2. **假 Qdrant 用一个 `set()` 存点 id** —— 不是简单地 `return None` 糊弄过去，而是**真的维护一个集合**。
   所以"作废一行时向量有没有跟着删掉"这种事，测试能真的验出来。
   假实现的最低标准是：**它的状态转移要和真实现一致**。
3. **`monkeypatch.setattr(store, "search_similar", ...)`** —— 打的洞打在 **`store` 模块的引用上**，
   不是打在 `qdrant_client` 上。因为 `store.py` 是 `from ... import search_similar` 进来的，
   换源头没用，得换它自己手里那个名字。这是 Python mock 最常见的翻车点。

### 4.2 断言"行为"，不断言"实现"

`FakeLLM` 里那行 `self.calls.append(list(messages))` 才是精髓：它让测试能问
**"你到底给模型看了什么？"**，而不是只能问"最后输出对不对"。

```python
async def test_user_message_carries_goal(...):
    # 断言的是"目标被放进了 user 消息"，而不是"分类结果等于 analysis"
```

同类手法还有 `test_agent_eval_judges.py` 里的 `RecordingRegistry`（继承真实 `ToolRegistry`，只加录制），
让测试能断言**"这个子任务到底调了哪几个工具"**。

判断标准很简单：**你对实现的直觉改了、但行为没变时，测试该不该红？不该。**
例如把"两条消息合成一条"这种重构，断言 `calls` 结构的测试就会红 —— 这种断言写的时候就要克制。

## 五、评测：把"感觉变好了"变成数字

测试回答"坏没坏"，评测回答"**好了多少**"。

### 5.1 先解决"尺子有没有刻度"

第一版评测集我用的是**常识性条款**（"退货要运费吗"这类）。结果：

```
Recall@5 全部 100%，MRR 顶格
```

看着满分，其实**毫无信息量** —— 这种问题 BM25、向量、甚至模型预训练全都能答对，
四种策略全满分，说明这把尺子**量不出任何差别**。

于是换了一条规则：

> 真值只选**预训练背不到**的虚构条款（运费多少、包邮门槛、保修天数）。
> 答错 = 真没检索到，不可能是模型自己会的。

这一条是整个评测体系的地基。它同时给了三件事：
① 评测有区分度；② 幻觉可判定（模型答出"保修 1 年"而库里没有，就是编的）；
③ 后面所有的**扰动测试**才有了可能（见 5.4）。

### 5.2 第一层：切分 —— 一次"假满分"的发现

粗切（按固定长度切）时语料只有 **7 块**，检索评测全满分。

改成结构化切分（`##` 标题强制开新块、段落不腰斩、标题块不加重叠）后变成 **32 块**，
**梯度立刻出来了** —— 向量单跑的 Hit@1 掉到 51%。

这一正一反构成了一条完整证据链：

```
粗块 → 顶格    说明评测没区分度，不是检索做得好
细块 → 有梯度  说明"切分决定召回上限"是真命题
```

> （32 块是那一轮语料的数字。后来又补了会员/发票/账户/促销/跨境五个来源，块数更多了；
> 但"切分粒度决定评测有没有区分度"这个结论不变。）

### 5.3 第二层：检索 —— 四路 A/B

`scripts/rag_eval.py` 对 51 条 golden question 跑四种策略，看真值块在不在 top-5：

- **BM25**（纯字面）
- **向量**（纯语义）
- **混合 RRF**（`_rrf_fuse(bm25, vector)` 取 top5，不精排）
- **混合 + 精排**（`retriever.search()` —— **线上客服走的就是这个函数**）

| | BM25 | 向量 | 混合 RRF | 混合 + 精排 |
|---|---:|---:|---:|---:|
| Recall@5 | 96% | 63% | 100% | 100% |
| Hit@1 | 73% | 51% | 82% | **90%** |
| MRR | .819 | .565 | .894 | **.942** |

（51 题，2026-09-05）

三个结论，也就是面试要讲的三句话：

1. **向量单跑最弱**（Hit@1 只有 51%）—— 条款/数值这类"精确关键词"问题，BM25 反而强。
   **单路各有盲区**，这才是做混合的动机，不是"大家都说混合好"。
2. **混合 RRF 把 Recall 拉回 100%** —— RRF 不比较分数绝对值、只比排名位次，
   BM25 和向量**谁对都救得回来**，1+1 > 2。
3. **精排把 Hit@1 从 82 → 90** —— Cross-Encoder 对 top-10 逐对重排。
   结论：**精排的增益通常大于盲目加大召回**。生产路径 51/51 全对。

最后一行是这个脚本的设计要点：**第四条策略必须是生产路径本身**，而不是"评测专用的理想路径"。
否则你测的是一个不存在的系统。

脚本末尾自己把读法打出来了：

```
怎么读：BM25→向量 是两种召回方式的差距；向量→混合RRF 是融合收益；
混合RRF→混合+精排 是 rerank 的收益。改任何检索逻辑前后各跑一次对比数字。
```

### 5.4 第三层：生成端（隔离式）—— 扰动测试

检索评测只能证明"对的块被捞回来了"，证明不了**"模型真的在看这些块"**。
模型完全可以一边把资料喂给它、一边靠预训练里的常识答 —— 这叫 **bypass**。

`scripts/rag_quality_eval.py` 用两个扰动把它逼出来：

| 扰动 | 做法 | 期望 | 不符合说明什么 |
|---|---|---|---|
| **V1 换值** | 把资料里某条款的数值改掉，问原问题 | 回答**跟着新值走** | 还答旧值 → 在靠记忆，没真看资料 |
| **V2 清空** | 资料留空，问原问题 | **答不出 / 说资料里没有** | 还能答出条款 → 纯幻觉 |

再加上一个 **judge 忠实度**：用独立 prompt 当裁判，判"回答里每个事实性陈述能不能在资料里找到出处"。
最后一组是"故意只给无关块"，好模型应该说"资料里没有"，自信编条款就是幻觉。

设计上有两个刻意的选择：**只调对话 LLM、完全不碰 Qdrant**，
所以这个脚本**后端不用停**，可以跟别的评测并行跑（这一点在第六节会显得很重要）。

### 5.5 第四层：生成端（端到端）—— 整条链路的答案

5.4 是"隔离式"的：手工把 context 拼好直接问模型。它答不了另一个问题：
**整条链路交付出来的答案**（ServiceAgent → RAGTool → 混合检索 → 精排）忠实不忠实。

`scripts/rag_answer_eval.py` 补这一层，与 `rag_eval.py` **共用同一份 GOLDEN 真值集**，三个指标：

| 指标 | 判法 | 为什么这么判 |
|---|---|---|
| ① 事实命中率 | LLM 判：答案有没有答到真值那条事实 | 检索层已测"片段召回没召回"，这里测"答没答对" |
| ② 忠实度 1-5 | LLM 判：每个事实性陈述能否在**召回片段**里找到依据 | 依据用的是生产路径真正喂给 LLM 的那几块（录制代理截获），不是事后补的 |
| ③ 数字越界 | **确定性**：答案里的数字逐个在召回片段里找字面出现 | 幻觉最典型的形态，不看 LLM 脸色 |

③ 的取舍要讲清：它**只筛不判**。匹配刻意偏松（子串而非词），所以"10000 写成 1 万"不会误报；
真正会误报的是**答案自己算出来的数**（8 元 + 18 元 → 26 元）。
所以它输出的是"待人工复核"清单，不是扣分项 ——
**一条确定性规则的正确用法是缩小人工复核的范围，不是替人下结论。**

它还有一版更硬的扰动：**不动真实知识库**，把扰动语料重新向量化写进临时集合，
只在本进程内把向量检索指过去，然后**基线对照**：

```
基线（真实知识库）声明的包邮门槛：'99'
扰动后声明的包邮门槛：'199'
结论：门槛从 99 → 199，答案跟着知识库变了 → 确实在检索，不是背预训练常识 ✅
```

### 5.6 第五层：编排 —— 那两把尺子量不到的地方

RAG 的评测全都**不看 supervisor / planner / executor**。而多 Agent 的失败恰恰发生在那一层：

- 意图分错链路（该查知识库却去查数据库）
- 拆解漏维度（只查了销售就下"营业额为什么低"的结论）
- 子任务不调工具，纯靠 LLM 空想
- 报告里出现了子任务结果里没有的数字

这些**在 RAG 指标上完全看不出来**。所以有了 `scripts/agent_eval.py`，
思路是：多 Agent 的输出没有唯一正确答案，那就拆成**能自动判的确定性指标**。

| 指标 | 判法 |
|---|---|
| ① 意图路由准确率 | 期望链路 vs 实际链路 |
| ② 工具调用召回 / 精确 | 期望工具集合 vs registry 实际被调用的（召回抓"该查没查"，精确抓"多调乱调"） |
| ③ 必要维度覆盖率 | 该覆盖的方面有没有出现在证据里 |
| ④ hint 合规率 | planner 有没有守"一条子任务一个工具"的契约 |
| ⑤ 报告数字有据率 | 报告里的数字能否在子任务结果里逐字找到（复用 ③ 的 `numeric_overflows`） |
| ⑥ 成本 | 每个 case 一个 `UsageBudget`，记 LLM 调用次数 / token / 耗时 |

它最漂亮的地方是"**零侵入**"：生产代码一行不改，三个观察点全是现成的 ——
事件流（`build_supervisor(on_event=...)` 本来就有 intent/plan/subtask/report）、
工具调用（`RecordingRegistry` 继承 `ToolRegistry` 只加录制）、
入口（直接 `graph.invoke(合成 state)`，不碰 SQLite、不写长期记忆）。

### 5.7 为什么这五把尺子不能互相替代

| | 检索 A/B | 生成端·隔离 | 生成端·端到端 | 编排 |
|---|---|---|---|---|
| 走检索栈 | 只测检索本身 | ✗ 手工拼 context | ✓ 完整链路 | ✗ |
| 能抓到的 | 片段召回对不对 | 模型看没看资料 | 交付的答案忠实不忠实 | 路由/拆解/工具调用 |
| 抓不到的 | 模型怎么用资料 | 检索选错块、工具没被调 | 意图分错链路、漏维度 | 答案本身对不对 |
| 前置 | 停后端 | **不用停** | 停后端 | 不用停（不碰 DB） |

一句话：**每一层只能证伪它自己那一层的错。**
把这四张表拼起来，才构成"我知道我的系统哪里可能坏、以及我怎么知道它没坏"。

## 六、评测脚本里的工程细节

这些细节不写进简历，但**写脚本的时候一定会撞上**：

**① Qdrant 本地模式是单进程独占**

任何要读 `qdrant_data/` 的脚本，跑之前**必须先停后端（8000 端口）**，否则直接冲突。
应对办法分三种：能并行跑的就不碰 Qdrant（`rag_quality_eval.py`）、
要写的就写进临时集合（`rag_answer_eval.py` 的 `kb_perturb_test`）、
实在要读的就停后端（`rag_eval.py`）。脚本说明里都会写清前置条件。

**② golden 集要能自检**

`rag_eval.py` 开跑前先检查每条真值片段在语料里命中几个块：

```python
n = sum(1 for t in texts if snip in t)
if n == 0:
    print(f"  [警告] 片段查无此块（可能 KB 没重建/已过期）：{q} → {snip!r}")
elif n > 1:
    print(f"  [提示] 片段命中 {n} 个块（真值有歧义）：{q} → {snip!r}")
```

`n == 0` 说明**知识库没重建**（评测跑的是旧语料，数字全是假的）；
`n > 1` 说明**真值有歧义**（哪个块算命中说不清）。
评测跑出漂亮数字时，先看这两类警告 —— 它们比结果重要。

**③ 90 秒超时 + 并发闸门**

judge 那段一开始是串行跑的，卡了六分钟。现在每个请求包 `asyncio.wait_for(90s)`，
外面再套 `Semaphore(4)` 限并发。

**④ judge 输出强制单行 JSON**

`{"faithful":…,"hallucinate":…,"reason":…}`，用正则抽 JSON 就能解析，
不用处理多行/代码围栏/前后废话。**让 LLM 的输出格式尽量难出错**，比写容错代码便宜。

## 七、这一章踩过的坑

**坑 1：粗块假满分**

第一版评测全 100%，我差点以为检索做完了。真相是**评测集和切分粒度双重没区分度**。
→ 教训：**评测跑出满分时，第一反应应该是"尺子坏了"，不是"我做对了"。**

**坑 2：扰动断言用字面短语，被 markdown 加粗判成"没走检索"**

第一版写的是 `"满 199 元包邮" in answer`。实际回答是"满 **199 元** 即可享受包邮"——
中间插了加粗符号、还改写了措辞，断言直接判失败。

→ 改成从回答里**抽语义点**（正则抽"满 N 元…包邮"的门槛数字）再与基线比对。
顺带发现：回答里另一处"不满 **99** 元"是**另一个没被扰动的档位**，本来就该照实留着 ——
所以断言里也不能简单写"答案不含 99"。

**坑 3：继承注册表时没重写 `subset()`，一条调用都记不到**

`RecordingRegistry` 继承 `ToolRegistry` 只加了录制。但 executor 会给子任务**收窄工具集**，
而父类的 `subset()` 返回的是**新建的 `ToolRegistry`**（类名写死的），
于是子任务的调用**一条都记不到**，指标全是零。

→ 教训：**继承一个返回 `self.__class__` 的地方被硬编码成父类名的类，是个隐藏地雷。**

**坑 4：数字越界会误报"答案自己算出来的数"**

8 元 + 18 元 → 26 元，26 在召回片段里找不到，被标成"疑似幻觉"。

→ 这个指标没改成"扣分"，而是**改成输出复核清单**（见 5.5）。
一条确定性规则做不到的事，不要硬让它做。

**坑 5：一个"从没被走到过的行"，让 150 个用例全绿也没拦住**

```python
async def _user_extract_lock(user_id):     # 普通协程：内部 return 一把锁
    ...
async with _user_extract_lock(user_id):    # 调用处要的是异步上下文管理器
```

拿到的是 coroutine，直接 `TypeError`。而提炼跑在**后台任务**里，异常被兜底函数接住只写一行日志
（正是 09 章讲的静默失败）——用户体验是"记忆时有时无"，真相是**一次都没成功过**。

**发现方式很土**：为了截 README 的图把项目跑起来，看后端日志才撞见的。**测试没撞见，是因为它从来没有真跑过这条路**：

- 这个文件里其余用例都把 `_extract_and_save` 整个 `monkeypatch` 掉了；
- 唯一真调它的 `test_trivial_goals_are_skipped` 走的是"寒暄"早返回，
  **在加锁那一行之前就 `return` 了** —— 差一行。

→ 教训：**"这个函数被调用过"和"这个函数的关键路径被执行过"是两回事。**
一个函数有多个出口时，用例很容易全部落在最前面那个出口上。
修法是补一条**真跑主路径**的用例（而不是再加一条 mock 用例）。

## 本章小结

- 四类脚本**别混着用**：测试防回归、冒烟看通路、验证验功能、评测出数字
- **全绿不等于没问题**：一个 bug 可以正好落在"所有用例都没走到的那一行"上（坑 5）
- 151 个用例能离线跑，靠的是 **`BaseLLM` 这层抽象**（01 章的伏笔）
- 打洞要打在**模块引用**上，假实现要**保持状态转移一致**
- 评测的地基是**有区分度的真值集**：只选预训练背不到的虚构条款
- 五把尺子各测一层：**切分 / 检索 / 生成·隔离 / 生成·端到端 / 编排**，谁也替代不了谁
- **满分先怀疑尺子**；确定性指标只筛不判

## 练手挑战

**挑战一（必做）：给一个没有测试的分支补测试**

`executor` 的子任务结果为空时会兜底成一句"未返回结果"（05 章的三层隔离里提到过），
但 `tests/` 里没有直接测这个兜底的用例。用 `FakeLLM` 造一个"不返回任何内容"的响应，把这个分支覆盖掉。

**验收**：`uv run pytest tests/test_planner_executor.py` 通过；把源码里那句兜底删掉，**测试要变红**
（不能变红的测试等于没写）。

**挑战二（推荐）：自己跑一次检索 A/B，拿到属于你的数字**

先停掉后端，然后：

```bash
uv run python -m scripts.rag_eval
```

把四策略的表和本文 5.3 的数字对比。然后**改一个参数再跑一次**（比如把 `CHUNK_SIZE` 从 200 改成 400，
或把 RRF 的 `k` 从 60 改成 10），看指标往哪边动。

**验收**：能说出"我改了 X，Hit@1 从 A 变成 B，我判断原因是 Y"。
数字和本文不一样没关系（语料已经变过），**关键是有没有对照**。

**挑战三（加分）：给"数字越界"加一条豁免规则**

现在的误报都是"答案自己算出来的数"。试着加一条：如果某个数字**能由召回片段里的两个数字通过四则运算得到**，
就把它从"待复核"降级成"疑似派生值"。

**验收**：`tests/test_rag_answer_eval.py` 里有个 `test_derived_number_is_false_positive`
记录的正是这个误报场景，让它的断言从"被标记"变成"被标记但归类为派生"，
并且**原有 7 个用例全部仍然通过**。
