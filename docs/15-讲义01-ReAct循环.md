## 1. 先建立直觉：没有 Agent 的世界长什么样

你自己的 LLM 抽象层里就有这个能力：给它一段对话，它回你一段文本（backend/core/llm/qwen.py 的 chat 方法）。

问题在于：**它只会说话，不会查数据。** 你问"这周充电宝卖得怎么样"，它没有你的数据库，只能编一个看着合理的数字。

想让它能查数据，两条路：

- **思路 A（工具当装饰）**：程序先查好数据，塞进 prompt，再让它总结 —— 决策权在你手里，它只是"会写字的嘴"。
- **思路 B（Agent）**：把工具的说明书一起给它，**让它自己决定查什么、查几次、什么时候停**。

思路 B 更强，但立刻带来四个新问题：**它可能不用工具、乱用工具、用错参数、或者永远停不下来。**

**ReAct 就是为这四个问题设计的循环结构。**【你写的】

---

## 2. 一句话定义（背下来）

    LLM 说"我要调 X(参数)"  →  程序真的去调 X  →  把结果塞回对话
         ↑                                                    ↓
         └──────────── LLM 看着结果，决定下一步 ←──────────────┘
                          直到它不再要求调工具 → 输出最终答案

要能说出的三个关键词：**Thought / Action / Observation 三元组**、**工具结果回灌上下文**、**循环终止条件**。

## 3. 逐段读代码（simple_agent.py）

### 3.1 开头那个小函数：把"错误"也喂回去（第 7-15 行）【后来加的】

    def _result_text(result) -> str:
        if result.success:
            return str(result.data)
        return f"调用失败：{result.error}"

工具执行完返回一个 ToolResult（success / data / error）。这个函数决定"往对话里回灌什么"。

**看点全在失败分支上。** 早期版本是直接 str(result.data)：失败时 data 是 None，模型在对话里只看到一个光秃秃的 None —— 它不知道错在哪，下一轮只能瞎猜或放弃。

现在把 error 一起喂回去，模型看到的是「调用失败：调用 query_sales 的参数 start_date 类型不对，应为字符串」这类可读信息，下一轮自己就把参数改对了。

**这是 Agent 韧性的最小实现，也是一句好话术：错误不是终点，是下一轮的输入。**

### 3.2 三个成员（第 21-24 行）【你写的】

    def __init__(self, llm, registry, max_rounds: int = 10):
        self.llm = llm                  # 谁做决策（BaseLLM 抽象，不关心是千问还是 DeepSeek）
        self.registry = registry        # 能调哪些工具（工具契约层，负责校验与隔离）
        self.max_rounds = max_rounds    # 循环上限，防止无限烧钱

llm 是**抽象类型**：这就是第 01 章那个依赖倒置在 Agent 里的落地 —— 换模型，这个类一行不用改。

### 3.3 主循环（第 30-53 行）：五个动作

    for _ in range(self.max_rounds):
        response = await self.llm.chat(messages, tools=tool_specs)     # ① 问模型：下一步干啥
        if not response.tool_calls:                                    # ② 终止条件
            return response.content
        messages.append(Message(role="assistant", content="",          # ③ 记账：模型要调工具
                                tool_calls=response.tool_calls))
        for tc in response.tool_calls:
            result = await self.registry.execute(tc.name, **tc.arguments)   # ④ 执行
            messages.append(Message(role="tool", content=_result_text(result),
                                    tool_call_id=tc.id))               # ⑤ 结果塞回对话

**① tools 只是"说明书"，不是函数本体**【你写的】
tool_specs 是一串 JSON Schema（工具名 + 描述 + 参数结构）。模型只能"点名 + 给参数"，**执行权永远在程序手里**。被问到要主动说 —— 这是"工具调用安全"的边界。

**② 终止条件是"没有 tool_calls"**【你写的】
模型不再要求调工具，就说明它认为信息够了。**不用你判断"它答完了没"，它自己说停就停。**

**③ 为什么要把模型的 tool_calls 存进 messages？**【你写的】
这是 OpenAI 兼容协议的硬要求：**"请求调用"和"返回结果"必须成对出现**，缺一半下次请求会被 API 直接拒掉（400）。你在 qwen.py 的 _to_qwen_messages 里专门序列化 tool_calls 和 tool_call_id，就是为了这个。

**④ registry.execute 是不可靠输入的收口处**【后来加的，第 62-73 行】
这里的参数是 LLM 生成的，属于完全不可信输入。registry 统一兜了四类：工具名不存在 / 缺必填参数 / 多传或传错键名 / 工具本体抛异常 —— **四类一律不抛异常，而是返回模型能看懂的结构化错误**。
（这就是 3.1 那个函数能起作用的前提。原始版本这里是直接 execute，工具报错会穿透上来打死整个循环。）

**⑤ tool 消息必须带 tool_call_id**【你写的】
它是"这条结果对应哪次请求"的配对编号。模型一轮里可能同时要调三个工具，没有编号它分不清哪个结果对应哪个请求。

**循环用尽还没答**（第 52-53 行）：再调一次模型强制作答，注意**这次不传 tools** —— 否则它可能又要调工具，接着循环。

### 3.4 一个必问细节：messages 就是全部状态【你写的】

这个类没有全局变量、没有类属性，循环的全部"记忆"就是 messages 这个列表。两个推论：

1. **上下文会越来越长** → token 越来越贵（所以要上下文预算）；
2. **调试就像看日记** → 把 messages 打出来，就能看到模型每步"看到了什么、决定了什么"。

### 3.5 run_stream 与 run 的差别（第 55-94 行）【你写的】

- **工具阶段仍然非流式**：必须拿到完整 tool_calls（工具名 + 参数）才能执行，边流边解析是自找麻烦；
- **最终回复才流式**：这时不再需要工具决策，逐字吐给用户 → 前端打字机效果；
- 每个阶段 yield 一个状态事件（第 59、66、78、91 行）→ **这就是前端"活动流"的数据来源**。

## 4. 一次真实执行的消息序列（最重要的直觉，看三遍）

提问：**帮我看看充电宝最近卖得怎么样**（假设 planner 给这个子任务指定了 product_query）

    msg[0] role=system
      你是数据分析子任务执行者,今天是 2026-09-15。你被分配了一个明确的子任务…
      【建议优先使用】product_query（也可以调用其它数据分析工具交叉验证，例如查完销售再确认库存）。

    msg[1] role=assistant        ← 模型的第一次决策
      tool_calls=[ToolCall(id="call_1", name="product_query",
                           arguments={"keyword": "充电宝"})]
      （content 是空的：这一轮它只说"要调工具"）

    msg[2] role=tool  tool_call_id="call_1"    ← 程序执行完，把结果塞回来
      {'商品名': '充电宝', '分类': '数码', '单价(元)': 129.0, '库存': 8,
       '时间段': '不限 ~ 不限', '总销售额(元)': 4200.0, '订单数': 33}

    msg[3] role=assistant        ← 模型看着事实做总结，这一步没有 tool_calls
      "充电宝库存仅剩 8 件，已低于安全阈值；累计销售额 4200 元、33 单。"

循环在第 33 行的判断命中处结束，返回值就是 msg[3] 的内容。

**看懂这张图就看懂了 Agent**：第 1 条是模型的决策，第 2 条是程序的执行，第 3 条是模型基于**真实数据**的总结。所谓"Agent 比聊天机器人多的东西"，就是这三条之间的那个 while 循环。

（一个真实细节：executor 调用时**只传了一条 system 消息**，任务写在 system 而不是 user。被问"为什么"就答：子任务是一次性执行、不需要多轮对话语义，历史/画像/上传数据也一并拼在 system 里，保持单一入口。）

## 5. 三个取舍（追问重灾区）

**5.1 为什么不用 LangChain 的 AgentExecutor / LangGraph？**
"我先用 LangGraph 做过 demo，自写是为了吃透 state 传递和条件路由（核心只有 48 行）；**生产我会选成熟框架**，自己维护编排引擎不划算。"（能上能下，比一味吹自研强。对应映射表第 13 题）

**5.2 为什么错误回灌而不是抛异常？**
"抛异常=快速失败，适合'这轮对话已经没意义了'；回灌=给模型一次自我纠正的机会，适合**参数级错误**。我的分界线是：**工具级错误回灌，预算耗尽由上层降级** —— BudgetExceeded 被 supervisor 接住，把已经查到的数据照样出报告，而不是给用户一个 500。"【后来加的】

**5.3 max_rounds=10 的代价？**
最坏：一个子任务 10 轮 × 每轮多次工具调用，4 个子任务并行就是 40+ 次 LLM 调用。怎么兜：**预算卡在 LLM 层**（BudgetedLLM 装饰器），因为调用次数是循环内部攒出来的，Graph 节点看不见。【后来加的】

**5.4 追加一招（很加分）：工具集收窄**
executor 会把 registry 收窄成**分析角色**的子集（5 个数据工具）再交给 ReActAgent。**既省 token（每轮少传一半 schema），又防止子任务乱调**（写文件、生成文案的工具根本不在里面）。
（2026-09-16 调整：最早是"按 tool_hint 只给一个工具"，粒度绑错了层 —— 子任务要回答"一个问题"，天然可能要用多个工具；现在边界绑在**角色**上，tool_hint 只作"建议优先使用"的提示。）【后来加的】

## 6. 面试口播稿（90 秒，照着背）

> "ReAct 是把推理和行动交替放进一个循环，我的实现就三件事：
> 一是**决策** —— 把工具的 JSON Schema 一起传给 LLM，让它自己决定调哪个、调几次；注意工具只能点名不能执行，执行权始终在程序手里；
> 二是**回灌** —— 工具结果作为 tool 消息塞回对话，还要带 tool_call_id，因为 OpenAI 协议要求请求和结果成对出现；
> 三是**终止与兜底** —— 模型不再要工具就结束，轮次用尽就强制它总结。
> 有个细节我踩过坑：工具失败时**不能只回灌结果**，必须把错误也喂回去，否则模型只看到一个 None，下一轮没法自我纠正；现在我的 registry 会把它变成「参数 start_date 格式不对」这类可读反馈，模型下一轮就改对了。
> 另外 ReAct 的轮次是模型自己决定的，所以我在 LLM 层加了 token 预算，超限降级出报告而不是报错。"

## 7. 五个高频追问 + 答法

| 追问 | 怎么答 |
|---|---|
| 工具结果太长塞不下怎么办？ | 截断 + 只回传必要字段（我的工具返回结构化 dict 而不是长文本）；进一步是做摘要压缩 |
| 一轮里要调多个工具，怎么处理？ | 现在是 for 循环**顺序**执行；这里可以改成并发 gather —— 诚实说"目前顺序执行，是明确的优化点" |
| 怎么防止死循环 / 重复调用？ | 三重：max_rounds 上限、LLM 层 token 预算、子任务按角色收窄工具范围；检测侧目前只有日志 |
| ReAct 和 Plan-and-Execute 什么关系？ | **层次不同**：任务之间是计划-执行（planner 拆 2~5 条并行），子任务内部是 ReAct；两者配合而非二选一 |
| 模型说"做完了"但其实没调工具？ | 任务幻觉。三层防护：参数/名称错误必回灌、子任务空结果不进报告、评测里有"报告数字有据率"专筛编造的数字 |
