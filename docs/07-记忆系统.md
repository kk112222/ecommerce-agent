# 07 · 记忆系统

> 第 06 章解决了"**公共知识**"（政策文档人人一样）。
> 这一章解决"**这个人**"：他负责哪个类目、上周说过什么、他不关心什么。
> LLM 本身**无状态**——每一次调用都是失忆的，记忆得我们自己建。

## 本章目标

读完这一章，你会明白：

1. 三层记忆各存什么、凭什么分层
2. 会话历史为什么要**按整条丢**而不是截断
3. 记忆是**什么时候**产生的（为什么必须后台）
4. 语义画像的**增量合并**：三档相似度分别怎么处理

6. 召回怎么用"**相似度 × 重要性 × 新鲜度**"加权，以及为什么"召回"不该涨"重要性"
7. SQLite 和 Qdrant 两个存储怎么保持一致（**没有共享事务**）

## 一、先看痛点：没有记忆的 Agent 每次都是陌生人

同一个运营人员连聊三天，没有记忆时会发生什么：

| 用户说 | 期望 | 没记忆时 |
|---|---|---|
| "这个月男装卖得怎么样" | 知道他一直负责男装 | 每次都问"哪个类目？" |
| "刚才那个数据再算一遍" | 知道"刚才那个"指什么 | 完全不知道 |
| "我不想看转化率" | 记住这个否定 | 下次还给他推转化率 |

**这里其实是三种不同的记忆**，混在一起就做不好：

```
① 这一轮对话说过什么     → 会话历史（短期）
② 这个人是干什么的       → 语义画像（长期、稳定）
③ 上个月发生过什么       → 情景记忆（长期、会过期）
```

---

## 二、三层记忆总览

| 层 | 存哪 | 存什么 | 生命周期 |
|---|---|---|---|
| **会话历史** | SQLite `chat_messages` | 这一轮的对话原文 | 跟着会话走，**删会话一起删** |
| **语义画像** | SQLite `long_term_memories`（`kind=semantic`）+ Qdrant `user_memories` | 跨会话**稳定**的偏好：负责类目、关注 KPI、报告偏好 | 长期；被更新时作废旧版、保留行可审计 |
| **情景记忆** | 同表（`kind=episodic`）+ 同一个 Qdrant collection | 发生过的事：带时间的数值、新动向、待跟进、明确否定的方向 | **默认 30 天 TTL**，过期不再参与召回 |
| **兜底画像** | SQLite `user_profile` | 一句话偏好串 | 由语义行重算而来，**永远和长期记忆一致** |

两条设计原则贯穿全表：

**① 长期记忆存两处，但只有一个事实源。**

```
SQLite long_term_memories  ← 事实源（每行一条记忆：文本/类型/重要性/是否生效/向量点 id）
Qdrant user_memories       ← 只是"向量召回索引"
```

**为什么不在 Qdrant 里直接存文本就完了？** 因为你要做"**逐条管理**"：看列表、删单条、标作废、审计。向量库不擅长这些，SQLite 一行一条最方便。**把 Qdrant 降级成索引**，是这套设计的地基（第 7 节会看到它的回报）。

**② 语义和情景分开，因为它们的"正确行为"完全不同。**

| | 语义画像 | 情景记忆 |
|---|---|---|
| 例子 | "负责男装类目" | "男装转化率这周掉到 2%" |
| 新信息来了 | **要合并**（可能取代旧的） | **直接 append** |
| 会过期吗 | 不会 | **会**——"这周掉到 2%"过一个月就没参考价值了 |
| 读取方式 | 全量作为底子 + 召回 | 主要靠**向量命中** |

> 情景记忆的 TTL 注释写得很直接：*"'上周做了什么'过一阵就不再影响判断，不设 TTL 的话它会无限堆积、长期污染召回。"*

## 三、会话历史：预算怎么控

```python
MAX_HISTORY_CHARS = 8000

async def get_messages(sid: str, user_id: int, limit: int = 10) -> str:
    history = await load_messages(sid, user_id)
    recent = history[-limit:]
    lines = [f"{'用户' if m.role == 'user' else '助手'}: {m.content}" for m in recent]
    text = "\n".join(lines)
    # 超预算按整条丢（不砍半条），宁可少带几轮也别截断消息内容
    while len(text) > MAX_HISTORY_CHARS and len(lines) > 1:
        lines.pop(0)
        text = "\n".join(lines)
    return text
```

**关键点：超预算时按"整条消息"丢，不截断单条内容。**

对比一下两种做法：

| 做法 | 后果 |
|---|---|
| 截断文本（`text[:8000]`） | 最后一条消息被砍掉一半——**恰好是当前正在聊的这件事** |
| **丢整条**（从最旧的开始） | 丢掉的是很久以前的几轮，**最近几轮始终完整** |

对多轮对话来说，**"最近几轮完整"比"多带几轮但是残缺"重要得多**。

### 读的顺序有讲究

`chat.py` 里的顺序是**刻意排的**：

```python
# ① 读历史（在存当前消息之前）
history_text = await get_messages(sid, current_user.id)
# ② 读用户画像（长期记忆）
profile = await recall_user_memories(current_user.id, request.message)
# ③ 读该会话上传的文件数据
uploaded_data = await get_uploaded_docs(sid, current_user.id)
# ④ 存当前问题
await save_message(sid, current_user.id, "user", request.message)
```

**历史必须在存当前消息之前读**，否则这一轮的提问会在「历史」里出现两次（一次作为历史、一次作为 `goal`）。这种 bug 表现是"模型好像把问题重复理解了一遍"——很难从现象反推原因。

## 四、记忆什么时候产生：后台提炼

记忆**不能**在回复前生成（用户要多等一次 LLM 调用），也不能写进主流程（提炼失败不该让回复失败）。所以：

```python
await save_message(sid, current_user.id, "assistant", result)
_spawn(_extract_in_background(current_user.id, sid, request.message, result))
return ChatResponse(reply=result, ...)      # 用户已经拿到回复了
```

**回复先落库、先把响应返回，提炼在后台跑。**

### 4.1 原料是"整轮"，不是"用户的问题"

这是被外部评审指出后改的（注释里标为 M1）：

```python
# ② 整轮对话当原料（报告可能很长，截前 1600 字省 token）
conversation = f"用户：{goal_s}\n助手：{(reply or '')[:1600]}"
```

**为什么**：旧实现只喂 `用户：{goal}`，等于只看孤立的问题。但**稳定偏好藏在行为信号里**：

- 用户追问同一个方向 = **感兴趣**；
- 用户说"这个不用看了" = **不感兴趣**；
- 用户认可了某个口径 = 这个口径对。

这些信号**全在助手回答之后的反应里**，只看问题必然漏掉。所以提炼器现在一次看**问答对**。

### 4.2 一次调用产出两类

`ProfileExtractor.extract` 返回 `{"semantic": [...], "episodic": [...]}`：

```
semantic：把【已有画像】与【本轮新信息】合并成当前最完整的语义画像
episodic：本轮用户提到的数值/时间性事实/动作/新动向/待跟进 + 明确否定的方向
```

prompt 里有两条写法值得抄：

- **`去掉'该运营人员''用户'等主语前缀`**——因为每条会**当成检索条目**用。带主语前缀既浪费 token，又干扰相似度比较。
- **`用户明确否定/不想做的方向，记为一条'不关注 X / 放弃 X'`**——注释里那句"**不感兴趣也是信号**"是这层的关键：只知道用户要什么、不知道他不要什么，照样会推错东西。

容错还是老三层：剥代码块 → `json.loads` → **失败回空表**（记忆提炼失败绝不能影响主流程）。

### 4.3 太琐碎的寒暄直接跳过

```python
_TRIVIAL_GOALS = {"谢谢", "好的", "嗯", "好", "ok", "OK", "知道了", "好的好的"}

if len(goal_s) < 4 or goal_s in _TRIVIAL_GOALS:
    _EXTRACT_STATS["skipped"] += 1
    return
```

**"谢谢"里没有画像信息，但提炼是一次真金白银的 LLM 调用。** 注释也说了这只是轻量版，完整版是"**攒 N 轮再提炼**"（当前没做）。

## 五、写路径：语义画像的增量合并（本章最难的一段）

### 5.1 旧做法错在哪

最早的做法是"**删光重建**"：每次提炼先 `delete_by_user` 把这个用户的记忆整组清空，再把 LLM 输出的全量画像重新写进去。三个问题：

| 问题 | 后果 |
|---|---|
| **并发下丢记忆** | 两个请求同时提炼，A 清空 → B 清空 → A 写完 → B 写完，A 的结果没了 |
| **没法逐条管理** | 没有"这条记忆"的概念，删只能全删 |
| **没有情景层** | 只有一份画像串，装不下"发生过什么" |

### 5.2 新做法：逐条比对，四种结果

`merge_semantic_memories` 把 LLM 给的**当前全量画像**和库里**生效中的旧行**逐条比对：

```python
for s in clean:
    best_i, best_r = -1, 0.0
    for i, row in enumerate(old):
        if used[i]:                       # 每条旧行最多被认领一次
            continue
        r = _ratio(s, row.text)           # difflib 字面相似度
        if r > best_r:
            best_i, best_r = i, r
    if best_i >= 0 and best_r >= 0.90:
        used[best_i] = True
        keep_ids.append(old[best_i].id)                 # ① 同一条 → 只刷热度
    elif best_i >= 0 and best_r >= 0.45:
        used[best_i] = True
        fuzzy.append((s, best_i))                       # ② 歧义档 → 等 LLM 判
    else:
        add_texts.append(s); n_new += 1                 # ③ 全新 → append
```

| 相似度 | 判定 | 动作 |
|---|---|---|
| **≥ 0.90** | 同一条偏好 | 只刷新热度（`importance+1` / `last_access`），不重写文本 |
| **0.45 ~ 0.90** | **歧义** | 交 LLM 判是"更新"还是"并列"（见下） |
| **< 0.45** | 全新偏好 | 新增一行 |
| **没被任何新句认领的旧行** | 不再成立 | 作废（`active=False` + 删向量，**行保留可审计**） |

### 5.3 0.45~0.9 那档为什么非 LLM 不可

这是本文件里**最说明问题的一段注释**（实测数据）：

```python
"""为什么非它不可：difflib 实测分不出这两类 ——
"负责男装类目 vs 负责女装类目"=0.833（真更新）、"关注退货率 vs 关注退款率"=0.800（并列），
字面相似度几乎一样，语义判定只能交给模型。"""
```

这两组分数的**差距只有 0.033**，可语义上天差地别：

| 对 | 字面分 | 真实语义 | 该怎么做 |
|---|---|---|---|
| 负责**男装**类目 / 负责**女装**类目 | 0.833 | **更新**——他改负责类目了 | 作废旧行，写新行 |
| 关注**退货**率 / 关注**退款**率 | 0.800 | **并列**——两个都关注 | 两行都保留 |

按字面分怎么设阈值都会错。所以把这一档**批量交给 LLM 判一次**：

```python
_JUDGE_PROMPT = """下面每组是【已记住的旧偏好】和【本轮新出现的句子】，请逐组判断关系：
- update：新句是旧句的**更新版**，同一件事变了、新句取代旧句
- parallel：两句是**并列的不同事实**，都成立、互不取代
只输出 JSON 字符串数组，长度与组数一致…"""
```

**注意成本控制**：整轮合并**只多花一次 LLM 调用**（所有歧义对打包成一个请求），不是每组一次。而且判定失败（格式异常 / 抛异常）会**降级回字面判据，当作"更新"**——退回旧行为，不是崩溃。

### 5.4 从"缺席"推断作废，必须有护栏

最后那一类——**没被任何新句认领的旧行 = 作废**——是这个算法里**最危险**的一步。

因为它是**从"没出现"推断"不存在"**：

```
LLM 这次少写了一条  →  那条旧记忆被当作"不再成立" →  作废
LLM 输出被截断了    →  同上
```

这就是**静默丢真记忆**：不报错，用户只觉得"它怎么又忘了"。所以加了比例护栏：

```python
RETIRE_GUARD_RATIO = 0.5      # 单轮"从缺席推断作废"的比例上限
RETIRE_GUARD_MIN_ROWS = 3     # 低于 3 条时不套护栏（1 条里作废 1 条永远是 100%）

unclaimed = [old[i] for i in range(len(old)) if not used[i]]
guard = len(old) >= RETIRE_GUARD_MIN_ROWS and len(unclaimed) > len(old) * RETIRE_GUARD_RATIO
if guard:
    logger.warning("记忆合并护栏触发：%d/%d 条旧记忆未被本轮认领，本轮不作废（防静默丢记忆）", ...)
else:
    retire.extend(unclaimed)
```

**逻辑**：如果**超过一半**的旧记忆这轮都没被认领，那更可能是"**LLM 输出不全**"而不是"用户的偏好全变了"——**整批不作废**。

`MIN_ROWS = 3` 那个细节也很讲究：只有 2 条记忆时，"作废 1 条"就是 50%，比例在这里**没有统计意义**，套护栏反而会让正常的更新失效。

> 这条设计值得单独记住：**当推断依据是"信息缺失"时，缺失本身也可能是"采集失败"，而不是"事实不存在"**。必须给个比例护栏，宁可多留也不能静默丢。

### 5.5 情景记忆：append + 去重 + TTL

```python
EPISODIC_TTL_DAYS = 30

async def save_episodic_memories(user_id, events, source_session=None, ttl_days=EPISODIC_TTL_DAYS):
    old = await _active_rows(user_id, KIND_EPISODIC)
    to_add = [e for e in clean if not any(_ratio(e, row.text) >= 0.85 for row in old)]
    ...
    expires = now + timedelta(days=ttl_days) if ttl_days else None
```

比语义简单得多，只有两件事：**相似度 ≥0.85 视为重复跳过**，写行时带上 `expires_at`。

**过期不等于删除**：`_active_rows` 只是不再返回它，**行还留在库里**（可审计、可回溯）。这和 `active=False` 的作废是同一套思路——**"不再参与召回"和"从世界上消失"是两件事**。

## 六、读路径：召回怎么加权

```python
async def recall_user_memories(user_id: int, query: str, top_k: int = 3) -> str:
    rows = await _active_rows(user_id)              # 生效中的全部（语义 + 情景）
    if not rows:
        return await get_user_profile(user_id)      # ① 全空 → 兜底一句话画像

    vector = await embed_text(query)
    hits = search_similar(vector, top_k=max(top_k * 4, 12),
                          collection_name=MEMORY_COLLECTION, user_id=user_id)   # ② 多召回
    for h in hits:
        age_days = max(0.0, (now - (row.created_at or now)).total_seconds() / 86400.0)
        recency = 1.0 / (1.0 + 0.5 * age_days)                        # 越近越相关
        weight = (h["score"] or 0.0) * (1.0 + 0.3 * (row.importance or 1)) * recency
```

### 6.1 三个因子各管一件事

```
weight = 相似度 × 重要性 × 新鲜度
```

| 因子 | 形式 | 回答的问题 |
|---|---|---|
| **相似度** `h["score"]` | 向量余弦分 | 和这次的问题**相关吗** |
| **重要性** `1 + 0.3 × importance` | importance 1~10 → 权重 1.3~4.0 | 这条是**核心特征**还是随口一提 |
| **新鲜度** `1/(1 + 0.5 × age_days)` | 双曲线衰减：1 天 0.67、10 天 0.17、30 天 0.06 | 是**最近**的还是一年前的 |

两个系数是权衡出来的：

- 重要性用 `1 + 0.3 × imp` 而不是 `× imp`：**保证最低权重也是 1**——否则一条 importance=1 的记忆几乎永远召不回，重要性就变成了"一票否决"；
- 新鲜度用 `1/(1+0.5d)` 而不是指数衰减：**衰减更平缓**，一周前的记忆还有 0.22 的权重。记忆不该像搜索结果那样"过了三天就作废"。

### 6.2 命中不足时补什么？只补语义

```python
# 只补 semantic（P2-9）：情景记忆是"当时发生了什么"，和当前问题的相关性无法靠"最近"推断，
# 塞进来只会污染 prompt —— 而且它本来就更该靠向量命中，不该靠兜底。
if len(picked) < top_k:
    recent = sorted((r for r in rows if r.kind == KIND_SEMANTIC),
                    key=lambda r: r.created_at or datetime.min, reverse=True)
```

补**语义**记忆是为了接住"**刚才那个数据**""**上次说的那个**"这类指代——它们和当前问题的字面/语义都不像，向量召不回，但"最近确认为真的偏好"大概率相关。

**但情景记忆不能这样补**：它是"发生过的事"，"最近发生过"和"和这个问题相关"完全没关系。硬塞进来只会污染 prompt。

### 6.3 召回**不涨**重要性（一个被修掉的坑）

```python
# 只刷新 last_access（管理界面展示"最近用过"），**不再动 importance**（P2-8）：
# 召回只说明"这条被搜到了"，不说明它重要。以前每召回一次就 +1 封顶 10，
# 聊十来轮后所有记忆都饱和成 10，"重要性"直接退化成噪声。
# importance 现在只在合并 keep 时涨（LLM 每轮重新确认它仍成立 = 真的稳定偏好）。
```

这个 bug 很典型，值得完整记住：

```
初版：召回一次 → importance +1（当作"可用度反馈"）
问题：聊二十轮之后，只要被搜到过的记忆全封顶 10
结果：importance 的区分度归零 → 三个因子里有一个变成了常数
```

**修法是把"重要性"的来源换掉**：从"被搜到过"改成"**被 LLM 反复确认仍然成立**"——也就是只在**合并命中的 keep 分支**涨。这才是"稳定偏好"的正确定义。

> 顺带一个**注释漂移**：`user_memory.py` 里 `importance` 那行的行内注释还写着 *"被召回命中 +1（可用度反馈）"*，而 `store.py` 里的实际行为已经改成"召回不涨"。**代码是对的，注释是旧的**——和第六章那个"1536 维"是同一类问题。

### 6.4 输出的样子

```python
lines = []
for row in picked:
    prefix = "（事件）" if row.kind == KIND_EPISODIC else ""
    lines.append(f"{prefix}{row.text}")
```

**给情景记忆加 `（事件）` 前缀**，是为了让模型知道"这是我记得发生过的事"，而不是"用户现在的设定"。不加这个标记，模型会把"上周转化率掉到 2%"当成一个**当前事实**来说。

## 七、两个存储怎么对齐

这是本章**工程含金量最高**的一段。核心问题：

> **SQLite 和 Qdrant 没有共享事务。**

写一条记忆要动两处：向量库删旧的插新的、SQLite 提交行。**先做哪个都可能半路崩**：

| 崩在哪 | 后果 | 严重程度 |
|---|---|---|
| 向量已删/没插上，SQLite 行还在 | 这行**永远召不回**——不报错、不异常，**静默降级** | **最坑** |
| 向量插上了，SQLite 提交失败 | **孤儿向量**，白占空间、永远没人引用 | 只是浪费 |

代码里的结论很硬：

> **两边顺序怎么调都堵不住（换顺序只是把故障从一类挪到另一类）**，真正的出路是承认 SQLite 是唯一事实源，然后**定期拿事实源去校准索引**。

`reconcile_memory` 就是对账：

```python
actual   = list_point_ids(MEMORY_COLLECTION)                       # 向量库里实际有什么
expected = {r.qdrant_point_id for r in rows if r.qdrant_point_id}  # SQLite 认为该有什么

# ① 缺向量的生效行 → 重新 embedding 补上
need_fix = [r for r in rows if not r.qdrant_point_id or r.qdrant_point_id not in actual]
...
# ② 孤儿向量（没有任何行引用的点）→ 删
orphans = actual - expected
```

两边各修一种：

- **缺向量** → 重新向量化补上（**功能恢复**）；
- **孤儿向量** → 删掉（**清理泄漏**）。

**为什么这套能成立？** 回到第 2 节那条地基：**SQLite 是事实源，Qdrant 只是索引**。索引坏了可以重建，因为**真数据一直在 SQLite 里**。如果当初把文本只存在向量库，那就永久丢了——这就是"每行落 SQLite"的真正回报。

> 补向量失败怎么办？注释写得很清楚：*"补不了就留着，下次对账再试，**绝不静默丢文本**"*。数据库里的文本才是事实。

## 八、并发与可靠性：三个真 bug

这一节是整个记忆系统里**最值得面试讲**的部分，因为三条都是**"上线才暴露、且现象诡异"**的问题。

### 8.1 per-user 写锁：并发覆盖

```python
# per-user 提炼写锁：同一用户的 /chat 与 /chat/stream 可能并发触发提炼，
# 记忆是"读旧→merge 写"的读改写，不加锁会互相覆盖丢记忆（外部评审 M3 真 bug）。
# 用 WeakValueDictionary：锁只在"正被等待"期间被强引用，没人用了自动回收
_EXTRACT_LOCKS: "weakref.WeakValueDictionary[int, asyncio.Lock]" = weakref.WeakValueDictionary()
```

**为什么必须锁**：`merge_semantic_memories` 是典型的**读—改—写**——先读旧画像当合并底子，再写新结果。两个请求同时进来：

```
请求 A 读旧画像 → 请求 B 读同一份旧画像 → A 写 → B 写（A 的更新被覆盖）
```

用户开两个窗口、或者流式和非流式接口同时用，就会撞上。表现是"**记忆时有时无**"。

**为什么用 `WeakValueDictionary`**：普通 dict 只增不减，**用户越多内存越涨**（注释标为 P2-16）。弱引用字典让锁在没人等待时自动回收，长期跑也不漏。

### 8.2 后台任务要持有强引用

```python
# 后台任务的强引用集合：asyncio.create_task 的返回值没人接的话，任务可能在跑完前被 GC，
# 表现就是"这轮记忆莫名没提炼"（P2-16）。持有引用 + 完成即摘除。
_BACKGROUND_TASKS: set[asyncio.Task] = set()

def _spawn(coro) -> asyncio.Task:
    task = asyncio.create_task(coro)
    _BACKGROUND_TASKS.add(task)
    task.add_done_callback(_BACKGROUND_TASKS.discard)   # 完成即摘除，不留内存
    return task
```

这是 **asyncio 的一个经典陷阱**：`create_task` 返回的 Task 如果**没有任何强引用**，事件循环只持弱引用——**任务可能在跑完之前就被 GC 掉**。而它的表现是"什么都没发生"（不报错、不警告），最难查。

**注意 `add_done_callback` 那句**：持有强引用是为了防 GC，但也不能**永久持有**，否则任务对象越攒越多。完成即摘除，两边都照顾到。

### 8.3 失败落重试表（这就是第 03 章那个挑战的答案）

提炼失败以前只写一行日志，用户感受是"记忆时有时无"。现在**把失败的提炼连整轮原料一起落一行**：

```python
db.add(MemoryExtractTask(user_id=user_id, session_id=sid, goal=goal,
                         reply=reply, status="pending", attempts=1,
                         last_error=f"{type(error).__name__}: {error}"[:500]))
```

启动时重放：

```python
async def retry_pending_extracts(limit: int = 20) -> dict:
    """重放上次没跑成的提炼（启动时调用）

    重放安全的前提是写路径幂等：语义走增量合并（同义只刷热度）、情景按相似度去重，
    所以重复跑一轮最多是白做一次合并，不会把记忆堆重复。
    """
```

> **第 03 章的练手挑战三问的就是这个**：*"`memory_extract_tasks` 的重放为什么安全？"*
> 答案就是注释里那句——**因为两条写路径都幂等**：
> - 语义合并：同义句只**刷新热度**，不会写第二条；
> - 情景 append：相似度 ≥0.85 **去重跳过**。
>
> 所以"同一轮对话被重放两次"最多是白做一次合并，**不会出现两条一样的偏好**。**重放安全不是白来的，是写路径幂等换来的**——这也是第 03 章那句"重放安全的前提是写路径幂等"的兑现。

**不能无限重试**：

```python
# 反复失败的（比如 API Key 失效）就别无限重试了
row.status = "failed" if row.attempts >= 3 else "pending"
```

**API Key 失效这种失败，重试一万次也不会成功**，只会一直占着重放队列。所以 3 次就转 `failed` 退出循环。

### 8.4 失败也要能看见

```python
_EXTRACT_STATS = {"ok": 0, "skipped": 0, "failed": 0, "retried": 0}
```

**失败不再只躺在日志里，`/api/memory` 能看到。** 这已经是本项目第四次出现同一条原则了：

| 章 | 位置 | 做法 |
|---|---|---|
| 02 | 工具契约层 | 降级要告警 |
| 02 | 范围降级 | "静默降级 = 没人查得到" |
| 05 | 子任务异常隔离 | "降级不等于免责：必须留日志" |
| **07** | **记忆提炼** | **失败落表 + 计数进接口** |

**后台任务尤其需要这个**——它没有用户在看，失败了连"页面报错"都没有。**没有计数器，就等于没有发生。**

## 本章小结

- **三层记忆**：会话历史（短期）/ 语义画像（稳定）/ 情景记忆（会过期，30 天 TTL）；外加一句话画像表兜底
- **长期记忆存两处但只有一个事实源**：SQLite 每行一条（可逐条管理/审计），**Qdrant 只是向量索引**
- 会话历史超预算**按整条丢**（保住最近几轮完整），且**必须在存当前消息之前读**
- 提炼在**后台**跑，原料是**整轮问答**（画像信号藏在"答完之后用户什么反应"里），寒暄跳过
- 语义合并**四档处理**：≥0.9 刷热度 / 0.45~0.9 **交 LLM 判更新还是并列**（difflib 实测分不出）/ <0.45 新增 / 未认领作废
- **"从缺席推断作废"要加比例护栏**——信息缺失也可能是采集失败，宁可多留不能静默丢
- **召回加权 = 相似度 × 重要性 × 新鲜度**；命中不足**只补语义不补情景**；**召回不涨重要性**（否则聊十几轮后全饱和成 10，因子退化成噪声）
- **两个存储没有共享事务**，换顺序堵不住 → **承认 SQLite 是事实源 + 定期对账**（缺向量补、孤儿向量删）
- **三个并发/可靠性真 bug**：per-user 写锁（读改写覆盖）、后台任务强引用（防 GC）、失败落重试表（**重放安全靠写路径幂等**）
- **后台任务失败必须可观测**：落表 + 计数进接口——没有计数器就等于没发生

## 练手挑战

**挑战一（必做）：把护栏的边界测出来**

构造 3 条旧记忆，让新句只认领 2 条（未认领 1/3 < 50%）→ 应该**正常作废**；再构造 3 条只认领 1 条（未认领 2/3 > 50%）→ 应该**触发护栏不作废**。

**验收**：两条断言都过——证明 `RETIRE_GUARD_RATIO` 和 `MIN_ROWS` 都在起作用。

**挑战二（推荐）：给新鲜度加一个"半衰期"参数**

现在 `recency = 1/(1 + 0.5 × age_days)` 里的 `0.5` 是硬编码的。把它抽成常量（或配置项），然后算一下：**半衰期是多少天**？（提示：解 `recency = 0.5`）

**挑战三（加分）：把召回末尾那 N 次查询压成 1 次**

`recall_user_memories` 最后刷新 `last_access_at` 是这么写的：

```python
for row in picked:
    r = await db.get(LongTermMemory, row.id)   # ← 每条一次查询
    if r:
        r.last_access_at = now
```

`picked` 最多 `top_k`（默认 3）条，所以是 3 次查询。改成**一条 `update(...).where(id.in_(...))`**（`merge_semantic_memories` 里作废旧行就是这种写法）。

**验收**：行为不变（`last_access_at` 被刷新），日志里 SQL 从 N 条变 1 条。顺手想一下：如果 `top_k` 调到 50，这个改动的意义会变大还是变小？
